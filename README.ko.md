# dart-review-agent

한국 상장사의 공시 재무제표(OpenDART)로 재무 수치를 **조회하고 기간끼리 비교하는** 로컬 도구다. 비교가 성립할 때만 비교한다. 조회한 보고서 안에서 연결·별도 기준, 기간 길이, 통화가 같고 재작성이 보이지 않아야 한다. 아니면 거절하거나 되묻고 이유를 말한다. 조회하지 않은 정정 공시까지 확인하는 것은 아니다. 영어판: [README.md](README.md).

**v0.1 (2026-10-09).** 한 줄로 말하면 "**규칙 기반 재무 비교 도구 + LLM 교차 확인 실험**"이다. 사전 등록한 평가를 두 번 했다.

| 평가 | 질문 | 공식 판정 | 제품의 틀린 수치 답 | 해결률 (제품 / 규칙만) | LLM이 막은 잘못된 수치 답 / 잃은 정답 |
|---|---|---|---|---|---|
| 3-1 봉인 평가 | 사람이 쓴 36개 | **기준 미달** (비교용 방식의 채점기 불일치) | 0 / 수치 답 22 | 22/23 / **23/23** | 0 / 1 |
| 3-5 대량 템플릿 평가 | 규칙으로 만든 600개 | **기준 충족** (3-1 뒤 고친 채점기, 실행 뒤 완화한 판정 조건 P5 기준) | 0 / 수치 답 419 | 419/480 / **476/480** | 0 / **62** (답이 있는 질문 57, 함정 5) |

- 두 평가 모두 제품은 **틀린 수치를 하나도 내지 않았다.**
- **키워드 규칙만 쓴 쪽이 더 많이 맞혔다.** LLM 교차 확인은 잘못된 수치 답을 하나도 막지 못했고, 모델의 오독과 출력 한도 때문에 맞게 처리할 수 있던 질문을 잃었다.
- 질문은 회사 4곳에 한정되고, 3-5는 정해진 표현 틀로 만든 질문이다. 그래서 일반적인 정확도로 읽지 않는다.

v0.1.0의 `dart_review/`는 평가한 고정 커밋 P(`c182075`)와 같다. v0.1.1은 문구만 바꿨다. 도구의 참고·이유 문장을 존댓말로 보여 주고, 계정을 되묻는 질문이 비교를 전제하지 않게 했다. 상태와 수치는 하나도 바뀌지 않았고, 재생 테스트가 저장된 실행과 대조해 이를 확인한다.

**v0.1.2**는 3-5에서 찾은 제품 결함을 고쳤다.
- 모델이 쓴 공식 영문 회사명을 한국어 공식명으로 바꾼다(corpCode.xml 기준).
- 질문에 쓰인 모르는 회사는 범위 밖으로 거절한다.
- 두 해석이 모두 거절이면 일치로 본다.
- 계정 행을 못 찾으면 "데이터 없음" 대신 숫자 없는 "확인 필요"로 답한다.
- 비표준 계정명 하나를 더하고, 문구 두 가지를 고쳤다.

3-5의 기록된 모델 응답을 재생해 보면 22개 문항이 개선되고 나빠진 문항은 없다. 다만 이미 결과를 본 질문이라 평가 결과로 쓰지 않는다. v0.1.2의 성능은 새 질문으로 다시 잰다.

```text
$ python -m dart_review demo        # 인증키, 모델 서버, 네트워크 없이 실행
## 삼성전자 매출액
**검증 상태:** 비교 가능
| 구분 | 기준 | 기간 | 금액(원) | 보고서 | 접수번호 |
| 비교 기간 | 연결 | 2025년 연간(1~12월) | 333,605,938,000,000 | 2025년 사업보고서 | 20260310002820 |
| 기준 기간 | 연결 | 2024년 연간(1~12월) | 300,870,903,000,000 | 2025년 사업보고서 | 20260310002820 |
**변화:** 32,735,035,000,000원 (10.88%, 증가)
```

## 봉인 평가 결과 (3-1, 사전 등록)

- 대상은 개발에 쓰지 않은 회사 4곳(NAVER, CJ제일제당, 이마트, LG에너지솔루션)이고, 질문은 36개다.
  - 14개는 사용자가 데이터를 보지 않고 썼다.
  - 22개는 Claude가 썼다.
- 실행 전에 질문, 정답, 기준, 제품 고정 커밋을 커밋했다(사전 등록 R = `c9a4a55`). 그 뒤 세 방식을 한 번씩 실행했다.

| 방식 | 수치 질문 23개 정답 | 거절·되묻기 13개 정답 | **틀린 수치 답** | 그 밖의 실패 | 모델 시간 |
|---|---:|---:|---:|---|---:|
| 키워드 규칙만 | **23** | 13 | **0** | 없음 | 0 |
| **교차 확인 (제품)** | 22 | 13 | **0** | 불필요한 되묻기 1 | 8.7분 |
| 모델 해석만 | 21 | 10 | **0** | 잘못된 거절 4, 잘못된 되묻기 1 (이 중 2개는 채점기 불일치) | 12.1분 |

- **공식 판정은 "기준 미달"이다.**
  - 제품에 대한 기준 네 가지는 모두 충족했다. 틀린 수치 답 0, 해결률 22/23(기준 70% 이상), 불필요한 되묻기 비용 4.3%(기준 25% 이하), 범위 밖·모호 질문 10/10이다.
  - 미달 원인은 비교용 "모델 해석만" 방식이다. 이 방식은 답 앞에 "이렇게 이해했습니다: …2025년…"을 붙이는데, 고정된 채점기가 이 연도를 근거 없는 숫자로 셌다.
  - 이것은 제품 설계(해석 연도는 허용)와 채점기 사이의 불일치다. 실행 전 독립 검토 두 번에서도 잡지 못했다. 실행 뒤에 채점기를 고쳐 결과를 바꾸지 않았고, 허용했을 때의 결과는 민감도로만 따로 적었다.
- **이 36문항에서 LLM이 보탠 것은 없었다.** 규칙은 틀리고 모델은 맞은 경우가 0건, 교차 확인이 막은 잘못된 수치 답도 0건이다. 오히려 모델이 매출을 "시점 값"으로 잘못 읽어서, 규칙만으로 답했을 질문 하나를 되물었다.
- **모델에게만 맡기면 생기는 일:**
  - 기간이나 계정을 잘못 읽어 답이 있는 질문을 거절했다.
  - 거절 이유를 틀리게 말했다(회사가 여러 개인데 "다루지 않는 회사"라고 함).
  - 온도 0인데도 바이트까지 같은 요청에 실행마다 다른 해석을 냈다.
- **"0건"의 무게:**
  - 이 36문항에서 관찰한 결과일 뿐이다. 답한 수치 질문 22개에서 0건이면 95% 신뢰 상한은 약 13%다.
  - 질문 대부분이 2024~2026년 단순 조회·비교였다. 재작성, 부호 전환, 계정ID 오표기 같은 어려운 유형이 적었다.
  - 그래서 규칙이 모두 맞힌 것은 "규칙이 충분히 강하다"는 증거라기보다 "질문이 규칙 범위 안에 있었다"는 뜻에 가깝다.

## 대량 템플릿 평가 결과 (3-5, 사전 등록)

- **방법:** 3-1과 같은 회사 4곳에 대해 질문 600개를 정해진 표현 틀로 만들었다. 3-1 결과와 관계없이 하기로 미리 약속한 평가다.
  - 생성 방식: 회사 × 기준 × 계정 × 기간의 모든 조합을 만들고 고정 시드로 뽑았다.
  - 구성: 답이 있는 질문 480개(조회, 전년 비교, 두 보고서에 걸친 재무상태표 비교, 연결·별도 나란히)와 함정 120개(4분기 3개월, 현금흐름 분기 3개월, 2014년, 범위 밖, 모호, 복합 질문)
  - 사전 등록: 질문, 정답, 기준, 제품 v0.1.1을 실행 전에 커밋했다. Codex 검토를 반영한 뒤 사전 등록했다.

| 기준 | 교차 확인 (제품) | 충족 |
|---|---|---|
| 잘못된 수치 답 0 | **0** (수치를 보인 답 419개) | 예 |
| 해결률 ≥ 80% | 419/480 = 87.3% | 예 |
| 함정 처리 ≥ 90% | 112/120 = 93.3% | 예 |
| 근거 없는 숫자 0 | 0 | 예 |

- **판정이 채점기 수정에 달려 있다.** 3-1 때 채점기라면 되묻기 문장 8개의 해석 연도가 근거 없는 숫자로 잡혀 기준 미달이 된다. 수정은 3-1에서 드러난 불일치를 고친 것이다. 3-5 실행 전에 계약에 적고 검토를 거쳐 사전 등록했다.
- **판정 조건도 실행 뒤에 한 번 완화했다(P5).** 계약은 실행마다 커밋하라고 했는데, 판정기는 두 실행이 같은 커밋이어야 판정했다. 실행 기록 파일만 다른 커밋을 같은 코드로 보게 고쳤다. P5가 없었다면 "판정 보류"였다. 점수와 문턱은 그대로다.
- **규칙만:** 476/480(99.2%), 잘못된 수치 답 0. 실패 4개는 이마트의 비표준 현금흐름 행이다.
- **LLM:** 막은 잘못된 수치 답 0, 잃은 정답 62(답이 있는 질문 57, 함정의 올바른 처리 5).
  - 두 해석이 갈린 40건: 분기말을 3개월로 읽음 16, 회사를 영어로 씀 14, 연간을 시점으로 읽음 4, 연도를 다르게 읽음 3, 그룹명을 회사로 확정 2, "이익"을 한 계정으로 확정 1. 이 가운데 37건이 불필요한 되묻기가 됐다.
  - 출력 한도 도달로 보류 24
- **오류율 참고 계산:** 수치 답 419개에서 0건이면 약 0.71%다. 독립 시행을 가정한 계산이라 엄밀한 상한은 아니다. 419개 답은 원본 근거 행을 730회 참조했고, 서로 다른 행은 642개다.
- **찾은 제품 결함:** 모델 해석의 회사 이름 정규화, 비표준 계정명(그리고 "자료가 없다"는 잘못된 설명), 처음 보는 회사의 범위 밖 처리. 평가 중에는 고치지 않았다.

## 보기보다 어려운 이유

OpenDART의 같은 칸이 보고서와 재무제표에 따라 뜻이 다르다. 개발용 캐시 보고서 72건으로 확인했다([데이터 확인 기록](docs/DATA_NOTES.ko.md)).

- 분기 손익계산서의 `thstrm`은 3개월인데, 분기 현금흐름표의 `thstrm`은 이미 연초부터의 누적이다.
- 분기 재무상태표의 "전기"는 전년 같은 분기말이 아니라 **전년 말**이다.
- 나중 보고서가 앞 값을 **재작성**한다(카카오, 셀트리온, 봉인 평가의 CJ제일제당 부채).
  - 카카오 2024년 3분기 매출 증감률은 재작성 값 기준 −4.48%다.
  - 처음 공시한 값 기준으로는 −11.08%다.
- 계정ID가 틀린 경우가 있다. 카카오 2023년 분기 매출은 `ifrs-full_GrossProfit`으로 표기돼 있다.

이 규칙들은 모두 코드이고, 실제 캐시로 테스트한다. 규칙을 순진한 버전으로 바꾸면 해당 함정 테스트가 실패하는 것도 확인했다(11개 중 11개 검출, `scripts/check_trap_tests.py`).

## 동작 방식 (교차 확인형)

```text
질문 ──► 키워드 규칙 ──► 해석 A ─┐
     └─► 로컬 모델   ──► 해석 B ─┤ 같은가? ── 예 ─► 도구(규칙이 OpenDART 데이터를 판정) ─► 코드가 답을 씀 ─► 숫자 검사 ─► 답
                                 └ 아니오 ─► 두 해석을 보여 주고 어느 쪽인지 되묻는다
```

- **두 해석자가 질문을 따로 읽는다.**
  - 하나는 키워드 규칙이다.
  - 다른 하나는 로컬 모델(Ollama의 `gpt-oss:20b`)이다. 해석 JSON을 한 번 요청하고, 프롬프트에 기준 날짜를 넣는다.
  - 둘이 같으면 코드가 답하고, 다르면 되묻는다.
  - 두 해석자는 같은 저자가 같은 기본값 표로 만들었다. 그래서 둘의 오류가 서로 독립이라고 보장하지는 않는다.
- **한쪽만 읽은 경우:**
  - 모델 해석을 얻지 못하면 답하지 않는다.
  - 규칙이 못 읽고 모델만 읽으면(예: "순익") 코드가 쓴 "이렇게 이해했습니다: …"를 맨 앞에 두고 답한다. 해석이 틀렸으면 사용자가 바로 볼 수 있다.
  - `--no-model`은 사용자가 직접 고른 규칙 전용 모드이고, 답에 그렇게 표시한다.
- **지원하지 않는 계정은 비슷한 계정으로 바꿔 읽지 않고 거절한다.** 유동자산(≠자산총계), 매출원가(≠매출액)처럼 지원 계정 이름을 일부로 포함하는 계정도 마찬가지다.
- **문장은 코드가 쓴다.** 금액, 기간, 기준, 이유 같은 사실 문장은 모두 코드가 도구 결과로 쓴다. 모델은 문장을 쓰지 않는다.
- **보여 주기 전에 숫자를 검사한다.** 본문과 Markdown 보고서 전체의 숫자가 대상이다.
  - 금액·비율·접수번호는 도구 결과에 있어야 한다.
  - 연도는 도구 결과나 질문에 있어야 한다. 되묻기 문장과 "이렇게 이해했습니다" 문장에서는 해석이 제안한 연도도 허용한다.
  - 근거 없는 숫자가 하나라도 있으면 답을 내보내지 않는다.
  - 이 검사는 같은 값이 근거에 있는지만 본다. 그 값을 맞는 기간에 붙였는지는 렌더러 테스트와 사람 검토로 확인한다.

## 여기까지 온 과정 (실패한 설계 포함)

개발 질문 13개와 표현 변형 13개로 설계를 골랐다([보고서](eval/feasibility_2026-10-07/REPORT.md)).

| 설계 | 결과 | 보여 준 것 |
|---|---|---|
| 올바른 도구 결과를 주고 모델이 답 전체를 씀 | 자동 11/13, **본문 검토 뒤 1/13** | 구조화된 칸은 맞았지만 본문이 한 단어이거나 기준·이유를 빠뜨림 |
| 에이전트: 모델이 도구를 부르고 결정 | 23/26 | 결정 단계 실패, 근거 없는 원인을 단정한 해석 문장 |
| 키워드 규칙만 | 25/26 | **에이전트를 이김.** 다만 실패 1건이 확신에 찬 틀린 비교 |
| **교차 확인 (현재)** | **25/26, 확신에 찬 틀린 답 0** | 규칙의 오해가 되묻기로 바뀜 |

## 어떻게 평가했나

- **사전 등록:** 데이터를 보기 전에 계약, 제품 고정(P), 질문을 커밋했다. 사용자 질문은 해시로만 먼저 약속했다.
- **정답:** 원본 칸에서 따로 계산하고 제품 규칙과 대조했다.
  - 둘이 다른 1건(C06)은 원본을 다시 확인해 정답을 고쳤다(재작성 발견, 사용자 승인).
  - 이 수정은 제품과의 대조가 계기였으므로 완전히 독립적인 판정이 아니다. 보고서에 그 사실과 민감도를 적었다.
- **판정:** Claude가 방식마다 본문을 1차 검토했고, 사용자가 확인했다. 그 뒤 엄격한 판정기(`eval/judge.py`)를 한 번 돌렸다. 판정기는 해시가 맞지 않으면 판정을 보류한다.
- **독립 검토:** 다른 에이전트(Codex)에게 다섯 번 검토를 받았다. 지적마다 재현하고 반영 여부를 기록했다([docs/reviews/](docs/reviews/)). 실행 전에 검토지 생성 중단, 실행 사이 봉인 해시 비교 누락 같은 평가 도구 결함을 잡았다.

## 한계

- 회사 7곳, 계정 6개, 한 번씩 실행한 결과다.
- 봉인 평가의 질문은 쉬운 편이었다. 36개 중 22개는 제품 설계를 아는 사람(Claude)이 썼다.

- 로컬 모델은 온도 0에서도 결정적이지 않다.
- 다루지 않는 것: 금융사 재무제표, 여러 회사·여러 계정을 한 번에 묻는 질문, "왜 늘었나" 같은 원인 설명.
- 3-5의 질문은 기계적이다. 3-5의 사람 검토는 실패 전부와 통과 표본 60개만 봤다.
- 다음은 3-5에서 찾은 제품 결함의 보완이다. 고친 버전은 이미 결과를 본 질문이 아니라 새 질문으로 다시 잰다.

## 빠른 시작

Python 3.10 이상이고, 표준 라이브러리만 쓴다.

```bash
python -m dart_review demo
python -m unittest discover -s tests
python -m dart_review ask "삼성전자 매출 알려줘" --no-model --cache demo/opendart --offline --reference-date 2026-10-08
```

`--reference-date`를 빼면 오늘 날짜가 기준이 된다. 연도 없는 질문은 기준 날짜로 최근 사업보고서 연도를 정하므로, 데모 자료에 없는 연도를 찾게 될 수 있다.

본인 OpenDART 인증키를 `~/.config/opendart/api_key`(권한 600, `DART_API_KEY_FILE`로 위치 변경 가능)에 두고, 로컬 Ollama에 `gpt-oss:20b`가 있으면 다음처럼 쓴다.

```bash
python scripts/fetch_dev_cache.py
python -m dart_review ask "카카오 2024년 3분기 매출은 전년 같은 분기보다 얼마나 줄었어?"
```

## 데이터 출처와 이용

- **데이터 출처: 금융감독원 OpenDART (opendart.fss.or.kr).**
- 원본 응답 전체는 저장소에 넣지 않는다(`cache/`는 git 제외). 저장소에 있는 것은 다음뿐이다.
  - 데모용 축소본(대상 계정 행만, 원본 1,012행 중 73행)
  - 정답과 실행 기록에 나온 계정 행과 수치
- OpenDART 이용약관(2020-01-21 시행)에서 공시 데이터의 재배포를 직접 금지하는 조항은 찾지 못했다. 그렇다고 재배포 허가를 확인한 것은 아니다. 약관에 없는 저작권 사항은 저작권법과 공공데이터법을 따른다(제16조 ④). 이것은 법률 자문이 아니라 공개 전에 확인한 내용이다([공개 전 점검](docs/PUBLICATION_CHECK.ko.md)).
- 수치의 정확성과 원 공시에 대한 책임은 공시한 회사와 OpenDART에 있다. 이 저장소의 수치는 2026-10-07~08에 받은 응답에서 뽑았다.
- 이 도구의 출력은 투자 조언이 아니다.

## 안전과 재현

- OpenDART 인증키는 기본적으로 `~/.config/opendart/api_key`에서 읽는다(`DART_API_KEY_FILE`로 위치 변경 가능). 키 값은 로그·캐시·저장소에 남기지 않는다.
- 공개 전에 두 가지를 검사했고, 검사 범위 안에서 발견은 0건이었다. 이것이 비밀값이 없다는 증명은 아니다. 패턴에 맞지 않는 형태(인코딩된 값, 바이너리 파일)는 잡지 못한다.
  - 지금 파일 검사(`scripts/check_public_safety.py`)
  - git 기록 전체 검사(`scripts/check_history_safety.py`). 로컬 키 값 대조는 키 파일이 있는 작성자 컴퓨터에서만 하고, CI에서는 패턴 검사만 한다.
  - 두 검사 모두 찾은 값은 출력하지 않고 종류와 위치만 출력한다.
- 평가 실행마다 기록하는 것: 실제 요청, 원시 응답, 모델 digest, 프롬프트·도구·정답 해시, 기준 날짜. CLI `ask`는 요청 기록을 남기지 않는다.
