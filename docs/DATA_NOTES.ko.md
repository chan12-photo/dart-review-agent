# 데이터 확인 기록: 개발용 캐시 72건 (2026-10-07)

- 갱신: 2026-10-07, Codex 독립 검토([reviews/1-3_codex_result.ko.md](reviews/1-3_codex_result.ko.md)) 반영. 반영 내역은 [reviews/1-3_codex_response.ko.md](reviews/1-3_codex_response.ko.md)

재무 도메인 규칙(로드맵 1-2)을 만들기 전에, 칸의 의미를 추측하지 않고 실제 응답으로 확인한 기록이다. 규칙 코드는 [`dart_review/periods.py`](../dart_review/periods.py), [`accounts.py`](../dart_review/accounts.py), [`compare.py`](../dart_review/compare.py), [`review.py`](../dart_review/review.py)에 있다.

- 범위: 개발용 3곳(삼성전자, 카카오, 셀트리온) × 2023~2025 × 4개 보고서(1분기, 반기, 3분기, 사업) × 연결·별도 = 72건
- 방법: 저장된 응답만 사용 (네트워크 0회, 인증키 없이 실행)
- 대상 계정 6개: 매출액, 영업이익, 당기순이익, 영업활동현금흐름, 자산총계, 부채총계

| 확인 내용 | 결과 |

- 현금 확인의 불일치 1건: 카카오 2023 반기 연결 (기초 현금 4,835,909,162,298, 재무상태표 전년 말 현금 4,780,244,024,656). 원인은 확인하지 않았다. 카카오 연결 3건(2023 3분기, 2024 반기, 2024 3분기)은 재무상태표에 표준 현금 ID가 없어 이 확인에서 빠졌다.
- 기초 현금의 일치와 연도 간 칸의 일치는 누적 해석을 뒷받침하지만, 현금흐름표의 모든 행의 기간 의미를 증명한 것은 아니다.
- 처음 기록은 현금흐름 전기 칸을 3분기 보고서만 세어 "12/12"로 적었다. Codex 검토가 분모를 지적했고, 1분기·반기까지 넣어 36/36으로 다시 확인했다.
- 손익 누적 관계(108건)와 분기 재무상태표 전기(72건)는 `tests/test_rules_on_cache.py`가 매번 다시 확인한다.

## 3. 계정 찾기

- 6개 계정 × 72건 = 432건 중 **표준계정ID로 426건, 계정명으로 6건**을 찾았다.
- 계정명으로 찾은 6건: 카카오 2023년 1분기·반기·3분기 보고서의 매출(연결·별도). 이 보고서들은 "영업수익"을 `ifrs-full_Revenue`가 아니라 **`ifrs-full_GrossProfit`으로 표기**했다. ID만 쓰면 매출을 못 찾고, 매출총이익을 찾는 질문에는 매출을 잘못 돌려줄 수 있다. 제출자가 왜 그렇게 표기했는지는 확인하지 않았다.
- **이름과 다른 표준ID가 충돌하는 행의 처리 (Codex 검토 R4 반영):** 계정명이 같아도 행에 다른 표준ID가 붙어 있으면 같은 계정이라고 단정하지 않는다. 예를 들어 "당기순이익"이라는 이름에 `ifrs-full_ProfitLossAttributableToOwnersOfParent`(지배기업 소유주 귀속)가 붙어 있으면 범위가 다른 숫자다. 이런 행은 값은 보여 주되 `확인 필요`로 답한다.
  - 예외는 근거를 확인한 경우만 목록(`VERIFIED_MISTAGS`)으로 관리한다. 지금은 카카오 1건이다. 근거: 카카오의 캐시 응답 24건 중 18건은 같은 "영업수익" 행을 `ifrs-full_Revenue`로 표기했고, `ifrs-full_GrossProfit` 표기는 2023년 1분기·반기·3분기(연결·별도) 6건뿐이다. 카카오의 손익 표에는 다른 매출 성격의 행이 없다.
- 카카오는 손익계산서(IS)가 없고, 매출과 영업이익이 포괄손익계산서(CIS)에 있다. 그래서 IS를 먼저 보고 없으면 CIS를 본다.
- 당기순이익(`ifrs-full_ProfitLoss`)은 IS·CIS 외에 현금흐름표(간접법 시작 행)와 자본변동표(구성요소별 여러 행)에도 나온다. 대상 재무제표만 보고, `account_detail`이 "-"인 합계 행만 쓴다.
- 같은 재무제표에 같은 ID가 두 번 나온 경우: 0건. (규칙상 두 개 이상이면 자동으로 고르지 않고 `확인 필요`)
- 실제 계정명 변형:
  - 매출: 매출액, 영업수익, 수익(매출액)
  - 영업이익: 영업이익, 영업이익(손실)
  - 순이익: 당기순이익, 당기순이익(손실), 반기순이익, 분기순이익, 분기순이익(손실)
  - 영업활동현금흐름: 영업활동현금흐름, 영업활동 현금흐름, 영업활동으로 인한 현금흐름
- 금액 형식: 정수 문자열 또는 빈 문자열만 나왔다. 통화는 모두 KRW. 다른 형식이 나오면 조용히 넘어가지 않고 오류로 멈춘다. 통화가 비어 있으면 같은 통화로 간주하지 않고 `확인 필요`로 답한다(Codex 검토 R5 반영).

## 4. 정정 공시와 전기 값 재작성

- 카카오 공시 목록(`list.json`, 2023-04-01~2025-04-30 정기공시, 요청 1회)과 캐시를 대조했다:
  - 캐시한 카카오 2023~2024년 보고서 8건 × 연결·별도 = 16개 응답의 접수번호가 모두 **그 조회 범위 안의 마지막 `[기재정정]` 접수번호**와 같았다. 예: 2023년 3분기는 원본(20231114002666)과 정정 2건이 있고, 캐시는 마지막 정정본(20231226000387)이다.
  - 같은 날(2024-03-20) 카카오는 2020~2022년 사업보고서도 정정했다.
  - 이것은 한 회사, 한 조회 범위의 관찰이다. 모든 회사에 대해 API가 항상 최신 정정본을 돌려준다는 일반 동작이나, 2025-04-30 이후 더 늦은 정정이 없었다는 것은 확인하지 않았다(Codex 검토 R7 반영).
  - 삼성전자·셀트리온 2024년 1분기의 접수일(5월 16일)은 5월 15일이 공휴일이었던 영향으로 보인다(목록으로 확인하지는 않았다).
- 따라서 캐시는 "받은 시점에 API가 돌려준 판"이다. 그 뒤의 정정은 반영되지 않는다(SCOPE 8절).
- **같은 기간의 값이 보고서마다 다르다 (재작성).**

- 카카오 2023년 3분기는 영업이익·순이익과 별도 기준도 다르다(2024년 연간 순이익은 같다). 셀트리온은 부채총계와 별도 기준도 다르다.
- **확인한 것은 "같은 기간의 숫자가 보고서마다 다르다"는 사실뿐이다.** 오류 수정, 분류 변경, 중단영업, 합병 같은 회계적 원인은 확인하지 않았다(공시 원문 확인 필요, 4단계 범위). 표의 "앞 보고서" 값도 최초 공시가 아니라 캐시한 판이다. 예를 들어 카카오 2024 사업보고서는 정정본이고, 최초본(20250318001297)의 금액은 확인하지 않았다.
- 영향: 카카오 2024년 3분기 3개월 매출의 전년 대비 증감률은 같은 보고서의 재작성 값으로 **-4.48%**, 2023년 보고서의 원래 값으로 **-11.08%**다. 2025년 연간 영업이익 증가율은 **+47.80%**와 **+59.07%**다.

## 5. 규칙에 반영한 결정

1. **기간은 칸 이름이 아니라 명시적 표로 정한다.** (1절의 표가 곧 `column_periods`)
2. **기준 값은 비교 기간 보고서의 비교 칸에서 읽는다.** 같은 보고서의 당기·전기는 같은 기준으로 작성되기 때문이다. 원래 보고서의 값이 다르면 메모로 남긴다.
3. **두 보고서가 필요한 비교**(예: 분기말 재무상태표의 전년 같은 분기말)는 두 보고서와 그 사이 사업보고서에 함께 나오는 값을 대조한다. 같은 해 손익 분기끼리는 "누적 − 3개월"로 앞 분기의 누적을 구해 앞 보고서와 대조한다(기준 확인용으로만 쓰고 답으로는 쓰지 않는다). (Codex 검토 R1 반영)
   - 함께 나오는 값이 모두 같고 두 보고서가 그 값들로 이어지면 `비교 가능`이다. 이것은 재작성이 없다는 증명이 아니라, 관찰한 범위에서 불일치가 없다는 뜻이다.
   - 값이 다르면 `확인 필요`. 이유에는 관찰한 차이만 적고, 이번 비교 기간이 실제로 바뀌었다고 단정하지 않는다. (예: 셀트리온 2025-09-30과 2024-09-30 비교)
   - 필요한 사업보고서가 없거나(캐시 없음, 013), 그 보고서에서 계정을 쓸 수 없거나, 이어지는 값이 하나도 없으면 `확인 필요`. 확인하지 못한 것을 `비교 가능`으로 올리지 않는다.
4. **직접 제공되지 않는 기간은 계산해서 만들지 않는다.** 반기·3분기의 현금흐름 단독 분기 값, 4분기 3개월 손익은 `비교 불가`와 이유를 돌려준다. 차감으로 계산할 수는 있지만 지금 제품이 지원하지 않는 범위다.
5. **기준 값이 0 이하이거나 부호가 바뀌면 변화율을 계산하지 않는다.** 영업이익·순이익은 흑자 전환, 적자 전환, 적자 축소·확대로 표시한다.
6. **연결과 별도는 비교하지 않는다.** 나란히 보여 주는 것은 출력 단계(2-3)에서 한다.

## 6. 관찰 (규칙이 아니라 해석의 문제)

- 셀트리온 2024-09-30 자산총계는 2023-09-30의 3.1배(+209.79%)다. 2023년 말 합병 영향으로 보인다. 회계 기준이 바뀐 것이 아니므로 규칙상 `비교 가능`이다. 이런 변화의 해석은 사람과 설명 단계의 몫이고, 개발용 질문 세트(1-3)의 후보로 쓴다.
- 재작성 확인의 한계: 비교에 쓴 두 보고서와 그 사이 사업보고서만 본다. 그 밖의 보고서에서 생긴 정정이나, 함께 나오지 않는 값의 변경은 볼 수 없다.
- 회계연도가 12월에 끝난다고 가정한다. 범위의 7개 회사는 모두 12월 결산이다.

## 7. 함정 테스트가 실제로 실수를 잡는지 확인

`python scripts/check_trap_tests.py`는 규칙 하나를 순진한 버전으로 바꾼 뒤 규칙 테스트(합성 + 캐시)를 다시 돌려, 그 함정의 테스트가 실패하는지 확인한다.

| 순진한 규칙 | 지정한 테스트 |
|---|---|
| 연결·별도 구분 무시 | 연결·별도 함정 |
| 손익 "당기"를 누적으로 읽음 | 3개월·누적 함정 |
| 현금흐름 "당기"를 3개월로 읽음 | 현금흐름 누적 함정 |
| 재무상태표 "전기"를 전년 같은 분기말로 읽음 | 재무상태표 전기 함정 |
| 표준계정ID만 사용 | 계정ID 오표기 함정 |
| 전기 값을 그 기간의 원래 보고서에서 읽음 | 보고서 안 재작성 함정 |
| 재작성 확인 생략 | 보고서 사이 재작성 함정 |
| 합계 행 필터 제거 (Codex R3) | 같은 재무제표 안의 분해 행 |
| 다른 표준ID의 이름 일치를 그대로 인정 (Codex R4) | 이름·ID 충돌은 확인 필요 |

- 처음 실행에서는 "연결·별도 구분 무시"를 **놓쳤다.** 테스트가 같은 연도끼리 비교해서, 연결·별도 규칙이 아니라 "기준 기간이 앞서야 한다" 규칙 때문에 `비교 불가`가 나오고 있었다. 테스트를 연도가 다른 비교로 고치고, 이유 문구까지 확인하게 바꿨다.
- 아래 세 줄은 Codex 검토가 찾은 빈틈이다. 합계 행 필터를 없애도 기존 테스트 68개가 모두 통과했고, 이름·ID 충돌과 확인하지 못한 보고서 사이도 막는 테스트가 없었다. 변이 검사를 통과했다고 해서 모든 중요한 규칙이 검사된 것은 아니다.
