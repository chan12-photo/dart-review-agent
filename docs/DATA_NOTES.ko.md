# 데이터 확인 기록: 개발용 캐시 72건 (2026-10-07)

재무 도메인 규칙(로드맵 1-2)을 만들기 전에, 칸의 의미를 추측하지 않고 실제 응답으로 확인한 기록이다. 규칙 코드는 [`dart_review/periods.py`](../dart_review/periods.py), [`accounts.py`](../dart_review/accounts.py), [`compare.py`](../dart_review/compare.py), [`review.py`](../dart_review/review.py)에 있다.

- 범위: 개발용 3곳(삼성전자, 카카오, 셀트리온) × 2023~2025 × 4개 보고서(1분기, 반기, 3분기, 사업) × 연결·별도 = 72건
- 방법: 저장된 응답만 사용 (네트워크 0회, 인증키 없이 실행)
- 대상 계정 6개: 매출액, 영업이익, 당기순이익, 영업활동현금흐름, 자산총계, 부채총계

## 1. 보고서와 재무제표별 칸

| 보고서 | 재무제표 | 칸 | 의미 |
|---|---|---|---|
| 1분기·반기·3분기 | 손익계산서(IS), 포괄손익계산서(CIS) | `thstrm` / `thstrm_add` | 그 분기 3개월 / 연초부터 누적 |
| | | `frmtrm_q` / `frmtrm_add` | 전년 같은 분기 3개월 / 전년 같은 시점까지 누적 |
| | 현금흐름표(CF) | `thstrm` / `frmtrm_q` | **둘 다 연초부터 누적** (3개월 값 없음) |
| | 재무상태표(BS) | `thstrm` / `frmtrm` | 분기말 시점 / **전년 말** 시점 (전년 같은 분기말이 아님) |
| 사업보고서 | IS, CIS, CF | `thstrm` / `frmtrm` / `bfefrmtrm` | 당해 연도 / 전년 / 전전년 (`thstrm_add`는 비어 있거나 `thstrm`과 같음) |
| | BS | `thstrm` / `frmtrm` / `bfefrmtrm` | 당해 말 / 전년 말 / 전전년 말 |

- 현금 확인의 불일치 1건: 카카오 2023 반기 연결 (기초 현금 4,835,909,162,298, 재무상태표 전년 말 현금 4,780,244,024,656). 원인은 확인하지 않았다. 카카오 보고서 3건은 재무상태표 현금 행의 ID가 달라 이 확인에서 빠졌다.
- 손익 누적 관계(108건)와 분기 재무상태표 전기(72건)는 `tests/test_rules_on_cache.py`가 매번 다시 확인한다.

## 3. 계정 찾기

- 6개 계정 × 72건 = 432건 중 **표준계정ID로 426건, 계정명으로 6건**을 찾았다.
- 계정명으로 찾은 6건: 카카오 2023년 1분기·반기·3분기 보고서의 매출(연결·별도). 이 보고서들은 "영업수익"을 `ifrs-full_Revenue`가 아니라 **`ifrs-full_GrossProfit`으로 표기**했다. ID만 쓰면 매출을 못 찾고, 매출총이익을 찾는 질문에는 매출을 잘못 돌려줄 수 있다.
- 카카오는 손익계산서(IS)가 없고, 매출과 영업이익이 포괄손익계산서(CIS)에 있다. 그래서 IS를 먼저 보고 없으면 CIS를 본다.
- 당기순이익(`ifrs-full_ProfitLoss`)은 IS·CIS 외에 현금흐름표(간접법 시작 행)와 자본변동표(구성요소별 여러 행)에도 나온다. 대상 재무제표만 보고, `account_detail`이 "-"인 합계 행만 쓴다.
- 같은 재무제표에 같은 ID가 두 번 나온 경우: 0건. (규칙상 두 개 이상이면 자동으로 고르지 않고 `확인 필요`)
- 실제 계정명 변형:
  - 매출: 매출액, 영업수익, 수익(매출액)
  - 영업이익: 영업이익, 영업이익(손실)
  - 순이익: 당기순이익, 당기순이익(손실), 반기순이익, 분기순이익, 분기순이익(손실)
  - 영업활동현금흐름: 영업활동현금흐름, 영업활동 현금흐름, 영업활동으로 인한 현금흐름
- 금액 형식: 정수 문자열 또는 빈 문자열만 나왔다. 통화는 모두 KRW. 다른 형식이 나오면 조용히 넘어가지 않고 오류로 멈춘다.

## 4. 정정 공시와 전기 값 재작성

- 정정 공시가 있으면 재무제표 API는 **가장 마지막 정정본**을 돌려준다. 카카오 공시 목록(`list.json`, 2023-04~2025-04 정기공시, 요청 1회)으로 확인했다:
  - 캐시한 카카오 보고서 중 2023년 1분기~2024년 사업보고서 8건은 모두 마지막 `[기재정정]` 접수번호였다. 예: 2023년 3분기는 원본(20231114002666)과 정정 2건이 있고, API는 마지막 정정본(20231226000387)을 돌려줬다.
  - 같은 날(2024-03-20) 카카오는 2020~2022년 사업보고서도 정정했다.
  - 삼성전자·셀트리온 2024년 1분기의 접수일(5월 16일)은 정정이 아니라 5월 15일이 공휴일이었던 영향으로 보인다(목록으로 확인하지는 않았다).
- 따라서 캐시는 "받은 시점의 최신 정정본"이다. 그 뒤의 정정은 반영되지 않는다(SCOPE 8절).
- **같은 기간의 값이 보고서마다 다르다 (재작성).**

| 회사 | 값 | 처음 보고서 | 나중 보고서 | 차이 |
|---|---|---:|---:|---:|
| 카카오 | 2023년 3분기 3개월 매출 (연결) | 2,160,931,354,165 (2023 3분기) | 2,011,471,714,310 (2024 3분기) | -6.92% |
| 카카오 | 2024년 연간 영업이익 (연결) | 460,212,161,525 (2024 사업) | 495,277,757,353 (2025 사업) | +7.62% |
| 카카오 | 2024년 연간 매출 (연결) | 7,871,692,199,887 | 7,864,033,326,475 | -0.10% |
| 셀트리온 | 2023년 말 자산총계 (연결) | 19,917,534,297,169 (2023 사업) | 19,956,813,831,274 (2024 사업) | +0.20% |

- 카카오 2023년 3분기는 영업이익·순이익과 별도 기준도 다르다(2024년 연간 순이익은 같다). 셀트리온은 부채총계와 별도 기준도 다르다. **재작성 원인은 확인하지 않았다** (공시 원문 확인 필요, 4단계 범위).

## 5. 규칙에 반영한 결정

1. **기간은 칸 이름이 아니라 명시적 표로 정한다.** (1절의 표가 곧 `column_periods`)
2. **기준 값은 비교 기간 보고서의 비교 칸에서 읽는다.** 같은 보고서의 당기·전기는 같은 기준으로 작성되기 때문이다. 원래 보고서의 값이 다르면 메모로 남긴다.
3. **두 보고서가 필요한 비교**(예: 분기말 재무상태표의 전년 같은 분기말)는 두 보고서와 그 사이 사업보고서에 겹쳐 나오는 기간을 대조한다. 두 보고서 사이에 재작성이 있었으면 `확인 필요`로 표시하고 이유를 적는다. (예: 셀트리온 2025-09-30과 2024-09-30 자산총계 비교)
4. **직접 제공되지 않는 기간은 계산해서 만들지 않는다.** 현금흐름표 3개월 값, 4분기 3개월 값은 `비교 불가`와 이유를 돌려준다.
5. **기준 값이 0 이하이거나 부호가 바뀌면 변화율을 계산하지 않는다.** 영업이익·순이익은 흑자 전환, 적자 전환, 적자 축소·확대로 표시한다.
6. **연결과 별도는 비교하지 않는다.** 나란히 보여 주는 것은 출력 단계(2-3)에서 한다.

## 6. 관찰 (규칙이 아니라 해석의 문제)

- 셀트리온 2024-09-30 자산총계는 2023-09-30의 3.1배(+209.79%)다. 2023년 말 합병 영향으로 보인다. 회계 기준이 바뀐 것이 아니므로 규칙상 `비교 가능`이다. 이런 변화의 해석은 사람과 설명 단계의 몫이고, 개발용 질문 세트(1-3)의 후보로 쓴다.
- 재작성 확인의 한계: 겹치는 기간이 하나도 없는 두 보고서(예: 같은 해 2분기와 3분기의 3개월 손익)는 재작성 여부를 확인하지 못하고 "서로 다른 보고서" 메모만 남긴다.
- 회계연도가 12월에 끝난다고 가정한다. 범위의 7개 회사는 모두 12월 결산이다.

## 7. 함정 테스트가 실제로 실수를 잡는지 확인

`python scripts/check_trap_tests.py`는 규칙 하나를 순진한 버전으로 바꾼 뒤 캐시 테스트를 다시 돌려, 그 함정의 테스트가 실패하는지 확인한다.

| 순진한 규칙 | 잡은 테스트 |
|---|---|
| 연결·별도 구분 무시 | 연결·별도 함정 |
| 손익 "당기"를 누적으로 읽음 | 3개월·누적 함정 외 3개 |
| 현금흐름 "당기"를 3개월로 읽음 | 현금흐름 누적 함정 |
| 재무상태표 "전기"를 전년 같은 분기말로 읽음 | 재무상태표 전기 함정 외 2개 |
| 표준계정ID만 사용 | 계정ID 오표기 함정 외 3개 |
| 전기 값을 그 기간의 원래 보고서에서 읽음 | 보고서 안 재작성 함정 |
| 재작성 확인 생략 | 보고서 사이 재작성 함정 외 1개 |

- 결과: 7개 모두 잡힘. 원래 규칙에서는 캐시 테스트 11개 모두 통과.
- 처음 실행에서는 "연결·별도 구분 무시"를 **놓쳤다.** 테스트가 같은 연도끼리 비교해서, 연결·별도 규칙이 아니라 "기준 기간이 앞서야 한다" 규칙 때문에 `비교 불가`가 나오고 있었다. 테스트를 연도가 다른 비교로 고치고, 이유 문구까지 확인하게 바꿨다.
