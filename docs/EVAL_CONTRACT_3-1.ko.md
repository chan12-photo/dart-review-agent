- ⑤ 이후 제품을 고치면 그 버전은 이 평가의 대상이 아니다. 고친 내용과 이유는 따로 기록하고, 이 평가 점수에는 섞지 않는다.
- ⑤에서 정답과 제품 규칙이 다르면 빌드를 멈추지 않는다(개발 세트와 다른 점이다). 판정 절차는 4.5절을 따른다. 정답이 틀렸으면 정답을 고치고, 제품이 틀렸으면 그대로 두고 실패로 잰다. 판정 내역은 모두 남긴다.
- **코드와 파일의 경계 (Codex 1차 1):** 봉인 질문은 `run_eval --questions <파일>`로 읽는다. 질문 파일 안의 `"gold"` 항목이 정답 파일을 가리킨다. ② 뒤에는 코드를 바꾸지 않고 질문·정답 파일만 추가한다. 실행 기록에는 제품 코드 커밋(P)과 두 파일의 해시(`set_questions`, `set_gold`)가 따로 남는다.
- **깨끗한 실행 (Codex 1차 11):** 실행 결과 폴더를 저장소 안에 만들면 다음 실행 전 작업 트리가 더러워진다. 그래서 실행마다 결과를 커밋한 뒤 다음 실행을 시작한다. 판정기는 깨끗하지 않은 실행을 판정 보류로 처리한다.

## 2. 대상

- **회사:** 봉인 4곳 — NAVER(00266961), CJ제일제당(00635134), 이마트(00872984), LG에너지솔루션(01515323).
  - 회사 선정 때 이 회사들의 2025년 사업보고서·3분기 보고서의 계정 행 수와 계정 이름을 봤다. 금액은 보지 않았다(SCOPE 11절). 그래서 이 데이터는 "아무것도 보지 않은 데이터"가 아니라 "**금액을 보지 않은 데이터**"다.
- **계정:** 지원 계정 6개 그대로다.
- **기간:** 2014년 이후 OpenDART가 제공하는 기간. 기준 날짜는 ④의 수집일로 고정하고 사전 등록에 적는다.
- **질문:** 4절.
- 이 평가가 말할 수 있는 것은 "**이 4곳과 이 질문들**"까지다. 업종 일반화나 다른 회사 일반화는 주장하지 않는다.

## 3. 비교하는 방식 (같은 질문, 같은 도구·렌더러·출력 계약)

| 방식 | 해석 | 답하는 조건 |
|---|---|---|
| 규칙만 (`baseline`) | 키워드 규칙 | 규칙이 읽으면 답한다 |
| 모델만 (`model_only`, 신규) | 같은 해석 프롬프트(reading-v4)의 해석 JSON 1회 | 모델 해석이 쓸 수 있으면 답한다. 그 앞에 "이렇게 이해했습니다"를 붙인다 |
| 교차 확인 (`crosscheck`, 제품) | 둘 다 | EVAL_DESIGN 11.1·12절 정책 |

- 모델만 방식은 교차 확인 실행의 모델 응답을 **다시 쓰지 않고** 따로 실행한다. 같은 질문에 대한 모델 응답이 두 실행에서 다를 수 있으므로, 두 기록을 모두 보고한다.
- 2-1 에이전트 결과는 비교에 쓰지 않는다. 도구 계획, 결정, 설명 생성이 섞여 있어 원인을 나눌 수 없다.

- 작성자를 질문마다 기록하고, 결과를 작성자별로도 나눠 보고한다.

### 4.2 질문 계약 (지원·되묻기·거절)

| 표현 | 계약 |
|---|---|
| "올해/작년/지난해/재작년" | 기준 날짜(④ 수집일)로 정한다 |
| 연도 없음 | 가장 최근 사업보고서 연도(기준 날짜가 4월 1일 이후면 전년) |
| "직전 분기" | 바로 앞 분기. 1분기의 직전 분기는 전년 4분기 3개월이고, 사업보고서가 제공하지 않으므로 비교 불가다 |
| 기준 날짜에 아직 제출되지 않은 보고서 | 데이터 없음(013) 또는 수집 시점에 없음. 정답도 그렇게 쓴다 |
| 약칭 | 고정 별칭표(4.4)에 있으면 지원한다. 없으면 회사를 찾지 못한 것으로 본다(무응답) |
| 그룹 이름(CJ, LG, 삼성) | 지원 회사가 하나뿐이어도 되묻는다 |
| 오타 | 지원하지 않는다. **평가에서 뺀다.** 질문에 오타가 있으면 그 질문만 탐색으로 따로 보고한다 |
| 한 회사·한 계정의 조건 여러 개(기준, 기간 종류) | 지원한다 |
| 회사 여러 개, 계정 여러 개, "전부" | 범위 밖 거절 |
| 모호한 질문 | 정답 작성자가 나중에 한쪽으로 정해 채점하지 않는다. 작성 단계에서 "되묻기가 정답"으로 표시한 것만 모호한 질문으로 센다 |

### 4.3 사용자 질문을 블라인드로 받는 방법

1. 사용자가 저장소 **밖**에 파일 두 개를 쓴다(Codex 1차 9: 기대 결정이 정답 작성자에게 먼저 보이지 않게 나눈다).
   - **질문 파일**(예: `~/Documents/dart_3-1_questions.txt`): 한 줄에 질문 하나, 앞에 번호를 붙인다(`U01 네이버 매출좀 알려줘`). 다른 표시는 붙이지 않는다.
   - **기대 결정 파일**(예: `~/Documents/dart_3-1_expected.txt`): 같은 번호마다 기대하는 결과를 한 단어로 적는다: 답, 거절, 되묻기.
2. 사용자가 두 파일의 SHA-256을 계산해(`shasum -a 256 <파일>`) 채팅에 해시만 알려 준다. Claude는 두 해시를 ③에서 커밋한다.
3. ②의 제품 고정 뒤, ⑤에서 사용자가 **질문 파일만** 먼저 넘긴다. Claude는 해시를 확인하고, 질문과 원본 데이터만 보고 정답(기대 결정 포함)을 쓴 뒤 커밋한다.
4. 그다음 사용자가 기대 결정 파일을 넘긴다. Claude의 기대 결정과 다른 문항은 목록으로 만들고, 질문을 쓴 **사용자가** 정한다. 바뀐 문항과 이유는 따로 기록한다.
4. 사용자에게는 이 문서 2·4.2절(제품 범위와 질문 계약)만 보여 준다. 구현 규칙과 실패 사례는 보여 주지 않는다(Codex A3).

### 4.5 정답 판정·수정·제외 규칙 (Codex 1차 9)

- **⑤에서 정답과 제품 규칙이 다를 때:**
  - Claude가 원본 칸을 다시 읽고(독립 정답 생성기), 어느 쪽이 맞는지 근거와 함께 적는다.
  - 사용자가 각 판정을 승인한다.
  - 판정 목록은 ⑥ 사전 등록 커밋에 포함한다. 모든 판정은 **모델을 한 번도 실행하기 전에** 끝낸다.
- **⑥ 뒤 정답 수정:** 원본 근거나 계산의 오류가 발견된 경우에만 고친다.
  - 제품 출력과 점수를 보지 않은 상태에서 원본을 다시 확인해 판단한다.
  - 사용자 승인을 받고, 이유와 고치기 전후 점수를 모두 보고한다.
  - 점수가 나쁘다는 이유로는 고치지 않는다.
- **문항 제외:** 미리 정한 두 경우에만 뺀다.
  - 오타 질문(4.2)
  - 질문이 수집 범위(5절) 밖의 데이터를 요구하는데, 추가 수집도 할 수 없는 경우
  
  제외는 모델 실행 전에 정하고 이유를 기록한다. 실행 뒤에는 어떤 문항도 빼지 않는다.
- **작성자 편향 기록:** Claude 몫 22문항은 제품 설계와 v3·v4의 실패를 아는 사람이 쓴다. 결과는 작성자별, 묶음별로 ID와 개수를 함께 보고한다.

## 5. 데이터 수집 (④, 사용자 승인 필요)

- 범위: 봉인 4곳 × 2014년 사업보고서 + 2022년부터 기준 날짜까지 제출된 모든 정기보고서(1분기, 반기, 3분기, 사업) × 연결·별도. 질문에 필요한 보고서가 이 범위 밖이면 추가로 받고 기록한다.
- 받은 응답은 지금처럼 `cache/`에 둔다(git 제외). 받은 시각과 SHA-256을 남긴다. 평가는 오프라인 캐시로만 돌린다.
- 받는 스크립트는 기존 수집 스크립트와 분리한다. 봉인 차단을 푸는 것은 평가 모드에서만 한다(7절).

## 6. 정답

- 1-3 방식을 그대로 쓴다. 질문마다 근거 칸(보고서, 칸, 재무제표, 계정ID)을 사람이 지정하고, 원본에서 독립 계산한다(`build_gold.py`, `build_lookup_gold.py`의 독립 부분 재사용).
- 정답에는 다음을 적는다:
  - 기대 상태
  - 기대 결정(answer / side_by_side / refuse / clarify)
  - 기대 해석(정규화 키): 해석 기여 표에 쓴다
  - 근거 칸
- 정답과 제품 규칙의 불일치는 1절 마지막 항목대로 처리한다.

## 7. 실행 전에 필요한 코드 (①에서 구현, Codex 1차 검토 대상)

1. **평가 모드 (A4):**
   - 회사 집합(이름, 별칭, 그룹)을 설정 파일로 주입한다. 기본값은 개발 3곳이다. 평가 모드에서는 봉인 4곳이 지원 회사가 되고, 개발 3곳은 범위 밖이 된다.
   - 봉인 차단(`ensure_not_sealed`)은 평가 모드에서만 풀린다.
   - **설정 변경**으로 세는 것: 회사 집합 주입, 회사명 사전 재생성, 캐시 수집.
   - **코드 수정**으로 세는 것: 그 밖의 모든 것. 계정 이름·ID 추가, 오표기 예외, 규칙·기간·프롬프트 변경이 여기에 든다. 평가 실행 전에 코드 수정이 필요해지면, 그 목록이 곧 "회사 확장성" 결과다.
2. **모델만 방식**(`--mode model_only`).
3. **결과 분류기:** 질문마다 아래 4개 표의 칸을 자동으로 정하고, 사람 검토로 확정한다.
4. **진행 판정기 (B10):** 고정 ID의 완전성, 중복, 평가기 오류, 수동 확인 상태, 근거 위반을 `threshold`와 따로 검사한다. 판정을 다시 확정하면 새 버전 파일로 남긴다.
5. **재채점 경로 통일:** 재채점은 실행기와 같은 채점 함수를 쓴다(Codex 3.1).
6. 비지원 계정 사전은 **개발 캐시로 만든 것을 그대로** 쓴다. 봉인 데이터로 다시 만들지 않는다. 그렇게 하면 봉인 데이터로 제품을 맞추는 일이 된다.

## 8. 측정표 (Codex A2, 네 개 모두 사전 등록)

| 측정 | 분류 |
|---|---|
| 해석 기여 | 규칙 정답/모델 정답, 규칙 오답/모델 정답, 규칙 정답/모델 오답, 둘 다 오답, 규칙 미해석, 모델 미해석(형식 실패, 출력 한도 포함) |
| 제품 결과 | 정답 제공, 맞는 거절, 맞는 되묻기, 불필요한 되묻기, 잘못된 되묻기, 보류·무응답, **잘못된 수치 답**, 잘못된 거절 |
| 교차 확인 효과 | 막은 오답(규칙만이나 모델만이면 틀렸을 것), 잃은 정답(한쪽만이면 맞았을 것), 일치한 오답, 한쪽 해석으로 낸 답 |
| 실용 비용 | 전체 대비 해결률, 답한 질문 중 오류율, 추가 확인(되묻기) 횟수, 모델 시간, 출력 한도 도달 |

- **잘못된 수치 답:** 답 상태(값 확인, 비교 가능, 확인 필요, 나란히 표시)를 보여 줬는데 값·기간·기준·회사·계정 중 하나라도 정답과 다른 경우. 되묻기가 정답인데 답한 경우도 여기에 든다.
- **잘못된 거절:** 답이 있는 질문에 범위 밖·비교 불가·조회 불가·데이터 없음으로 답한 경우. 거절이 정답이어도 거절 이유(상태)가 다르면 여기에 든다.
- **설명 실패 (Codex 2차 5):** 답 상태를 보여 줬고 자동 채점(값, 기간, 기준, 회사, 계정)은 통과했는데, 본문 검토에서 설명만 실패한 경우다. 이유를 빠뜨렸거나 근거 없는 원인을 단정한 경우가 해당한다. 검토자가 `failure_kind: "설명"`으로 적는다. 해결로 세지 않지만 **잘못된 수치 답에는 넣지 않는다.** 본문이 값·기간·기준·회사·계정을 틀리게 말하면 `failure_kind: "수치"`이고 잘못된 수치 답이다.
- **잘못된 되묻기:** 되묻기가 정답인데 후보를 잘못 물은 경우(구현 중 추가). 묶음 C 비율에서 맞는 처리로 세지 않는다.
- **보류·무응답:** 읽을 수 있는 답이 없는 경우다. 모델 실패로 보류, 해석 불가, 도구 오류, 출력 숫자 검사로 막힌 경우가 모두 여기에 든다.
- 해석 기여 표는 교차 확인 실행이 기록한 두 해석 키(`rule_key`, `model_key`)로 만든다. 모델만 실행의 모델 해석은 같은 질문이라도 다를 수 있으므로 따로 보고한다.
- 분모가 작은 칸(예: "규칙 오답/모델 정답" 2건)은 비율 대신 개수와 ID를 쓴다.

## 9. 판정 기준 (실행 전 고정)

| 기준 | 대상 | 값 (안) |
|---|---|---|
| **잘못된 수치 답** | 교차 확인 | **0** |
| 해결률 | 교차 확인, 답이 있는 질문 | 70% 이상 |
| 불필요한 되묻기 + 보류·무응답 + 잘못된 거절 | 교차 확인, 답이 있는 질문 | 25% 이하 |
| 범위 밖·모호 처리 | 교차 확인, 묶음 C | 맞는 거절·되묻기 75% 이상 |
| 근거 없는 숫자 | 모든 방식 | 0 |

- **실제 문턱 (Codex 1차 12, 2차 4에서 정정):**
  - 정답 기준으로 답이 있는 문항은 **23개**다(값 확인 11, 비교 가능 9, 확인 필요 1, 나란히 표시 2). 처음 적은 "26개"는 A의 거절 문항 3개(C04, C07, C12)를 빼지 않은 착오였다.
  - 잘못된 수치 답이 0이면 해결률 70%와 비용 25%를 함께 적용할 때 **최소 18/23(78.3%)** 이다. 17/23이면 비용이 6/23 = 26.1%라 넘지 못한다. 설명 실패가 있으면 그만큼 해결 수가 줄어든다.
  - 전부 거절하거나 전부 되묻는 전략은 해결률 때문에 통과하지 못한다.
- **판정기는 엄격 모드로 돌린다:** 세 방식 모두, 모든 방식의 사람 검토(사용자 확인 포함), 36문항 구성, 같은 모델 식별값, 기록된 해시와 현재 파일의 일치, 해석 키 기록이 갖춰지지 않으면 판정 보류다. 적용할 수 없는 기준도 보류다.
- **거절과 되묻기의 이유는 본문 검토로 확인한다 (Codex 1차 4):** 자동 채점은 상태만 본다. 그래서 회사가 원인인데 "계정이라서"라고 거절한 답도 자동으로는 통과한다. 사람 검토가 필수이므로 이런 답은 검토에서 실패한다([HUMAN_REVIEW](../eval/HUMAN_REVIEW.ko.md) 공통 4번).
- 0건이라는 관찰은 이 36문항에서 본 것이다. 다른 회사와 질문의 오류율을 증명하는 것처럼 쓰지 않는다.

### 9.1 사람 검토와 실행 운영 규칙 (Codex 2차 6, 실행 전 고정)

- **실행 순서:** baseline → crosscheck → model_only를 각 한 번씩 돌리고, 실행마다 결과를 커밋한다.
  - 같은 방식으로 같은 질문을 다시 돌리지 않는다.
  - 실행이 평가 장치 오류(예외, 수집 누락)로 중단되면 원인을 기록하고, 새 폴더에서 그 방식 전체를 다시 돌린다. 중단된 기록도 지우지 않고 보고한다.
  - 모델의 답이 마음에 들지 않는다는 이유로는 다시 돌리지 않는다.
  - 실행 중과 실행 뒤에 프롬프트·규칙·옵션을 조정하지 않는다.
- **검토자:** Claude가 1차로 판정하고, 사용자가 문항마다 확인한다. `confirmed_by_user`는 사용자가 확인한 뒤에만 true로 바꾼다.
- **검토 순서와 노출 정보:**
  - 방식마다 별도의 검토지(`review_sheet.md`)로 판정한다.
  - 검토자는 질문, 그 방식의 답, 정답 요약을 보고 판정한다.
  - 다른 방식의 판정과 판정기 결과는 세 방식의 판정을 모두 마친 뒤에 본다.
- **기록 형식:**
  - 문항마다 `body_ok`를 적고, false면 `failure_kind`를 "수치" 또는 "설명"으로 적고 `note`에 이유를 쓴다.
  - `finalize.py`가 만드는 `final.json`에는 방식(mode), 검토한 `cases.jsonl`·`run.json`·`human_review.json`의 SHA-256이 들어간다. 판정기는 방식과 cases 해시가 실행과 다르면 보류한다.
- **재검토:** 덮어쓰지 않는다. `human_review.json`에 `revision_reason`을 적으면 `final_v2.json`처럼 새 버전이 생기고 이전 버전은 남는다. 판정에 쓴 버전과 이유를 보고서에 적는다.
- **판정:** 세 방식의 확정 검토 파일을 `--final MODE=FILE`로 명시해 엄격 모드로 한 번 돌리고, 그 출력을 그대로 보고한다.
- 세 기준을 모두 넘으면, v0.1 README에 "봉인 평가에서 틀린 수치 답 0, 해결률 X%"라고 쓴다. 하나라도 못 넘으면 못 넘었다고 쓴다. 기준을 실행 뒤에 바꾸지 않는다.
- **LLM의 기여는 합격 기준이 아니다.** 해석 기여 표와 교차 확인 효과 표로 보고만 한다. "LLM이 기여했다"는 말은 사례가 있을 때만, 그 ID와 함께 쓴다. 모델이 규칙보다 못해도 평가 실패가 아니며, 질문 비중을 나중에 바꾸지 않는다.
- **판정 보류(자동):** `eval/judge.py`는 기준을 적용하기 전에 실행 기록부터 검사한다. 아래 중 하나라도 해당하면 기준을 적용하지 않고 "판정 보류"와 이유를 낸다(Codex B10).
  - 정답의 문항이 실행마다 정확히 한 번씩 있지 않다(누락·중복·남는 문항).
  - 평가기 오류가 있다.
  - 실행끼리 코드 커밋, 질문 세트, 회사 집합, 기준 날짜, 계약 해시가 다르다.
  - 깨끗하지 않은 작업 트리에서 실행했다.
- 평가 회사 집합(`--companies sealed-3-1`)으로 돌리는 실행은 모델을 쓰든 안 쓰든 커밋된 깨끗한 트리에서 `--out`으로 기록해야 한다. 실행기가 그렇지 않은 실행을 거부한다.
- 평가기 버그, 정답의 모호성, 데이터 누락이 발견되면 모델 성능 판정을 보류한다. 수정은 새 버전으로 기록한다. 봉인 질문을 개발 세트처럼 반복 조정하지 않는다.

## 11. 다음 단계의 대량 평가 (사용자 결정 A, 2026-10-08, 봉인 데이터 수집 전 커밋)

- **3-1 결과와 관계없이**, 3-1 보고 뒤 다음 단계에서 **대량 템플릿 평가**를 반드시 실시한다. 결과를 보고 할지 말지 정하지 않는다.
- **방법:** 같은 봉인 4곳 × 지원 계정 × 기간 × 정해진 표현 틀로 질문을 수백 개 자동 생성한다. 정답은 원본에서 코드로 계산한다.
- **목적:** 정형 표현에서 잘못된 수치 답의 오류율 상한을 좁힌다. 3-1에서 0건이 나와도 95% 신뢰 상한은 분모에 따라 다르다(Codex 2차 4에서 정정).
  - 실제로 수치 답을 낸 문항 수가 분모다. 23개 모두 답했고 0건이면 약 12%다(1 − 0.05^(1/23)).
  - 답한 문항이 더 적으면 상한은 더 커진다.
  - 거절·되묻기 문항은 수치 답의 안전성 표본으로 세지 않는다.
  - 처음 적은 "약 8%"는 36개 모두를 분모로 둔 잘못된 계산이었다.
- **하지 않는 것:**
  - 3-1의 36문항 점수를 바꾸거나 대신하지 않는다.
  - 사람이 쓴 질문에서 난 실패를 대량 평가의 성공으로 상쇄하지 않는다.
  - 질문 표현이 기계적이므로 "LLM이 필요한가"의 근거로 쓰지 않는다.
- 생성 틀, 문항 수, 판정 기준은 그 단계를 시작할 때 실행 전에 따로 정해 커밋한다.
