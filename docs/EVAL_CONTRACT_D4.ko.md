# D4 문서 → 엑셀 정확도 평가 계약 (초안 3판, 2026-10-10)

- 상태: **초안 3판. Codex 1차 검토(12건)와 재검토(11건)를 반영했다([1차 결과](reviews/D4_contract_codex_result.ko.md), [1차 응답](reviews/D4_contract_codex_response.ko.md), [재검토 결과](reviews/D4_recheck_codex_result.ko.md), [재검토 응답](reviews/D4_recheck_codex_response.ko.md)). Codex 3차 검토와 사용자 결정(10절) 전.** 평가 문서를 고르거나 내려받기 **전에** 확정한다.
- 대상 기능: v0.2 "문서 → 검증된 엑셀" (`python -m dart_review extract`, API `POST /jobs`).
- **목적:** 처음 보는 재무제표 PDF에서, 엑셀에 **표시 없이 들어간 틀린 숫자**, **표시 없이 틀린 계정명**, **표시 없이 빠진 숫자**가 몇 칸인지 잰다. 확인 필요 표시가 얼마나 많은지(사람이 확인할 양)와 합계 검산이 실제로 돈 비율도 같이 잰다.
- **이 평가로 하지 않는 것:**
  - 개발 중에 본 문서 6개(11절)의 결과를 평가 결과로 쓰지 않는다. 그 문서들로 고쳤기 때문이다.
  - "AI가 규칙보다 낫다"를 이 평가 하나로 주장하지 않는다. 두 방식의 결과는 나란히 보고만 한다.
  - 회사 10곳은 사례다. 결과를 일반적인 오류율의 정밀한 추정으로 쓰지 않는다. 칸들은 독립이 아니다(같은 문서, 같은 표 구조).
  - 자본변동표는 v0.2가 읽지 않는다(문제로만 표시). 평가 대상이 아니다. "읽지 않았다는 표시가 있는가"만 본다.

## 1. 순서

| 단계 | 하는 일 |
|---|---|
| ① 계약 | 이 문서를 확정한다. 모집단, 순서, 제외 절차, 정답 규칙, 채점, 기준을 문서를 고르기 전에 고정한다 |
| ② Codex 검토 (필수) | 1차(12건), 재검토(11건) 반영. 3판을 3차로 검토받는다 |
| ③ 사용자 결정 | 10절. 새 문서 내려받기와 OpenDART 조회는 사용자 승인 뒤에 한다 |
| ④ 고정 | **어떤 후보 문서도 열기 전에** 제품 커밋 P, 평가 도구 커밋 T(`eval/d4_gold.py`, `eval/d4_score.py`), 모집단 파일과 SHA-256, 순서 코드와 시드를 커밋 F로 고정한다 |
| ⑤ 후보 판정과 문서 준비 | 3.2의 절차로 순서대로 후보를 판정하고(포함, 또는 제외 이유와 근거) 기록한다. 포함된 10곳의 문서를 받고 SHA-256을 기록한다. 합성 스캔을 만든다(3.3) |
| ⑥ 정답 준비 | 정답 생성기를 돌리고, 사람이 매핑표의 모든 항목을 결정해 확정한다(4.2). 제품을 이 문서들에 돌리기 전에 끝낸다 |
| ⑦ 사전 등록 | 후보 판정 기록, 문서 해시, 정답, 확정된 매핑표, P와 T, 모델·OCR 버전을 커밋 R로 고정한다 |
| ⑧ 실행 | 사용자 승인 뒤 규칙 → AI 순서로 한 번씩. 실행 전에 `git diff P HEAD -- dart_review` 와 `git diff T HEAD -- eval/d4_gold.py eval/d4_score.py` 가 비어 있음을 확인하고 기록한다 |
| ⑨ 판정·보고 | 정답에 없는 칸의 사람 판정(4.5), 채점(`eval/d4_score.py`), 기준 판정. 실패를 포함해 그대로 보고한다 |

- ④ 뒤에는 제품과 평가 도구를 바꾸지 않는다. ⑤~⑨ 사이에 결함을 찾으면 고치지 않고 P로 잰 결과를 공식 결과로 한다. 고친 버전을 따로 재면 두 결과를 모두 보고하고, 고친 결과를 공식 결과로 부르지 않는다.
- ⑤에서는 제품을 후보 문서에 돌리지 않는다. 후보 판정은 PDF를 받을 수 있는지와 열리는지만 본다(재무제표 내용을 읽지 않는다).
- 정답을 ⑦ 뒤에 고쳐야 하면, 고친 이유와 전후를 기록하고 원래 정답과 고친 정답의 두 결과를 모두 보고한다.

## 2. 대상

- **제품:** ④에서 고정하는 커밋 P(후보 문서를 열기 전). 평가 도구는 커밋 T.
- **읽기 방식 두 가지:**
  - AI (`--reader ai`, 기본값): 로컬 비전 모델이 띠 단위로 읽는다. 텍스트 PDF는 숫자와 계정명을 PDF 글자의 같은 줄과 대조한다. 스캔·사진은 숫자를 OCR의 같은 줄에서 찾고, 계정명은 macOS Vision이 읽은 경우에만 대조한다.
  - 규칙 (`--reader rules`): 단어 위치와 규칙만. 참고로 같이 잰다.
- **모델:** Ollama, `qwen3-vl:8b`(Q4_K_M, digest는 ④에서 기록), 프롬프트 `band-v1`, 온도 0, num_ctx 16384, num_predict 2000, 빈 생각 블록 미리 채우기. 기계: Apple M5 Pro, 메모리 24GB.
- **OCR:** Tesseract 5.5.3(kor+eng), macOS Vision(시스템 버전). 버전은 ④에서 기록한다.

## 3. 평가 문서

세 묶음으로 나눠 따로 보고한다. 묶음끼리 합친 점수 하나로 판정하지 않는다.

### 3.1 텍스트 PDF (실제 감사보고서): 모집단과 순서
- **모집단:** OpenDART 회사 고유번호 목록(`corpCode.xml`)에서 종목코드가 있는 회사. 파일을 받은 날짜와 SHA-256을 ④에서 기록한다. (유가증권·코스닥 구분은 이 파일에 없다. 시장을 한정할지는 10절에서 정한다.)
- **순서:** 각 회사의 `sha256("D4-2026|" + 고유번호)`를 오름차순으로 정렬한 순서. 시드 문자열과 코드, 정렬된 전체 목록을 ④에서 커밋한다.
- 순서대로 포함된 회사가 10곳이 되면 멈춘다. 판정 기록에는 판정한 모든 후보가 들어간다.

### 3.2 후보 판정 절차 (순서대로, 후보마다 기록)
1. **개발·봉인 회사:** 삼성전자, NAVER, 한화시스템, 포스코, LG에너지솔루션, 카카오, 셀트리온, CJ제일제당, 이마트(고유번호를 ④에서 고정)면 제외.
2. **금융업:** OpenDART 기업개황(`company.json`)의 업종코드(`induty_code`)가 64·65·66으로 시작하면 제외. 응답과 받은 시각을 기록한다.
3. **2025 회계연도 사업보고서:** OpenDART 공시 목록(`list.json`, 정기공시, 2026-01-01~2026-06-30 접수)에서 "사업보고서 (2025.12)"를 찾는다. 정정 공시가 있으면 가장 늦게 접수된 것을 쓴다. 없으면 제외(사유: 사업보고서 없음).
4. **연결감사보고서 PDF:** 그 사업보고서의 첨부 가운데 연결감사보고서 PDF를 DART 웹에서 받는다(받는 방법은 10절). 연결감사보고서가 없으면 제외(사유: 연결재무제표 없음). 받기가 실패하면 다른 시각에 한 번 더 시도하고, 두 번 모두 실패하면 제외한다. 받은 파일이 열리지 않으면(PDF 글자 층 읽기 실패) 제외한다.
5. 기록: 고유번호, 회사명, 접수번호, 첨부 파일 이름, 시도 시각과 결과, 판정과 사유, 포함이면 SHA-256.
- 이 절차는 재무제표 내용을 보지 않는다. 결과를 보고 후보를 고를 틈을 줄이기 위한 것이다.

### 3.3 합성 스캔 (3.1 문서에서 만든 이미지 PDF)
- 3.1 문서의 재무제표 쪽(정답이 있는 쪽)을 쪽 전체 그대로 이미지로 바꾼다. 자르지 않는다. 조건: 200dpi 정상, 150dpi + 1도 기울기, 150dpi + 흐림(제안). 3조건 × 10문서.
- 만드는 코드와 시드를 ④의 T에 포함한다. 합성 쪽과 원본 쪽의 대응표를 남기고, 쪽 수가 같은지 확인한다.
- 정답은 3.1의 같은 쪽 정답을 쓴다(쪽 번호는 대응표로 바꾼다).

### 3.4 사진 PDF (선택, 사용자 결정)
- 사용자가 인쇄물이나 화면을 휴대폰으로 찍은 PDF. 개인정보가 없는 공시 문서만 쓴다. 찍는 조건은 사용자가 정하고 기록한다.
- 문서 수가 적으므로 사례 보고로만 쓴다. 정답은 원본 텍스트 PDF가 있으면 그 정답을, 없으면 OpenDART와 사람 검토로 정한다.

## 4. 정답

### 4.1 칸과 재무제표
- 재무제표마다 id(제목@시작 쪽)와 쪽 범위가 있다. 같은 제목이 다시 나오면 다른 재무제표다.
- (재무제표 id, 인쇄된 행, 기간) 하나가 칸 하나다. 기간은 당기와 전기 두 개다. 정답 값은 **인쇄된 그대로의 부호**를 원 단위로 바꾼 값이다(괄호는 음수). 인쇄본이 "-"인 칸은 "값 없음" 칸이다.
- 계정명 정답은 그 줄에 인쇄된 계정명이다(항목 번호와 주석 번호를 뺀 것).

### 4.2 정답 생성기와 매핑표 (제품 코드와 독립)
- 정답 생성기(`eval/d4_gold.py`)는 제품의 표 해석 코드(`dart_review/documents/`)를 쓰지 않는다. PDF 글자 층을 직접 읽어 인쇄된 칸을 만들고, OpenDART 값과 하나씩 짝지어 확인한다(같은 값이 두 행에 있으면 두 번 센다).
- 자동으로 정하지 못한 것은 매핑표 항목(id가 있다)으로 사람에게 넘긴다:
  - `not_in_dart`: 인쇄된 칸인데 OpenDART에 그 값이 없다 → 결정 `keep`(인쇄 그대로 정답) 또는 `drop`
  - `dart_only`: OpenDART 값인데 인쇄본에 없다 → `ignore`(OpenDART가 다르게 묶음) 또는 `add`(정답 칸 추가)
  - `uncertain_line`: 쪽 아래쪽의, 쉼표 있는 금액이 없는 줄(바닥글 또는 작은 금액 행). 제안된 칸과 함께 → `ignore` 또는 `add`
  - `slots`(한 줄에 금액이 셋 이상), `no_label`, `one_slot_no_boundary`, `no_unit` → `ignore` 또는 `add`(칸을 직접 적는다)
- 매핑표의 결정마다 근거(쪽, 인쇄된 글자)를 적는다. Claude가 1차로 쓰고 사용자가 확인한다. **모든 항목에 결정이 있어야 채점기가 정답을 받는다**(`apply_mapping`이 결정 없는 항목을 거부한다). 확정한 뒤에 바꾸면 변경 이력을 남긴다.
- 정답에 넣지 않는 것: 자본변동표, 주석.
- 구현과 시험: `eval/d4_gold.py`, `eval/d4_score.py`. 개발 문서 6개로만 시험했다. 두 도구 모두 이 문서들로 다듬었으므로 개발 문서에서의 일치는 정확성의 근거가 아니다.

### 4.3 칸마다의 채점 (⑨, `eval/d4_score.py`)

| 결과 | 뜻 |
|---|---|
| 맞음 | 같은 재무제표·행(계정명)·기간의 제품 칸이 정답 값과 같다. "값 없음" 칸은 제품에도 값이 없으면 맞음(칸 수에 넣지 않는다) |
| 값 틀림 | 같은 행·기간인데 값이 다르다(자릿수, 단위 10³·10⁶·10⁸, 부호, 다른 기간의 값 포함). "값 없음" 칸에 제품 값이 있으면 값 틀림 |
| 계정명 틀림 | 그 행·기간의 제품 칸은 없는데, 같은 기간의 다른 행 이름 아래에 정답 값이 있다(쓰이지 않은 칸만) |
| 빠짐 | 위 어디에도 없다 |

- 부호: 정답이 인쇄된 부호이므로 부호 차이는 값 틀림이다.
- 계정명 비교는 띄어쓰기·항목 번호("1.", "가.", "1)", "Ⅰ.")·주석 표기를 뺀 문자열로 한다. 오타는 다른 계정명이다(계정명 틀림).

### 4.4 빠진 칸과 "가리킴"
- **칸의 표시:** 엑셀에서 그 칸이 "확인 필요"면 표시된 것이다.
- **빠진 칸이 가리켜졌다:** 그 재무제표(또는 문서 전체)의 문제 문장이 다음 가운데 하나를 만족한다.
  1. 그 칸의 인쇄 금액과 그 행의 계정명을 함께 적었다("10쪽 '매출액' 줄: 원본의 금액 '47'…", "1쪽 '47' (기본주당이익)"). 쪽을 적었다면 쪽도 같아야 한다.
  2. 그 행의 계정명 바로 뒤에 기간("당기", "전기")을 적었다("유동자산 당기 칸을 읽지 못했다").
  3. 그 칸의 인쇄 금액만 적었는데, 그 금액이 그 재무제표의 정답 칸에서 **한 번만** 인쇄됐다. 같은 금액이 여러 행에 있으면 금액만 적은 문장은 어느 칸도 가리키지 않는다.
- "AI가 한 부분을 읽지 못했다"처럼 금액을 적지 않은 메시지는 어느 칸도 가리키지 않는다. 그런 메시지가 있는 재무제표의 가리켜지지 않은 빠진 칸은 G1로 따로 센다.

### 4.5 정답에 없는 칸
- 제품 칸 가운데 어느 정답 칸과도 짝지어지지 않은 칸(주석 표를 읽은 행, 인쇄되지 않은 값 등).
- **"확인 필요"가 아닌 것은 모두 사람이 판정한다:** `wrong`(엑셀에 틀린 값이 표시 없이 들어갔다) 또는 `ok`(인쇄본에 있는 값인데 정답 생성기가 놓친 것 등, 이 경우 정답 생성기 결함으로 따로 보고한다). 판정마다 근거를 적는다.
- 판정이 없는 표시 없는 칸이 하나라도 있으면 그 묶음의 결과는 **판정 불가**다(채점기의 `complete=false`).
- "확인 필요"인 칸은 목록으로만 보고한다.

## 5. 지표와 기준

| 지표 | 정의 | 기준 |
|---|---|---|
| **S1 표시 없이 틀린 값** | 값 틀림 칸 가운데 "확인 필요"가 아닌 칸 + 정답에 없는 칸 가운데 표시 없이 `wrong`으로 판정된 칸 | 3.1 **0**, 3.3 **0** |
| **L1 표시 없이 틀린 계정명** | 계정명 틀림 칸 가운데 "확인 필요"가 아닌 칸 | 3.1 **0**, 3.3 보고만 |
| **S2 가리켜지지 않은 빠진 칸** | 빠진 칸 가운데 4.4로 가리켜지지 않은 칸 | 3.1 **0**, 3.3 보고만 |
| G1 포괄 메시지로만 덮인 빠진 칸 | S2 가운데 "한 부분을 읽지 못했다"가 있는 재무제표의 칸 | 보고만 |
| A1 확인 필요 비율 | 표시된 칸 / 엑셀의 칸 | 보고만 |
| A2 덮은 비율 | 맞음 칸 / 정답 칸 | 보고만 |
| A3 시간 | 문서당 실행 시간, 모델 호출 수 | 보고만 |
| A4 합계 검산 | 재무제표마다 실제로 계산한 항등식·소계의 수(기간마다 하나, 값이 모두 있었던 것만: `sums_checked`), 층을 확인하지 못해 계산하지 않은 소계가 있다고 보고된 재무제표 수, 검산을 하나도 못 했다고 보고된 재무제표 수 | 보고만 |

- 공식 판정은 S1, L1, S2로 한다. 묶음(3.1, 3.3)마다, 읽기 방식마다 따로 판정한다. **제품 판정은 AI 방식이다.** 4.5의 판정이 끝나지 않았으면(판정 불가) 공식 판정을 내지 않는다.
- 기준을 충족해도 "틀린 숫자가 없다"고 일반화하지 않는다. 칸 수, 문서 수, 매핑표에서 사람이 정한 항목 수, 4.5에서 사람이 판정한 칸 수를 함께 적는다.

## 6. 사람 검토

- 대상: 매핑표(4.2, 실행 전), 정답에 없는 칸(4.5, 실행 뒤).
- Claude가 1차로 판정하고 근거(쪽, 인쇄된 글자)를 적는다. 사용자가 확인한다. 판정을 바꾸면 변경 이력을 남긴다. 제3의 독립 검토자는 없다(한계로 보고한다).
- 매핑표는 실행 결과를 보기 전에 확정한다. 실행 결과를 본 뒤 매핑표를 바꾸면 1절의 두 결과 보고를 따른다.

## 7. 실행과 장애

- 실행 명령은 ⑦에서 고정한다. 문서 목록은 평가 도구의 입력 파일로 뺀다. 같은 데이터 폴더를 두 서버가 쓰지 않는다(서버가 폴더를 잠근다).
- 모델 서버 장애(연결 실패 등, 출력 한도 초과가 아닌 오류)가 나면 그 방식 전체를 새 폴더에서 다시 돌리고 두 기록을 모두 남긴다.
- 출력 한도 초과(띠 하나를 못 읽음)는 장애가 아니라 제품 동작이다. 그대로 잰다.

## 8. 공개와 데이터

- 평가 문서 PDF는 커밋하지 않는다. 회사, 문서 이름, 접수번호, SHA-256, 쪽 수만 남긴다.
- 기록에는 공시된 숫자와 계정명만 남긴다. 사진 PDF는 사용자가 개인정보가 없다고 확인한 것만 쓴다.
- OpenDART 응답 원본은 캐시(추적하지 않음)에만 둔다.

## 9. 위험

- 회사 선정 편향: 금융업 제외가 결과를 좋게 만들 수 있다. 제외 목록과 수를 보고한다.
- 정답 생성기의 오류: 정답 생성기도 PDF 글자 층을 읽는 코드다. 제품 코드를 가져다 쓰지 않지만 같은 글자 층을 보므로, 글자 층 자체의 잘못(예: 로마 숫자를 "l"로 담은 것)은 둘 다 같이 받을 수 있다. 매핑표 검토와 OpenDART 대조로 줄인다.
- 정답 생성기와 채점기는 개발 문서로 다듬었다. 새 문서에서 정답 생성기의 결함이 나오면(4.5의 `ok` 판정) 따로 보고한다.
- 사람 검토자가 한 명(사용자)이고 1차 판정을 Claude가 한다.
- 모델 비결정성: 온도 0이어도 결과가 달라질 수 있다. 한 번만 실행하고, 반복 측정은 10절에서 정한다.

## 10. 사용자 결정 사항

1. 텍스트 PDF 회사 수(제안 10곳), 모집단(종목코드가 있는 회사 전체 또는 유가증권시장만), 금융업 제외.
2. 감사보고서 PDF를 받는 방법(사용자가 DART 웹에서 받기, 또는 다른 방법)과 내려받기 승인.
3. 새 OpenDART 조회 승인: 모집단 파일(`corpCode.xml`, 다시 받을지 캐시를 쓸지), 후보마다 기업개황(`company.json`)과 공시 목록(`list.json`), 포함된 10곳의 재무제표(`fnlttSinglAcntAll`, CFS, 필요하면 OFS).
4. 합성 스캔 조건 3개를 그대로 쓸지.
5. 사진 PDF를 넣을지. 넣는다면 사용자가 찍는다.
6. 반복 실행(모델 비결정성 확인)을 넣을지.
