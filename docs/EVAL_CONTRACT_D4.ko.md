# D4 문서 → 엑셀 정확도 평가 계약 (초안 2판, 2026-10-10)

- 상태: **초안 2판. Codex 1차 검토(12건)를 반영했다([결과](reviews/D4_contract_codex_result.ko.md), [응답](reviews/D4_contract_codex_response.ko.md)). Codex 재검토와 사용자 결정(10절) 전.** 평가 문서를 고르거나 내려받기 **전에** 확정한다.
- 대상 기능: v0.2 "문서 → 검증된 엑셀" (`python -m dart_review extract`, API `POST /jobs`).
- **목적:** 처음 보는 재무제표 PDF에서, 엑셀에 **표시 없이 들어간 틀린 숫자**, **표시 없이 틀린 계정명**, **표시 없이 빠진 숫자**가 몇 칸인지 잰다. 확인 필요 표시가 얼마나 많은지(사람이 확인할 양)와 합계 검산이 실제로 돈 비율도 같이 잰다.
- **이 평가로 하지 않는 것:**
  - 개발 중에 본 문서 6개(11절)의 결과를 평가 결과로 쓰지 않는다. 그 문서들로 고쳤기 때문이다.
  - "AI가 규칙보다 낫다"를 이 평가 하나로 주장하지 않는다. 두 방식의 결과는 나란히 보고만 한다.
  - 회사 10곳은 사례다. 결과를 일반적인 오류율의 정밀한 추정으로 쓰지 않는다. 칸들은 독립이 아니다(같은 문서, 같은 표 구조).
  - 자본변동표는 v0.2가 읽지 않는다(문제로만 표시). 평가 대상이 아니다. "읽지 않았다는 표시가 있는가"만 본다.

## 1. 순서

| 단계 | 하는 일 |
|---|---|
| ① 계약 | 이 문서를 확정한다. 모집단, 순서, 제외 규칙, 정답 규칙, 지표, 기준을 문서를 고르기 전에 고정한다 |
| ② Codex 검토 (필수) | 1차 완료(12건 반영). 2판을 재검토받는다 |
| ③ 사용자 결정 | 10절. 새 문서 내려받기와 OpenDART 조회는 사용자 승인 뒤에 한다 |
| ④ 모집단·순서 고정 | 모집단 파일과 SHA-256, 순서를 만드는 코드와 시드, 제외 규칙을 커밋한다. **이 커밋 전에는 어떤 후보 문서도 열지 않는다** |
| ⑤ 후보 판정과 문서 준비 | 순서대로 후보를 하나씩 판정하고(포함, 또는 제외 이유) 기록한다. 포함된 10곳의 문서를 받고 SHA-256을 기록한다. 합성 스캔을 만든다(3.2) |
| ⑥ 정답 준비 | 정답 생성기(4.2)를 돌리고, 사람이 매핑표를 검토·확정한다. **제품을 이 문서들에 돌리기 전에** 끝낸다 |
| ⑦ 사전 등록 | 후보 판정 기록, 문서 해시, 정답, 매핑표, 제품 커밋 P, 평가 도구 커밋, 모델·OCR 버전을 커밋 R로 고정한다 |
| ⑧ 실행 | 규칙 → AI 순서로 한 번씩. 사용자 승인 뒤 |
| ⑨ 판정·보고 | 자동 채점, 사람 검토(6절), 기준 판정. 실패를 포함해 그대로 보고한다 |

- ⑦ 뒤에는 제품과 정답을 바꾸지 않는다. 평가 중에 결함을 찾으면 고치지 않고 실패로 잰다. 정답을 고쳐야 하면 고친 이유와 전후를 기록하고, 고친 정답과 원래 정답의 두 결과를 모두 보고한다.
- ⑤에서 제품을 후보 문서에 돌리지 않는다. 후보 판정은 4절의 정답 생성기도 쓰지 않는다(문서를 받을 수 있는지, 감사보고서가 있는지만 본다).

## 2. 대상

- **제품:** ⑦에서 고정하는 커밋 P.
- **읽기 방식 두 가지:**
  - AI (`--reader ai`, 기본값): 로컬 비전 모델이 띠 단위로 읽는다. 텍스트 PDF는 숫자와 계정명을 PDF 글자의 같은 줄과 대조한다. 스캔·사진은 숫자를 OCR의 같은 줄에서 찾고, 계정명은 macOS Vision이 읽은 경우에만 대조한다.
  - 규칙 (`--reader rules`): 단어 위치와 규칙만. 참고로 같이 잰다.
- **모델:** Ollama, `qwen3-vl:8b`(Q4_K_M, digest는 ⑦에서 기록), 프롬프트 `band-v1`, 온도 0, num_ctx 16384, num_predict 2000, 빈 생각 블록 미리 채우기. 기계: Apple M5 Pro, 메모리 24GB.
- **OCR:** Tesseract 5.5.3(kor+eng), macOS Vision(시스템 버전). 버전은 ⑦에서 기록한다.

## 3. 평가 문서

세 묶음으로 나눠 따로 보고한다. 묶음끼리 합친 점수 하나로 판정하지 않는다.

### 3.1 텍스트 PDF (실제 감사보고서)
- **모집단:** OpenDART 회사 고유번호 목록(`corpCode.xml`, 캐시)에서 종목코드가 있는 회사. 파일의 받은 날짜와 SHA-256을 ④에서 기록한다. (유가증권·코스닥 구분은 이 파일에 없다. 시장을 한정할지는 10절에서 정한다.)
- **순서:** 각 회사의 `sha256("D4-2026|" + 고유번호)`를 오름차순으로 정렬한 순서. 시드 문자열과 코드를 ④에서 커밋한다.
- **제외 규칙 (순서대로 판정하고, 제외마다 이유를 기록한다):**
  1. 개발·봉인에 쓴 회사: 삼성전자, NAVER, 한화시스템, 포스코, LG에너지솔루션, 카카오, 셀트리온, CJ제일제당, 이마트(고유번호 목록을 ④에서 고정).
  2. 금융업: OpenDART 기업개황의 업종코드(KSIC)가 64~66으로 시작하는 회사. 표 구조가 다르다. 제외한 회사 수를 보고한다.
  3. 2025 회계연도 사업보고서에 연결감사보고서(PDF로 받을 수 있는 것)가 없는 회사.
- 순서대로 포함된 회사가 10곳이 되면 멈춘다. 판정 기록에는 판정한 모든 후보(포함과 제외)가 들어간다.
- 문서: 각 회사의 2025 연결감사보고서 PDF. 페이지 지정 없이 문서 전체를 넣는다(실제 사용과 같게).

### 3.2 합성 스캔 (3.1 문서에서 만든 이미지 PDF)
- 3.1 문서의 재무제표 쪽(정답이 있는 쪽)을 쪽 전체 그대로 이미지로 바꾼다. 자르지 않는다. 조건: 200dpi 정상, 150dpi + 1도 기울기, 150dpi + 흐림(제안). 3조건 × 10문서.
- 만드는 코드와 시드를 ⑦에서 고정한다. 합성 쪽과 원본 쪽의 대응표를 남기고, 쪽 수가 같은지 확인한다.
- 정답은 3.1의 같은 쪽 정답을 쓴다. 쪽을 자르지 않으므로 인쇄된 칸이 이미지에서 빠지지 않는다.

### 3.3 사진 PDF (선택, 사용자 결정)
- 사용자가 인쇄물이나 화면을 휴대폰으로 찍은 PDF. 개인정보가 없는 공시 문서만 쓴다. 찍는 조건은 사용자가 정하고 기록한다.
- 문서 수가 적으므로 사례 보고로만 쓴다. 정답은 원본 텍스트 PDF가 있으면 그 정답을, 없으면 OpenDART와 사람 검토로 정한다.

## 4. 정답

### 4.1 칸
- (문서, 재무제표, 인쇄된 행, 기간) 하나가 칸 하나다. 기간은 당기와 전기 두 개다. 정답 값은 **인쇄된 그대로의 부호**를 원 단위로 바꾼 값이다(괄호는 음수).
- 계정명 정답은 그 줄에 인쇄된 계정명이다(항목 번호와 주석 번호를 뺀 것).

### 4.2 정답 생성기와 매핑표 (제품 코드와 독립)
- 정답 생성기는 제품의 표 해석 코드(`dart_review/documents/`)를 쓰지 않는다. PDF 글자 층을 직접 읽어, OpenDART의 각 값(인쇄 단위로 나눈 숫자)을 재무제표 쪽에서 찾고, 그 숫자가 있는 줄의 계정명과 기간 칸(그 줄의 금액 순서)을 기록한다.
- 자동으로 정하지 못한 것은 매핑표로 사람에게 넘긴다:
  - OpenDART 값이 인쇄본에서 하나로 찾아지지 않는 경우(없음, 여러 곳)
  - 인쇄된 금액 줄 가운데 OpenDART 값과 맞지 않는 줄(OpenDART가 세부를 다르게 묶은 경우. 개발 중 포스코·LG에너지솔루션에서 확인)
  - 한 인쇄 칸이 OpenDART 항목 여럿에 해당하는 경우(예: "기본 및 희석주당순손익" 한 줄이 OpenDART의 기본·희석 두 항목)
- 매핑표에는 칸마다 쪽, 줄의 인쇄 글자, 결정과 그 이유를 적는다. Claude가 1차로 쓰고 사용자가 확인한다. 확정한 뒤에 바꾸면 변경 이력을 남긴다.
- 정답에 넣지 않는 것: 자본변동표, 주석.
- 구현: `eval/d4_gold.py`(정답 생성기), `eval/d4_score.py`(4.3·4.4 채점). 개발 문서 6개로만 시험했다. 개발용 텍스트 PDF 다섯 개에서 정답과 규칙 방식이 1,407칸 모두 일치했고, 매핑표에는 포스코 27건, LG에너지솔루션 6건(OpenDART가 세부를 다르게 묶은 값)이 남았다. 두 도구 모두 이 문서들로 다듬었으므로, 이 일치는 정답 생성기의 정확성 근거가 아니다.

### 4.3 칸마다의 채점 (⑨에서 자동으로, 정답과 대조)

| 결과 | 뜻 |
|---|---|
| 맞음 | 같은 재무제표·같은 기간에서 정답 행과 같은 값, 계정명도 정답과 같다 |
| 값 틀림 | 정답 행이 있는데 값이 다르다(자릿수, 단위 10³·10⁶·10⁸, 부호, 다른 기간의 값 포함) |
| 계정명 틀림 | 값과 기간은 정답 행과 같은데 계정명이 다른 계정이다(한쪽이 다른 쪽을 포함하는 경우 포함: "부채"와 "유동부채") |
| 정답에 없는 칸 | 정답 어느 행에도 대응하지 않는 칸(주석 표를 읽은 행 등). 사람 검토로 틀림 여부를 정한다 |

- 부호: 정답이 인쇄된 부호이므로 부호 차이는 값 틀림이다. OpenDART의 부호 관례(비용을 양수로 저장 등)는 정답 생성 때만 쓰고 채점에는 쓰지 않는다.
- 계정명 비교는 띄어쓰기·항목 번호·주석 표기를 뺀 문자열로 한다. 표기만 다르고 같은 계정인지 애매한 것은 사람 검토로 보낸다.

### 4.4 빠진 칸과 표시
- **빠진 칸:** 정답 칸 가운데 엑셀의 어느 칸에도 대응하지 않는 칸. 같은 값이 다른 행에 있어도 빠진 칸이다(정답과 행 단위로 대조한다).
- **칸의 표시:** 엑셀에서 그 칸이 "확인 필요"면 표시된 것이다.
- **빠진 칸의 표시:** 그 재무제표의 문제 목록이 빠진 칸을 **가리키면** 표시된 것이다. 가리킨다는 것은 그 금액의 인쇄 글자를 따옴표로 적었거나("원본의 금액 '47'를 AI가 읽지 않았다"), 그 행과 기간을 적은 것이다.
- "AI가 한 부분을 읽지 못했다"처럼 어느 금액인지 말하지 않는 메시지는 칸의 표시로 인정하지 않는다. 이런 메시지가 덮을 수 있는 빠진 칸은 G1로 따로 센다.

## 5. 지표와 기준

| 지표 | 정의 | 기준 |
|---|---|---|
| **S1 표시 없이 틀린 값** | 값 틀림 칸 가운데 "확인 필요"가 아닌 칸 | 3.1 **0**, 3.2 **0** |
| **L1 표시 없이 틀린 계정명** | 계정명 틀림 칸 가운데 "확인 필요"가 아닌 칸 | 3.1 **0**, 3.2 보고만 |
| **S2 표시 없이 빠진 칸** | 빠진 칸 가운데 문제 목록이 가리키지 않는 칸 | 3.1 **0**, 3.2 보고만 |
| G1 포괄 메시지로만 덮인 빠진 칸 | S2에 들어간 칸 가운데 "한 부분을 읽지 못했다"가 있는 재무제표의 칸 | 보고만 |
| A1 확인 필요 비율 | 표시된 칸 / 엑셀의 칸 | 보고만 |
| A2 덮은 비율 | 맞음 칸 / 정답 칸 | 보고만 |
| A3 시간 | 문서당 실행 시간, 모델 호출 수 | 보고만 |
| A4 합계 검산 비율 | 검산한 합계 수(재무제표의 `sums_checked`)와, 검산하지 못했다고 보고된 재무제표 수 | 보고만 |

- 공식 판정은 S1, L1, S2로 한다. 묶음(3.1, 3.2)마다, 읽기 방식마다 따로 판정한다. **제품 판정은 AI 방식이다.**
- 기준을 충족해도 "틀린 숫자가 없다"고 일반화하지 않는다. 칸 수, 문서 수, 정답에서 사람이 정한 칸 수를 함께 적는다.

## 6. 사람 검토

- 대상: 매핑표(4.2), 정답에 없는 칸, 애매한 계정명, 빠진 칸 가운데 정답 생성기가 자동으로 정하지 못한 칸.
- Claude가 1차로 판정하고 근거(쪽, 인쇄된 글자)를 적는다. 사용자가 확인한다. 판정을 바꾸면 변경 이력을 남긴다. 제3의 독립 검토자는 없다(한계로 보고한다).
- 매핑표는 실행 전(⑥)에, 실행 결과에 대한 검토는 실행 뒤(⑨)에 한다. 실행 결과를 본 뒤 매핑표를 바꾸면 4.2의 변경 이력과 두 결과 보고를 따른다.

## 7. 실행과 장애

- 실행 명령은 ⑦에서 고정한다. 문서 목록은 평가 도구의 입력 파일로 뺀다.
- 모델 서버 장애(연결 실패 등, 출력 한도 초과가 아닌 오류)가 나면 그 방식 전체를 새 폴더에서 다시 돌리고 두 기록을 모두 남긴다.
- 출력 한도 초과(띠 하나를 못 읽음)는 장애가 아니라 제품 동작이다. 그대로 잰다.

## 8. 공개와 데이터

- 평가 문서 PDF는 커밋하지 않는다. 회사, 문서 이름, 접수번호, SHA-256, 쪽 수만 남긴다.
- 기록에는 공시된 숫자와 계정명만 남긴다. 사진 PDF는 사용자가 개인정보가 없다고 확인한 것만 쓴다.
- OpenDART 응답 원본은 캐시(추적하지 않음)에만 둔다.

## 9. 위험

- 회사 선정 편향: 금융업 제외가 결과를 좋게 만들 수 있다. 제외 목록과 수를 보고한다.
- 정답 생성기의 오류: 정답 생성기도 PDF 글자 층을 읽는 코드다. 매핑표 검토와 OpenDART 대조로 줄이지만, 정답 생성기와 제품이 같은 잘못을 할 수 있다(같은 글자 층을 보기 때문). 정답 생성기는 제품 코드를 가져다 쓰지 않는다.
- 사람 검토자가 한 명(사용자)이고 1차 판정을 Claude가 한다.
- 모델 비결정성: 온도 0이어도 결과가 달라질 수 있다. 한 번만 실행하고, 반복 측정은 10절에서 정한다.

## 10. 사용자 결정 사항

1. 텍스트 PDF 회사 수(제안 10곳), 모집단(종목코드가 있는 회사 전체 또는 유가증권시장만), 금융업 제외.
2. 감사보고서 PDF를 받는 방법(사용자가 DART 웹에서 받기, 또는 다른 방법)과 내려받기 승인.
3. 새 OpenDART 조회 승인: 후보마다 기업개황(업종), 사업보고서 목록, 포함된 10곳의 재무제표(CFS, 필요하면 OFS).
4. 합성 스캔 조건 3개를 그대로 쓸지.
5. 사진 PDF를 넣을지. 넣는다면 사용자가 찍는다.
6. 반복 실행(모델 비결정성 확인)을 넣을지.
