# D4 문서 → 엑셀 정확도 평가 계약 (초안, 2026-10-10)

- 상태: **초안. Codex 검토 전, 사용자 결정 전.** 이 문서를 검토받고 사용자 결정(10절)을 반영한 뒤 사전 등록으로 확정한다. 평가 문서를 고르거나 내려받기 **전에** 커밋한다.
- 대상 기능: v0.2 "문서 → 검증된 엑셀" (`python -m dart_review extract`, API `POST /jobs`).
- **목적:** 처음 보는 재무제표 PDF에서, 엑셀에 **표시 없이 들어간 틀린 숫자**와 **표시 없이 빠진 숫자**가 몇 칸인지 잰다. 확인 필요 표시가 얼마나 많은지(사람이 확인할 양)도 같이 잰다.
- **이 평가로 하지 않는 것:**
  - 개발 중에 본 문서 6개(11절)의 결과를 평가 결과로 쓰지 않는다. 그 문서들로 고쳤기 때문이다.
  - "AI가 규칙보다 낫다"를 이 평가 하나로 주장하지 않는다. 두 방식의 결과는 나란히 보고만 한다.
  - 자본변동표는 v0.2가 읽지 않는다(문제로만 표시). 평가 대상이 아니다. 대신 "읽지 않았다는 표시가 있는가"만 본다.

## 1. 순서

| 단계 | 하는 일 |
|---|---|
| ① 계약 초안 | 이 문서를 커밋한다. 문서 선정 규칙, 정답 규칙, 지표, 기준을 문서를 고르기 전에 고정한다 |
| ② Codex 검토 (필수) | 이 계약과 v0.2 코드(`6e8528d^..HEAD`), 개발 측정 기록을 검토받고 반영한다 |
| ③ 사용자 결정 | 10절의 결정 사항. 새 문서 내려받기와 OpenDART 조회는 사용자 승인 뒤에 한다 |
| ④ 문서 준비 | 3절 규칙으로 회사를 뽑고, 문서를 받고, 합성 스캔을 만든다. 문서마다 SHA-256을 기록한다 |
| ⑤ 정답 준비 | OpenDART 응답을 캐시에 받는다. 정답 규칙(4절)으로 칸마다 정답을 정한다. 실행 결과를 보기 전에 끝낸다 |
| ⑥ 사전 등록 | 문서 목록과 해시, 정답, 제품 커밋, 평가 도구 커밋, 모델과 옵션을 고정 커밋 R으로 남긴다 |
| ⑦ 실행 | 규칙 → AI 순서로 한 번씩. 사용자 승인 뒤 |
| ⑧ 판정·보고 | 자동 분류, 사람 검토(6절), 기준 판정. 실패를 포함해 그대로 보고한다 |

- ⑥ 뒤에는 제품을 바꾸지 않는다. 평가 중에 결함을 찾으면 고치지 않고 실패로 잰다. 고친 버전은 다음 평가의 대상이다.

## 2. 대상

- **제품:** ⑥에서 고정하는 커밋 P. 개발 측정 때의 코드는 `8b0a7bd`다(11절).
- **읽기 방식 두 가지:**
  - AI (`--reader ai`, 기본값): 로컬 비전 모델이 띠 단위로 읽고, 원본의 글자(텍스트 PDF) 또는 OCR(Tesseract, macOS Vision)로 숫자마다 대조한다.
  - 규칙 (`--reader rules`): 단어 위치와 규칙만. 참고로 같이 잰다.
- **모델:** Ollama, `qwen3-vl:8b`(Q4_K_M, digest는 ⑥에서 기록), 프롬프트 `band-v1`, 온도 0, num_ctx 16384, num_predict 2000, 빈 생각 블록 미리 채우기. 기계: Apple M5 Pro, 메모리 24GB.
- **OCR:** Tesseract 5.5.3(kor+eng), macOS Vision(시스템 버전 기록). 버전은 ⑥에서 기록한다.

## 3. 평가 문서

세 묶음으로 나눠 따로 보고한다. 묶음끼리 합친 점수 하나로 판정하지 않는다.

### 3.1 텍스트 PDF (실제 감사보고서)
- **회사 선정 규칙(제안):** 2025 회계연도 사업보고서를 낸 유가증권시장 상장사 가운데, 개발에 쓴 회사(삼성전자, NAVER, 한화시스템, 포스코, LG에너지솔루션)와 v0.1 봉인·개발 회사를 뺀 목록에서 고정 시드로 **10곳**을 뽑는다. 금융업(은행·보험·증권)은 표 구조가 달라 뺀다(빼는 것 자체를 보고한다).
- 문서: 각 회사의 2025 연결감사보고서 PDF(DART 첨부). 감사보고서가 없으면 다음 순번 회사로 넘어가고 그 사실을 기록한다.
- 페이지 지정 없이 문서 전체를 넣는다(실제 사용과 같게).

### 3.2 합성 스캔 (3.1 문서에서 만든 이미지 PDF)
- 3.1의 각 문서에서 재무제표 쪽만 이미지로 바꾼다. 조건(제안): 200dpi 정상, 150dpi + 1도 기울기, 150dpi + 흐림. 3조건 × 10문서.
- 정답은 3.1과 같다. 이미지로 바꾸는 과정은 코드로 고정한다(시드 포함).

### 3.3 사진 PDF (선택, 사용자 결정)
- 사용자가 인쇄물이나 화면을 휴대폰으로 찍은 PDF. 개인정보가 없는 공시 문서만 쓴다.
- 찍는 조건(한 쪽씩, 두 쪽 펼침)은 사용자가 정하고 기록한다. 문서 수가 적으므로 사례 보고로만 쓴다.

## 4. 정답

- **칸의 단위:** (문서, 재무제표, 행, 기간) 하나가 칸 하나다. 기간은 당기와 전기 두 개다.
- **정답 출처 두 가지:**
  1. OpenDART `fnlttSinglAcntAll`(연결 재무제표는 CFS, 별도는 OFS). 원 단위 정수.
  2. 3.1 문서의 텍스트 층(인쇄된 글자). 같은 줄에 계정명과 금액이 함께 있다.
- **칸마다의 판정(개발 측정 `eval/measure_documents.py`와 같은 분류):**

| 분류 | 뜻 | 맞음/틀림 |
|---|---|---|
| dart_exact | OpenDART에 같은 계정명·같은 기간·같은 값 | 맞음 |
| dart_value | 같은 기간에 같은 값, 계정명은 다름 | 맞음 (계정명 차이는 따로 센다) |
| dart_sign | 부호만 반대 (현금 유출을 양수로 저장한 회사가 있다) | 맞음 |
| pdf_only | OpenDART에 없고, 텍스트 층의 같은 줄에 같은 금액이 인쇄돼 있다 | 맞음 (OpenDART가 표시를 다르게 한 경우) |
| wrong_period | 값이 다른 기간에만 있다 | **틀림** |
| unit_mismatch | 10³·10⁶·10⁸배를 하면 OpenDART와 같다 | **틀림** |
| unconfirmed | 위 어디에도 없다 | 사람 검토(6절) 뒤 맞음/틀림 |

- **빠진 칸:** OpenDART 값 가운데 엑셀의 어느 칸에도 없는 값(부호 무관). 사람 검토로 "문서에 인쇄되지 않은 값(OpenDART 쪽 세분)"과 "문서에 있는데 엑셀에 없는 값"을 나눈다. 뒤의 것만 빠진 칸이다.
- **표시:** 엑셀에서 그 칸이 "확인 필요"이거나, 그 숫자를 읽지 않았다는 문제가 그 재무제표의 문제 목록에 있으면 표시된 것이다.
- **알려진 한계:** dart_value는 같은 값이 다른 계정에 있어도 맞음이 된다(우연한 일치). 개발 측정에서는 큰 금액이 대부분이라 위험이 낮다고 봤지만, 작은 값(1,000 미만)은 따로 센다.

## 5. 지표와 기준

| 지표 | 정의 | 기준 (제안) |
|---|---|---|
| **S1 표시 없이 틀린 칸** | 틀린 칸 가운데 표시되지 않은 칸 수 | 텍스트 PDF(3.1) **0**. 합성 스캔(3.2) **0** |
| **S2 표시 없이 빠진 칸** | 빠진 칸 가운데 표시되지 않은 칸 수 | 3.1 **0**. 3.2는 보고만 |
| A1 확인 필요 비율 | 표시된 칸 / 엑셀의 칸 | 보고만 (3.1 AI 10% 이하를 목표로 기록) |
| A2 덮은 비율 | 엑셀의 맞는 칸 / OpenDART 정답 칸 | 보고만 |
| A3 시간 | 문서당 실행 시간, 모델 호출 수 | 보고만 |

- 공식 판정은 S1과 S2만으로 한다. 묶음(3.1, 3.2)마다, 읽기 방식마다 따로 판정한다. **제품 판정은 AI 방식이다.**
- 틀린 칸이 0이어도 "틀린 숫자가 없다"고 일반화하지 않는다. 칸들은 독립이 아니다(같은 문서, 같은 표 구조). 칸 수와 문서 수를 함께 적는다.

## 6. 사람 검토

- unconfirmed 칸, 빠진 칸, 계정명 차이 상위 목록을 사람이 원본 PDF와 대조한다. Claude가 1차로 분류하고 사용자가 확인한다.
- 검토 결과는 칸마다 근거(쪽, 인쇄된 글자)와 함께 파일로 남긴다. 검토 전에 판정을 출력하지 않는다.

## 7. 실행과 장애

- 실행 명령은 ⑥에서 고정한다. 기본은 `python eval/measure_documents.py --pdf-dir <폴더> --reader <방식> --out <폴더>`를 평가용 문서 목록으로 바꾼 것이다(문서 목록은 평가 도구의 입력 파일로 뺀다).
- 모델 서버 장애(연결 실패, 출력 한도 초과가 아닌 오류)가 나면 그 방식 전체를 새 폴더에서 다시 돌리고 두 기록을 모두 남긴다.
- 출력 한도 초과(띠 하나를 못 읽음)는 장애가 아니라 제품 동작이다. 그대로 잰다.

## 8. 공개와 데이터

- 평가 문서 PDF는 커밋하지 않는다. 회사, 문서 이름, 접수번호, SHA-256, 쪽 수만 남긴다.
- 기록에는 공시된 숫자와 계정명만 남긴다. 사진 PDF는 사용자가 개인정보가 없다고 확인한 것만 쓴다.
- OpenDART 응답 원본은 캐시(추적하지 않음)에만 둔다.

## 9. 위험

- 회사 선정 편향: 고정 시드로 뽑지만, 금융업 제외가 결과를 좋게 만들 수 있다. 제외 목록을 보고한다.
- OpenDART와 인쇄본의 차이: 회사가 XBRL에서 세부 계정을 다르게 묶는다(개발 중 포스코). pdf_only가 이를 흡수하지만, 스캔 묶음에는 텍스트 층이 없으므로 3.1의 같은 문서 판정을 가져다 쓴다.
- 모델 비결정성: 온도 0이어도 결과가 달라질 수 있다. 한 번만 실행하고, 반복 측정은 이 평가에 넣지 않는다(10절에서 바꿀 수 있다).

## 10. 사용자 결정 사항

1. 텍스트 PDF 회사 수(제안 10곳)와 선정 규칙(고정 시드, 금융업 제외).
2. 합성 스캔 조건 3개를 그대로 쓸지.
3. 사진 PDF를 넣을지. 넣는다면 사용자가 찍는다.
4. 새 OpenDART 조회(10곳 × CFS, 필요하면 OFS)와 감사보고서 PDF 내려받기 승인.
5. A1 목표(10%)를 기준으로 올릴지, 보고만 할지.
6. 반복 실행(모델 비결정성 확인)을 넣을지.

## 11. 개발 중 측정 (평가 아님)

`eval/documents_2026-10-10/`. 개발에 쓴 문서 6개에서 OpenDART와 대조했다. 이 문서들로 결함을 찾아 고쳤으므로 평가 결과가 아니다. 숫자는 그 폴더의 `REPORT.ko.md`에 있다.
