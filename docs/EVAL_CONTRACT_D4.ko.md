### 1.1 고정 기록 (④, `eval/d4_preflight.py freeze`)
- 제품 커밋 P와 평가 도구 커밋 T, 그리고 각 커밋에서 다음 경로의 git 객체를 적는다.
  - 제품(P): `dart_review/`, `pyproject.toml`
  - 평가 도구(T): `eval/d4_gold.py`, `eval/d4_score.py`, `eval/d4_candidates.py`, `eval/d4_preflight.py`, `eval/d4_scan.py`(합성 스캔 코드와 조건)
- 환경도 적는다: Python 버전, 설치된 모든 패키지와 버전, 모델 digest(`ollama list`), Ollama 버전(모델 출력이 바뀔 수 있다), Tesseract 버전, macOS 버전(Vision OCR).
- 경로 하나라도 그 커밋에 없으면 고정 기록을 만들지 않는다.
- 모집단 파일(`corpCode.xml`)의 받은 날짜와 SHA-256, 순서 코드와 시드, 정렬된 전체 목록을 같은 커밋 F에 넣는다(3.1).

### 1.2 등록과 실행 전 점검 (⑦ `eval/d4_preflight.py register`, ⑧ `check`)
- **R은 파일만으로 고정할 수 없다.** 커밋은 자기 해시를 담을 수 없어서, 정답을 바꾼 새 커밋 R2와 그 등록 기록도 같은 모양으로 통과할 수 있다(4차 1번). 그래서 R을 저장소 밖에 고정한다.
  1. ⑦ `register`: 깨끗한 트리에서, 등록할 파일마다 HEAD의 git 객체를 적는다. 매핑표(이름이 `.mapping.json`이거나 내용에 `decisions`가 있는 파일)는 `confirmed`여야 받는다.
  2. 등록 기록을 커밋한 것이 R이다. R에 태그 `d4-registered`를 달고, **실행 전에 태그를 GitHub에 push한다**(사용자 승인). push 시각이 공개 기록이 된다.
  3. ⑧ `check --registered d4-registered --remote origin`: 원격 태그가 HEAD를 가리키는지까지 확인한다(`--remote`는 빼고 실행할 수 없다).
  - 남는 한계: 태그를 다른 커밋으로 옮겨 다시 push하는 것은 이 점검으로 막지 못한다. 실행 로그와 보고서에 R의 해시와 태그를 push한 시각을 적고, 태그를 옮기지 않는다.
- R을 새 작업 폴더로 꺼내(`git worktree add <폴더> d4-registered`) 그 안에서 점검하고 실행한다.
- 점검 항목(하나라도 실패하면 실행하지 않는다):
  - HEAD가 등록 커밋 R이고, push된 태그 `d4-registered`가 HEAD를 가리킨다.
  - 등록된 각 파일의 HEAD 객체가 등록 기록과 같다. 등록 기록의 P·T가 고정 기록과 같고, P·T가 R의 조상이다.
  - 작업 트리와 인덱스가 깨끗하다. 추적되지 않은 파일도 없다(`git status --porcelain --untracked-files=all`가 비어 있음). 커밋 사이의 diff만으로는 커밋하지 않은 변경을 보지 못하기 때문이다.
  - 고정된 각 경로의 HEAD 객체가 고정 기록과 같다.
  - `dart_review`를 이 작업 폴더에서 불러온다.
  - 환경(Python, 패키지, 모델 digest, Ollama, Tesseract, macOS)이 고정 기록과 같다.
- 점검 결과는 모든 항목과 함께 로그 파일로 남기고 실행 결과와 같이 커밋한다. 실패한 점검도 남긴다.
- **실행 절차 (7판, Codex 7차 3번):** 명령은 [`D4_RUN_PROCEDURE.ko.md`](D4_RUN_PROCEDURE.ko.md)에 고정한다(⑦에서 등록).
  - 작업 폴더, 점검 로그, 실행 폴더는 모두 저장소 밖에 둔다. 점검 로그는 실행 폴더의 형제 경로(`<실행 폴더>.preflight.json`)에 쓴다. 실행 폴더 안에 쓰면 폴더가 미리 생겨 실행기가 거부하고, 작업 폴더 안에 쓰면 트리가 더러워진다.
  - 실행기(`eval/d4_eval/run_d4.py`)는 점검 로그를 받아(`--preflight`) 다음을 확인한 뒤에만 실행하고, 로그의 SHA-256을 실행 기록에 적는다.
    - 모든 항목이 통과했다.
    - 지금 HEAD를 점검했다.
    - 작업 폴더가 여전히 깨끗하다.
  - 점검은 작업 폴더에서 모듈로 실행한다(`python -m eval.d4_preflight check …`). 고정 도구의 사용 예시(`python eval/d4_preflight.py check`)대로 하면 `ModuleNotFoundError`로 멈춘다. 제품이 가상환경에 설치돼 있지 않아 스크립트 폴더만으로는 제품을 불러오지 못하기 때문이다(2026-10-19 확인. 틀린 결과가 아니라 실행이 멈춘다). 고정 도구는 바꾸지 않는다.

### 1.3 신뢰 경계 (6판)
- **점검 도구가 지키는 것:** 정직하게 실행하는 사람이 실수로 등록된 것과 다르게 실행하는 일을 막는다. 예를 들면 커밋하지 않은 변경, 다른 제품·도구 커밋, 다른 환경, 등록 뒤에 바뀐 정답, 확정하지 않은 매핑표, 다른 PDF의 보고서다.
- **지키지 않는 것:** 실행하는 사람(사용자나 Claude)이 일부러 등록하지 않은 입력을 넣는 것. 이 프로젝트는 한 사람이 실행하므로 코드로 끝까지 막을 수 없다. 이것은 공개 기록(GitHub의 커밋과 태그 push 시각)과 독립 검토(Codex)로 확인한다. 5차 2·3·7번이 이 경우다.
- 그래서 다음 문장은 아래의 뜻으로만 읽는다(구현이 이보다 강하게 확인한다고 말하지 않는다).
  - **`source_verified`(원본 확인):** `--pdf`로 실행하면 채점기가 PDF 파일의 해시를 직접 계산한다. 저장된 보고서만 다시 채점하면 정답과 보고서에 **적힌** 해시를 비교할 뿐이다.
  - **`check`의 `--remote`:** 주어진 원격의 태그를 비교한다. 그 원격이 GitHub 저장소(`origin`, github.com/chan12-photo/dart-review-agent)인지는 실행하는 사람이 지킨다.
  - **`check --register`:** 주어진 등록 기록을 HEAD와 비교한다. 그 기록이 R에 커밋된 `eval/register_d4.json`인지는 실행하는 사람이 지킨다(공식 명령은 그 경로만 쓴다).
  - **공식 실행:** ⑦에서 고정한 명령만 쓴다. 채점기는 그 명령으로 실행됐는지 스스로 확인하지 않는다.
  - **모델 digest:** `ollama list`로 읽는다. 공식 실행은 Ollama를 7절의 명령 하나로만 띄운다(기본 주소 127.0.0.1:11434). 그래서 CLI가 보는 서버와 제품이 부르는 서버가 같다고 본다. 도구는 둘이 같은지 따로 확인하지 않는다.

## 2. 대상

- **제품:** ④에서 고정하는 커밋 P(후보 문서를 열기 전). 평가 도구는 커밋 T.
- **읽기 방식 두 가지:**
  - AI (`--reader ai`, 기본값): 로컬 비전 모델이 띠 단위로 읽는다. 텍스트 PDF는 숫자와 계정명을 PDF 글자의 같은 줄과 대조한다. 스캔·사진은 숫자를 OCR의 같은 줄에서 찾고, 계정명은 macOS Vision이 읽은 경우에만 대조한다.
  - 규칙 (`--reader rules`): 단어 위치와 규칙만. 참고로 같이 잰다.
- **모델:** Ollama, `qwen3-vl:8b`(Q4_K_M, digest는 ④에서 기록), 프롬프트 `band-v1`, 온도 0, num_ctx 16384, num_predict 2000, 빈 생각 블록 미리 채우기. 기계: Apple M5 Pro, 메모리 24GB.
- **OCR:** Tesseract 5.5.3(kor+eng), macOS Vision(시스템 버전). 버전은 ④에서 기록한다.

## 3. 평가 문서

세 묶음으로 나눠 따로 보고한다. 묶음끼리 합친 점수 하나로 판정하지 않는다.

### 3.1 텍스트 PDF (실제 감사보고서): 모집단과 순서
- **모집단:** OpenDART 회사 고유번호 목록(`corpCode.xml`)에서 종목코드가 있는 회사. 파일을 받은 날짜와 SHA-256을 ④에서 기록한다. (유가증권·코스닥 구분은 이 파일에 없다. 시장을 한정할지는 10절에서 정한다.)
- **순서:** 각 회사의 `sha256("D4-2026|" + 고유번호)`를 오름차순으로 정렬한 순서. 시드 문자열과 코드, 정렬된 전체 목록을 ④에서 커밋한다.
- 순서대로 포함된 회사가 10곳이 되면 멈춘다. 판정 기록에는 판정한 모든 후보가 들어간다.

### 3.2 후보 판정 절차 (순서대로, 후보마다 기록)

규칙은 `eval/d4_candidates.py`에 있고 T에 포함된다. 사람이 하는 일은 DART 화면의 첨부 목록을 그대로 적고 파일을 받는 것뿐이다. 무엇을 고를지는 규칙이 정한다.

1. **개발·봉인 회사:** 삼성전자, NAVER, 한화시스템, 포스코, LG에너지솔루션, 카카오, 셀트리온, CJ제일제당, 이마트(고유번호를 ④에서 고정)면 제외.
   - 고정한 고유번호(`eval/d4_excluded.json`): 삼성전자 00126380, NAVER 00266961, 한화시스템 00339391, 포스코 01620971, LG에너지솔루션 01515323, 카카오 00258801, 셀트리온 00413046, CJ제일제당 00635134, 이마트 00872984.
   - 개발 문서의 포스코는 비상장 법인(01620971)이라 원래 모집단에 없다. 상장사 POSCO홀딩스는 다른 법인이므로 이 규칙으로 제외하지 않는다(같은 그룹이지만 문서를 개발에 쓰지 않았다).
2. **금융업:** OpenDART 기업개황(`company.json`)의 업종코드(`induty_code`)가 64·65·66으로 시작하면 제외. 응답과 받은 시각을 기록한다.
3. **2025 회계연도 사업보고서:**
   - OpenDART 공시 목록(`list.json`, 정기공시, 2026-01-01~2026-06-30 접수)에서 보고서명이 "사업보고서 (2025.12)"인 공시를 모두 찾는다. 앞에 붙은 "[기재정정]", "[첨부정정]", "[첨부추가]"도 포함한다(`report_filings`).
   - 접수일, 같으면 접수번호가 늦은 것부터 차례로 본다.
   - 하나도 없으면 제외(사유: 사업보고서 없음).
4. **연결감사보고서 첨부:**
   - 3의 차례대로 공시를 열어 DART가 보여 주는 첨부 이름을 **보이는 순서 그대로** 기록한다.
   - 이름에 "연결감사보고서"가 있고(띄어쓰기 무시) "내부회계"가 없는 첫 첨부를 쓴다(`pick_attachment`). 그런 첨부가 있는 첫 공시에서 멈춘다(늦은 공시가 첨부만 고치거나 더했을 수 있다).
   - 어느 공시에도 없으면 제외(사유: 연결감사보고서 첨부 없음).
5. **받기:**
   - 그 첨부의 PDF를 받는다(받는 방법은 10절).
   - 실패하면 **10분 이상 지난 뒤** 한 번 더 시도한다. 두 번 모두 실패하면 제외(사유: 받기 실패).
   - 시도마다 시각과 오류 종류(연결 실패, 시간 초과, HTTP 상태, 받은 파일이 PDF가 아님)를 기록한다.
6. **열림과 글자 층 (`eval/d4_candidates.py check`):** 글자 수만 센다. 재무제표 내용은 보지 않는다.
   - pdfplumber가 모든 쪽을 오류 없이 읽지 못하면 제외(사유: 열리지 않음).
   - 공백을 뺀 글자가 1,000자 미만이거나, 글자가 100자 이상인 쪽이 전체 쪽의 절반 미만이면 제외(사유: 글자 층 없음, 스캔 문서).
   - 둘 다 아니면 포함한다.
   - 개발 PDF에서의 결과: 텍스트 PDF 5개는 모두 "포함"(글자 100자 이상인 쪽이 42쪽 중 36쪽 ~ 147쪽 중 142쪽), 사진 PDF는 "글자 층 없음"(0자).
7. **기록:** 고유번호, 회사명, 고려한 공시 모두(접수번호, 보고서명, 접수일), 각 공시의 첨부 이름 목록, 고른 첨부(목록에서의 순번과 이름), 받기 시도 시각과 결과, check 출력(SHA-256, 쪽 수, 글자 수, 쪽별 글자 수), 판정과 사유.
- **1~4단계는 `eval/d4_candidates.py select`가 한다.** 입력은 후보마다 기록한 것(업종코드, `list.json`의 공시, 공시마다 DART가 보여 준 첨부 이름)과, 따로 주는 제외 고유번호 파일(④에서 고정, `--excluded`)뿐이다. 공시 목록을 기록하지 않은 후보는 "기록 부족"이다(빈 목록과 구별한다). 접수일이 2026-01-01~06-30 밖인 공시는 쓰지 않고 따로 적는다. 출력은 판정과 고려한 공시 모두다. 첨부 목록을 기록하지 않은 공시가 차례에 오면 "기록 부족"으로 멈춘다(건너뛰지 않는다). "내부회계"와 "연결감사보고서"는 띄어쓰기를 지우고 찾는다.
- 6단계의 기준은 **문서 전체**의 글자 층이다. 재무제표 쪽에 글자 층이 있다는 보장은 아니다(4차 11번). 그래서 쪽별 글자 수를 기록하고, 선정 뒤 정답 재무제표 쪽의 글자 층 상태를 따로 보고한다. 이 상태를 보고 후보를 바꾸지는 않는다.

- 이 절차는 재무제표 내용을 보지 않는다. 결과를 보고 후보를 고를 틈을 줄이기 위한 것이다.
- 기준(규칙, 문턱값)을 ⑤를 시작한 뒤에 바꾸면, 원래 기준의 모집단과 바뀐 기준의 모집단을 따로 보고한다.

### 3.3 합성 스캔 (3.1 문서에서 만든 이미지 PDF, `eval/d4_scan.py`)
- 3.1 문서의 재무제표 쪽(정답 재무제표의 첫 쪽부터 끝 쪽까지)을 쪽 전체 그대로 회색 이미지로 바꾼다. 자르지 않는다.
- 조건(제안, 10절 4): 3조건 × 10문서. 어느 문서로도 맞춰 보지 않고 정했다.
  - `normal`: 200dpi, 그대로
  - `tilt`: 150dpi, 1도 기울임(더 큰 바탕에 돌려 쪽 모서리를 자르지 않는다)
  - `blur`: 150dpi, 가우스 흐림 반지름 1.2픽셀
- 무작위 요소가 없다(같은 PDF와 조건이면 같은 이미지와 같은 파일). 그래서 시드가 없다. 코드와 조건은 T에 포함한다.
- 스캔마다 대응표(`<스캔>.map.json`)를 남긴다: 원본 SHA-256, 조건, 스캔 쪽마다의 원본 쪽, 스캔 파일과 픽셀의 SHA-256. 쪽 수가 같은지 만들 때 확인한다.
- 정답은 3.1의 확정된 정답을 대응표로 쪽 번호만 바꿔 쓴다(`eval/d4_score.py --page-map`). 채점기는 다음을 확인하고, 하나라도 다르면 채점하지 않는다:
  - 대응표의 원본 SHA-256이 정답의 원본 PDF 해시와 같다.
  - 대응표의 쪽 목록이 정답 재무제표의 쪽 목록과 순서까지 같다.
  - 보고서의 원본 해시가 스캔 파일의 해시와 같다.

### 3.4 사진 PDF (선택, 사용자 결정)
- 사용자가 인쇄물이나 화면을 휴대폰으로 찍은 PDF. 개인정보가 없는 공시 문서만 쓴다. 찍는 조건은 사용자가 정하고 기록한다.
- 문서 수가 적으므로 사례 보고로만 쓴다. 정답은 원본 텍스트 PDF가 있으면 그 정답을, 없으면 OpenDART와 사람 검토로 정한다.

## 4. 정답

### 4.1 칸과 재무제표
- 재무제표마다 id(제목@시작 쪽)와 쪽 범위가 있다. 같은 제목이 다시 나오면 다른 재무제표다.
- (재무제표 id, 인쇄된 행, 기간) 하나가 칸 하나다. 기간은 당기와 전기 두 개다.
- 정답 값은 **인쇄된 그대로의 부호**를 원 단위로 바꾼 값이다(괄호는 음수).
- 인쇄본이 "-"인 칸은 "값 없음" 칸이다. **정답 칸이 아니다**(칸 수에 넣지 않는다). 제품이 거기에 값을 넣었는지만 본다(4.3).
- 계정명 정답은 그 줄에 인쇄된 계정명이다(항목 번호와 주석 번호를 뺀 것).

### 4.2 정답 생성기와 매핑표 (제품 코드와 독립)
- 정답 생성기(`eval/d4_gold.py`)는 제품의 표 해석 코드(`dart_review/documents/`)를 쓰지 않는다. PDF 글자 층을 직접 읽어 인쇄된 칸을 만들고, OpenDART 값과 하나씩 짝지어 확인한다(같은 값이 두 행에 있으면 두 번 센다).
- **줄을 사람 없이 버리는 경우는 셋뿐이다:** 알려진 쪽 바닥글, 날짜가 든 기간 줄, 머리글·단위 낱말만 있는 줄("과 목", "제 57 (당) 기", "(단위: 원)"). 그 줄만의 행 이름이 남으면 버리지 않는다. 그래서 "당기순이익 47 48", "기본주당이익(단위: 원) 47 48"은 행이다.
- 자동으로 정하지 못한 것은 매핑표 항목(id가 있다)으로 사람에게 넘긴다:
  - `not_in_dart`: 인쇄된 칸인데 OpenDART에 그 값이 없다 → `keep`(인쇄 그대로 정답) 또는 `drop`
  - `dart_only`: OpenDART 값인데 인쇄본에 없다 → `ignore`(OpenDART가 다르게 묶음) 또는 `add`(정답 칸 추가)
  - `uncertain_line`: 쪽 아래쪽의, 쉼표 있는 금액이 없는 줄(바닥글 또는 작은 금액 행). 제안된 칸과 함께 → `ignore` 또는 `add`
  - `no_grouped_amounts`: 쉼표 있는 금액이 하나도 없는 재무제표(작은 금액이나 쉼표 없는 금액만 있는 표). 숫자가 있는 줄과 함께 → `add`(쉼표 없는 인쇄값 "1000"도 적을 수 있다) 또는 `ignore`. **`ignore`하면 그 문서는 공식 판정 불가다**(숫자가 있는 표가 정답 없이 남고, 제품도 놓치면 검사할 것이 사라진다. 5차 1번).
  - `ungrouped_amount`: 금액 자리에 쉼표 없는 네 자리 이상 숫자("1000")가 있는 줄. 자동으로 칸을 만들지 않는다 → `ignore` 또는 `add`
  - `statement_not_found`: OpenDART에는 있는 연결 재무제표(재무상태표, 손익계산서, 포괄손익계산서, 현금흐름표. 손익과 포괄손익은 따로 찾는다)인데 정답 생성기가 찾지 못했다. **`ignore`는 없다.** 정답 생성기와 제품이 같은 표를 함께 놓치면 검사할 것이 사라지기 때문이다(4차 3번). 결정은 셋 가운데 하나다.
    - `add_statement`: 사람이 원본을 보고 그 재무제표(id, 종류, 제목, 쪽, 단위)와 칸을 적는다. 쪽은 PDF의 쪽 수(정답에 기록) 안이어야 하고, id는 "제목@첫 쪽", 제목은 그 종류여야 한다. 다른 재무제표와 쪽이 겹치면 각각 어디에 인쇄됐는지(`overlap_note`)를 적어야 한다.
    - `same_statement`: 손익 또는 포괄손익이고, 다른 하나가 인쇄돼 있으며, 인쇄된 한 표가 둘을 겸한다. **도구는 다른 하나가 인쇄됐는지만 확인한다.** 겸한다는 판단은 사람의 근거(note)에 기댄다(5차 4번, 한계). 확인하지 못하면 `unscorable`을 쓴다.
    - `unscorable`: 그 문서는 공식 판정을 내지 않는다(5절의 상태). 문서 수와 이유를 보고한다.
  - `slots`(한 줄에 금액이 셋 이상), `no_label`(쪽 아래의 행 이름 없는 숫자 줄 포함), `one_slot_no_boundary`, `no_unit` → `ignore` 또는 `add`(칸을 직접 적는다. `no_unit`의 `add`는 근거에 사람이 확인한 단위와 그 인쇄 근거를 적는다)
- **매핑을 적용한 뒤 인쇄된 정답 칸이 하나도 없는 재무제표가 있으면, 어떤 결정으로 그렇게 됐든(`no_unit`·`no_grouped_amounts`의 `ignore`, 모든 칸의 `drop` 등) 그 문서는 공식 판정 불가다**(`unscorable`에 이유가 남는다). 제품도 그 표를 놓치면 검사할 것이 사라지기 때문이다(5차 1번, 6차 1번).
- **매핑표의 형식과 기계 검사(`apply_mapping`):**
  - 상태: `draft` 또는 `confirmed`. `confirmed`에는 확인한 사람(`confirmed_by`)과 시각(`confirmed_at`)이 있어야 한다.
  - 모든 항목에 결정이 있어야 하고, 없는 항목의 결정이 있으면 안 된다.
  - 결정마다 근거(`note`)가 있어야 한다. 근거는 **그 항목의** 쪽과 인쇄된 줄, 그리고 OpenDART 값과 인쇄 칸을 잇는 계산(합·차)을 적는다. 같은 근거 문장을 여러 항목에 복사하면 거부한다. **도구는 근거가 비어 있지 않고 서로 다른지만 확인한다.** 근거가 실제 쪽·줄·계산과 맞는지는 사람이 확인한다(6차 기록 2).
  - `add`는 칸이 하나 이상이어야 한다. 칸마다 그 재무제표의 쪽 범위, 행 이름, 기간(0·1), 인쇄 글자와 그 글자가 뜻하는 값(그 재무제표의 단위. 원 단위는 계정명에 "주당"이 있는 행, 또는 사람이 `"row_unit": "원"`으로 원 단위 행이라고 적은 칸만. 부호 포함)을 검사한다. `row_unit`은 사람의 선언이고 도구가 인쇄된 단위를 확인하지 않는다(5차 8번, 한계). 쓴 칸은 근거(note)에 단위가 인쇄된 쪽과 줄을 적는다. 이미 정답 칸이 있는 자리(재무제표, 쪽, 채점기와 같은 방식으로 다듬은 행 이름, 기간)에는 더할 수 없다. 그래서 "Ⅰ. 유동자산"을 "유동자산" 옆에 더해 한 인쇄 행을 두 칸으로 만들 수 없다.
  - `drop`은 칸 하나만 지운다.
- Claude가 1차로 쓰고(`draft`) 사용자가 확인한다(`confirmed`). 확정한 뒤에 바꾸면 변경 이력을 남긴다. **`draft` 매핑표로 낸 점수는 공식 판정이 될 수 없다**(5절의 상태).
- 정답에 넣지 않는 것: 자본변동표, 주석.
- 구현과 시험: `eval/d4_gold.py`, `eval/d4_score.py`. 개발 문서 6개로만 시험했다. 두 도구 모두 이 문서들로 다듬었으므로 개발 문서에서의 일치는 정확성의 근거가 아니다.

### 4.3 칸마다의 채점 (⑨, `eval/d4_score.py`)

| 결과 | 뜻 |
|---|---|
| 맞음 | 같은 재무제표·행(계정명)·기간의 제품 칸이 정답 값과 같다 |
| 값 틀림 | 같은 행·기간인데 값이 다르다(자릿수, 단위 10³·10⁶·10⁸, 부호, 다른 기간의 값 포함) |
| 계정명 틀림 | 그 행·기간의 제품 칸은 없는데, 같은 기간의 다른 행 이름 아래에 정답 값이 있다(쓰이지 않은 칸만) |
| 빠짐 | 위 어디에도 없다 |
| "-" 칸에 값 | 인쇄본이 "-"인 칸에 제품 값이 있다. 정답 칸이 아니므로 위 넷과 분모에 넣지 않고 따로 센다. 표시가 없으면 S1이다 |

- 짝짓는 순서: ① 같은 행·기간·값(맞음), ② 같은 행·기간(값 틀림, "-" 칸에 값), ③ 같은 기간의 다른 행에 같은 값(계정명 틀림). 각 단계에서 정답과 같은 쪽의 제품 칸을 먼저 쓴다(③에서 빠져 있던 것을 4차 5번에서 고쳤다). 같은 계정명이 두 행에 인쇄됐고 제품이 하나를 빠뜨렸을 때, 남은 행을 빠진 행과 짝지어 "값 틀림"으로 세지 않기 위해서다.
- 부호: 정답이 인쇄된 부호이므로 부호 차이는 값 틀림이다.
- 계정명 비교는 띄어쓰기·항목 번호("1.", "가.", "1)", "Ⅰ.")·주석 표기를 뺀 문자열로 한다. 오타는 다른 계정명이다(계정명 틀림).
- 제품 출력은 API 보고서 형식(JSON)으로 **한 번 저장하고**(`--report`) 그 파일로 채점한다. 저장된 보고서는 덮어쓰지 않는다. 4.5의 판정이 이 파일의 칸을 가리키기 때문이다.

### 4.4 빠진 칸과 "가리킴"
- **칸의 표시:** 엑셀에서 그 칸이 "확인 필요"면 표시된 것이다.
- **가리킬 수 있는 문장은 제품의 구조화된 보고 두 가지뿐이다.** 다른 문장(자유 문장, 따옴표 안의 숫자)은 어느 칸도 가리키지 않는다.
  - AI 방식: "10쪽 '매출액' 줄 전기: 원본의 금액 '47'를 AI가 읽지 않았다". 행 이름이 없는 줄은 "3쪽 당기: …", 사진(OCR)은 기간 없이 "5쪽 '매출액' 줄: OCR이 읽은 금액 '1,234'를 …"
  - 규칙 방식: "표에 넣지 못한 금액 N개 (1쪽 '기타(손실)' 줄 '47', 2쪽 '1,000', …): …". 처음 12개만 적히고, "외 N개"로 줄인 것은 가리키지 않는다.
- **빠진 칸이 가리켜졌다:** 그 재무제표(또는 문서 전체)의 보고 하나가 다음을 모두 만족한다.
  1. 쪽이 같고, 인쇄 금액이 같다. 숫자·쉼표와 **부호**(괄호나 앞의 -·−·△)를 비교한다. "47"은 "(47)"을 가리키지 않는다. OCR이 괄호를 잃은 보고도 가리키지 않는 것으로 센다.
  2. 행 이름을 적었으면 그 행이고, 기간을 적었으면 그 기간이다.
  3. 1·2에 맞는 정답 칸이 **한 자리**(쪽, 행, 기간)뿐이다. 예를 들어 같은 행의 당기·전기에 같은 금액이 있는데 기간을 적지 않았으면 어느 칸도 가리키지 않는다. 행 이름 없이 금액만 적었는데 그 쪽의 두 행에 그 금액이 있어도 마찬가지다.
  4. 보고 하나는 칸 하나만 가리킨다. 같은 자리에 빠진 칸이 둘이면 보고도 둘이어야 한다.
- 이 규칙은 제품에 불리한 쪽으로 엄격하다. 행 이름이 정답과 조금만 달라도(줄바꿈된 계정명의 일부 등) 가리키지 않은 것으로 센다. 계정명에 작은따옴표(')가 들어 있으면 보고를 해석하지 않는다(가리키지 않음).
- "AI가 한 부분을 읽지 못했다"처럼 금액을 적지 않은 메시지는 어느 칸도 가리키지 않는다. 그런 메시지가 있는 재무제표의 가리켜지지 않은 빠진 칸은 G1로 따로 센다.
- 제품이 찾지 못한 재무제표의 칸은 모두 빠짐이다(S2, 가리킴은 문서 전체의 보고로만).

### 4.5 정답에 없는 칸
- 제품 칸 가운데 어느 정답 칸과도 짝지어지지 않은 칸이다.
  - 예: 주석 표를 읽은 행, 인쇄되지 않은 값, 세 번째 기간 열의 값.
  - **어느 정답 재무제표와도 짝지어지지 않은 제품 재무제표의 칸**도 모두 포함한다.
- 칸마다 저장된 보고서 안의 id("재무제표 순번/행 순번/열")가 있다.
- **"확인 필요"가 아닌 것은 모두 사람이 판정한다.**
  - `wrong`: 엑셀에 틀린 값이 표시 없이 들어갔다.
  - `ok`: 인쇄본에 있는 값인데 정답 생성기가 놓친 것 등. 이 경우는 정답 생성기 결함으로 따로 보고한다.
- **판정 파일의 형식과 기계 검사:**
  - 판정한 보고서의 SHA-256(`report_sha256`)과 판정한 사람(`judged_by`)을 적는다.
  - 판정마다 `{"verdict": "wrong" 또는 "ok", "note": 근거}`를 적는다.
  - 다른 값, 근거 없음, 없는 id, 다른 보고서의 해시는 채점기가 거부한다.
- 판정이 없는 표시 없는 칸이 하나라도 있으면 공식 판정을 내지 않는다(5절의 상태).
- "확인 필요"인 칸은 목록으로만 보고한다.

### 4.6 같은 재무제표의 같은 계정명 행: 위치 검사 (7판, `eval/d4_eval/position_check.py`)
- **왜:** 4.3의 짝짓기는 (재무제표, 계정명, 기간, 값)으로 한다. 같은 쪽의 칸을 먼저 쓰고, 없으면 다른 쪽의 칸도 쓴다. 그래서 한 재무제표에 같은 계정명이 두 행 이상 인쇄되면, 두 행의 값을 서로 바꾼 엑셀도 두 칸 모두 "맞음"이 된다(Codex 7차 1번).
  - 예: 두산 10쪽 유동 "파생상품평가자산 204,454"와 비유동 "파생상품평가자산 54,102"
  - 예: 두산 10쪽 유동 "충당부채"와 11쪽 비유동 "충당부채"

  고정 채점기는 바꾸지 않고, 같은 저장 보고서에 이 검사를 더한다.
- **자리:** (재무제표, 4.3의 방식으로 다듬은 계정명, 기간)에 정답 칸이 둘 이상이고("-" 칸 포함) 그중 인쇄 금액이 하나 이상인 곳.
  - ⑦ 전에 PDF 글자 층에서 칸마다 인쇄 줄을 찾는다. 그 쪽에서 계정명이 같고, 그 기간 열에 그 인쇄 글자가 있는 줄이다. 찾은 줄을 인쇄 순서(쪽, 위에서 아래)로 등록한다: `eval/d4_eval/duplicate_places.json`, 8개 문서 66곳(같은 쪽 60곳, 두 쪽에 걸친 6곳).
  - 줄을 모두 찾지 못하면 만들지 않는다. 사람이 풀고, 추측하지 않는다.
  - **⑦ 관문 (재검토 3번):** 매핑표를 확정한 뒤, 등록 직전에 자리를 PDF와 그때의 매핑표로 다시 만들어 등록할 파일과 같은지 본다(`position_check.py verify`). 다르면 등록하지 않는다.
  - **⑨에서의 대조:** 검사할 때마다 등록 자리를 그때의 정답(매핑 적용)에서 다시 센 자리와 대조한다. 비교하는 것은 자리 id의 집합과, 자리마다 인쇄 칸(쪽, 인쇄 글자, 값)의 모임이다. 하나라도 다르면 그 호출은 공식 판정 불가다. 예를 들어 자리가 빠졌거나, 정답에 없는 자리가 있거나, 칸이 다르면 그렇다. 인쇄 순서는 다시 셀 수 없으므로(PDF가 필요하다) ⑦ 관문으로 확인한다.
- **검사 (⑨, 저장 보고서마다):** 채점기와 같은 방식으로 짝지은 제품 재무제표에서, 그 계정명이고 값이 있는 행을 보고서 순서대로 모은다.
  - **행 수가 인쇄 행 수와 같으면** k번째 행을 k번째 인쇄 행과 비교한다.
    - k번째 행의 값이 k번째 인쇄 값과 다르면 틀린 칸이다. 인쇄가 "-"인 행에 값이 있는 경우도 포함한다. 값이 없는 행은 빠짐이고 채점기가 센다(S2).
    - 채점기가 그 자리에서 이미 센 칸(표시 없는 값 틀림, "-" 칸에 값)이 있을 수 있다. 그래서 자리마다 더하는 수(`S1_position`)는 다음과 같다: max(0, 순서로 센 표시 없는 틀린 칸 − 채점기가 그 자리에서 센 표시 없는 칸).
    - 이렇게 하면 같은 칸을 두 번 세지 않고, 채점기의 S1보다 작아지지 않는다.
      - 예: 두 행에 같은 값 204가 들어가면, 채점기가 둘째 행을 값 틀림으로 이미 세므로 더하지 않는다.
      - 예: 두 행이 바뀌면, 채점기는 둘 다 맞음으로 세므로 둘을 더한다.
  - **행 수가 다르면**(행이 빠짐, 나뉨, 더해짐) 순서로 짝지을 수 없다. 다음 둘이 모두 맞으면 사람이 판정한다(`needs_verdict`). 아니면 바뀔 값이 없다.
    - 그 자리의 인쇄 값이 그 재무제표의 같은 계정명·기간 칸에 하나라도 있다.
    - 인쇄 행끼리 값이 다르다.
  - 판정 파일은 4.5와 같은 형식에 표시 없이 위치가 틀린 칸 수(`wrong_unmarked`)를 더한다.
    - `wrong`에는 이 수를 **반드시** 0 이상의 정수로 적는다(틀린 칸이 모두 표시돼 있으면 0). 빠지면 거부한다(재검토 2번: 빠진 수를 0으로 읽어 `met`이 되던 경로). `ok`에는 쓰지 않거나 0만 쓴다.
    - 이 수는 **채점기가 "맞음"으로 센 칸** 가운데, 다른 인쇄 행의 자리에 있고 표시가 없는 칸만 센다. 채점기가 틀림으로 센 칸은 이미 S1에 있고, 정답 밖의 칸은 4.5에서 판정한다.
    - 검사 결과가 행마다 채점기의 결과를 보여 준다. 그런 칸의 수보다 큰 값은 거부한다.

    검사기는 다음도 거부한다.
    - 다른 보고서의 해시
    - 판정자 없음
    - 판정할 필요가 없는 자리
    - 정해진 형식이 아닌 값: 객체가 아닌 판정, 근거 없음, 정수가 아닌 수
    - 정해진 모양이 아닌 파일. 판정 파일은 **있으면** 객체다. 있는지는 파일 경로로 정한다. 내용이 `null`인 파일도 파일이며 거부한다(9차 1번).
    - `verdicts`가 객체가 아닌 파일. 비어 있어도 `{}`여야 하고, `[]`·`""`·`false`·`null`은 거부한다(8차 2번).
    - 판정이 하나도 없는 파일이라도 그 보고서의 해시와 판정자를 적어야 한다. 다른 보고서의 빈 파일도 거부한다(9차 3번).
    - 정답 밖 판정 파일(4.5)도 공식 집계가 고정 채점기 앞에서 위와 같은 검사를 한다.

    공식 집계는 거부된 파일이 있는 호출을 공식 판정 불가로 둔다. 판정 폴더에서 이번 집계가 읽지 않은 파일(이름이 틀렸거나 다른 방식의 파일)은 목록으로 알린다(9차 2번).
  - 판정을 기다리는 자리가 하나라도 있으면 `position_ready`가 아니다.
- **이 검사는 S1을 늘리거나 공식 판정을 막을 수만 있다.** 채점기가 낸 수를 줄이지 않는다. 고정 채점기만의 S1과 `S1_position`을 나눠서도 보고한다.
- **한계:**
  - 위치를 보고서의 행 순서로 판단한다. 제품이 인쇄 순서와 다르게 행을 내면 맞는 값도 위치 틀림이 될 수 있다(제품에 불리한 오차). 개발 문서 5개의 저장 보고서 10개(규칙·AI)에서는 62곳 모두 순서가 맞았다.
  - 서로 다른 계정명 사이에서 값이 바뀐 것은 이 검사의 대상이 아니다. 채점기가 값 틀림이나 계정명 틀림으로 센다.
  - 자리는 정답에서 같은 계정명인 행만이다. 정답 계정명이 다르게 다듬어진 행은 대상이 아니다.
  - 자리를 만든 시점은 정답을 만든 뒤, 제품을 평가 문서에 돌리기 전이다(10절).

  | 사람 확인 완료 | 매핑표가 `confirmed`이고(결정할 항목이 없는 문서도 매핑표를 확정한다), 정답 밖의 표시 없는 칸이 모두 판정됐고, 위치 검사에서 사람이 정할 자리가 모두 판정됐다(`position_ready`, 7판) |
  | 공식 판정 가능 | 사람 확인 완료이고, `unscorable` 결정이 없고, 보고서의 원본 해시가 정답의 원본(스캔이면 스캔 파일) 해시와 같고(1.3의 뜻으로), 저장된 보고서를 채점했다(`official_ready`) |

- 공식 판정은 S1, L1, S2로 하고, **공식 판정 가능**일 때만 낸다. 묶음(3.1, 3.3)마다, 읽기 방식마다 따로 판정한다. **제품 판정은 AI 방식이다.**
- **공식 집계 (7판, `eval/d4_eval/official_d4.py`):** 실행 폴더의 저장 보고서마다 다음을 한다.
  - 고정 채점기(`score`)로 채점하고 위치 검사를 한다.
  - 공식 S1은 채점기의 S1 + `S1_position`이다.
  - 호출의 공식 판정 가능(`official_ready`)은 다음이 모두 참일 때다.
    - 채점기의 `official_ready`
    - `position_ready`
    - **실행 기록상 성공한 호출**(재검토 1번, 8차 1번). 먼저 실행 기록 전체가 스스로 맞아야 한다. 하나라도 어긋나면 그 폴더의 어느 호출도 공식이 아니다.
      - `run.json`이 끝까지 쓰였다(`finished_at`).
      - 통과한 사전 점검을 적었다.
      - 등록된 문서 목록으로 돌았다(`documents_sha256`).
      - 방식이 등록된 순서(규칙 → AI)로 한 번씩이다.
      - `run_log.jsonl`이 계획된 호출을 정확히 한 번씩, 계획된 순서로(번호 1, 2, …) 담고, 종료값이 모두 정수다.
      - `failed`가 로그에서 종료값이 0이 아닌 호출과 정확히 같다(이름과 종료값, 한 번씩).
      - 호출 수와 성공 수가 맞는다.

      그다음 그 호출의 종료값이 0이어야 한다.
    - 채점기는 보고서를 저장한 **뒤** 채점하므로, 실패한 호출이 보고서를 남길 수 있다. 그런 보고서는 공식 판정이 될 수 없다. 숫자는 잠정치로만 보인다.
  - 한 묶음의 판정(`met`·`not met`)은 그 묶음의 **모든 호출**(방식마다 3.1은 10개, 3.3은 30개)이 공식 판정 가능일 때만 낸다.
  - 하나라도 아니면 그 묶음은 "공식 판정 불가"이고 호출마다 이유를 적는다. 이유는 보고서 없음, 판정이 남음, 원본 불일치, `unscorable` 등이다.
  - 문서를 빼고 나머지로 판정하지 않는다.
  - 집계는 실행 폴더 하나씩 한다. 한 방식을 새 폴더에서 다시 돌렸으면 그 방식은 새 폴더의 모든 호출로만 판정한다(`--readers`). 두 폴더의 호출을 섞지 않는다. 보고서에 방식마다 쓴 폴더, 점검 로그, 커밋을 적는다(재검토 6번).
- 기준을 충족해도 "틀린 숫자가 없다"고 일반화하지 않는다. 함께 적을 것: 칸 수, 문서 수, 매핑표에서 사람이 정한 항목 수, 4.5에서 사람이 판정한 칸 수.

## 6. 사람 검토

- 대상: 매핑표(4.2, 실행 전), 정답에 없는 칸(4.5, 실행 뒤).
- Claude가 1차로 판정하고 근거(쪽, 인쇄된 글자, 계산)를 적는다. 사용자가 확인한다. 판정을 바꾸면 변경 이력을 남긴다. 제3의 독립 검토자는 없다(한계로 보고한다).
- 매핑표는 실행 결과를 보기 전에 확정한다. 실행 결과를 본 뒤 매핑표를 바꾸면 1절의 두 결과 보고를 따른다.

## 7. 실행과 장애

- 실행 명령은 ⑦에서 고정한다. 문서 목록은 평가 도구의 입력 파일로 뺀다. 같은 데이터 폴더를 두 서버가 쓰지 않는다(서버가 폴더를 잠근다).
- 제품 출력은 문서·방식마다 보고서 파일 하나로 저장한다(4.3). 채점은 저장된 파일로만 한다.
- 모델 서버는 `OLLAMA_NO_CLOUD=1 OLLAMA_HOST=127.0.0.1:11434 ollama serve`로만 띄운다(다른 OLLAMA_ 설정 없이). 띄운 명령을 실행 기록에 적는다.
- 모델 서버 장애(연결 실패 등, 출력 한도 초과가 아닌 오류)가 나면 그 방식 전체를 새 폴더에서 다시 돌리고 두 기록을 모두 남긴다.
- 출력 한도 초과(띠 하나를 못 읽음)는 장애가 아니라 제품 동작이다. 그대로 잰다.
- 실행기는 호출마다 종료값을 기록한다(7판, Codex 7차 2번).
  - 실패한 호출(종료값이 0이 아님)의 이름과 수를 `run.json`에 적는다.
  - 실패가 하나라도 있으면 실행기는 종료값 1로 끝난다. 나머지 호출은 계속 실행한다.
  - 종료값 0은 모든 호출이 끝까지 돌았다는 뜻일 뿐이고, 공식 판정 가능과 다르다.
- **실패한 호출** (7판, 재검토 1번)은 보고서가 남아도 공식 판정이 될 수 없고, 그 묶음은 `met`이 될 수 없다.
  - 모델 서버 장애이면 위대로 그 방식 전체를 새 폴더에서 다시 돌린다.
  - 제품 자체의 실패(장애가 아닌 오류)는 다시 돌려 덮지 않는다. 그 묶음은 "공식 판정 불가(제품 실패)"로 보고하고, 실패한 문서와 원인을 결과로 적는다.
  - 실행이 중간에 끊겨 `run.json`이 끝까지 쓰이지 않은 폴더는 공식 결과가 될 수 없다.

## 8. 공개와 데이터

- 평가 문서 PDF는 커밋하지 않는다. 회사, 문서 이름, 접수번호, SHA-256, 쪽 수만 남긴다.
- 기록에는 공시된 숫자와 계정명만 남긴다. 사진 PDF는 사용자가 개인정보가 없다고 확인한 것만 쓴다.
- OpenDART 응답 원본은 캐시(추적하지 않음)에만 둔다.

## 9. 위험

- **회사 선정 편향:** 금융업 제외와 "글자 층 없음" 제외가 결과를 좋게 만들 수 있다. 제외 목록과 수를 보고한다.
- **정답 생성기의 오류:** 정답 생성기도 PDF 글자 층을 읽는 코드다.
  - 제품 코드를 가져다 쓰지 않지만 같은 글자 층을 보므로, 글자 층 자체의 잘못(예: 로마 숫자를 "l"로 담은 것)은 둘 다 같이 받을 수 있다. 매핑표 검토와 OpenDART 대조로 줄인다.
  - 정답 생성기가 찾지 못한 재무제표는 정답 없이 사람 판정(4.5)으로 넘어간다. 그 수를 보고한다.
- 정답 생성기와 채점기는 개발 문서로 다듬었다. 새 문서에서 정답 생성기의 결함이 나오면(4.5의 `ok` 판정) 따로 보고한다.
- 사람 검토자가 한 명(사용자)이고 1차 판정을 Claude가 한다.
- 모델 비결정성: 온도 0이어도 결과가 달라질 수 있다. 한 번만 실행하고, 반복 측정은 10절에서 정한다.
- 가리킴 규칙(4.4)은 엄격해서, 사람이 보면 찾을 수 있는 보고도 S2로 셀 수 있다. 제품에 불리한 쪽의 오차다.
- AI 방식은 그 쪽에 같은 기간의 금액이 없을 때, 한두 자리 숫자(주석 번호일 수도 있다)도 "AI가 읽지 않았다"로 보고한다. 거짓 경고가 늘 수 있다(5차 9번). 그런 경고는 정답 칸을 가리키지 않으므로 S2를 줄이지 않는다.
- 제품의 소계 층 규칙(4차 9번 반영)은 항목 기호와 들여쓰기가 함께 있을 때만 층을 믿는다. "1."과 "가."를 같은 x에 인쇄하는 문서는 맞는 칸도 "확인 필요"가 된다(A1이 커진다).
