## 1. 순서 (D4 1절과 같음)

① 계약 → ② Codex 검토(필수) → ③ 사용자 결정 → ④ 고정(F, 태그 `d5-frozen` push) → ⑤ 후보 판정과 문서 준비 → ⑥ 정답과 매핑표 확정 → 등록 전 Codex 검토(필수) → ⑦ 등록(R, 태그 `d5-registered` push) → ⑧ 실행 → ⑨ 판정·보고(결과 Codex 검토 뒤 공개)

- **④ 전에는 D5 후보의 PDF를 받거나 열지 않는다.** D5 포함 회사의 OpenDART 재무제표도 받지 않는다. 20~30번의 기업개황·공시 목록은 D4 때 받아 둔 것이라 예외다(5절).

## 2. 파일과 명령

| 무엇 | 경로 |
|---|---|
| 공유 도구 (T로 고정) | `eval/d4_gold.py`, `eval/d4_score.py`, `eval/d4_candidates.py`, `eval/d4_preflight.py`, `eval/d4_scan.py`, `eval/d4_eval/run_d4.py`, `eval/d4_eval/position_check.py`, `eval/d4_eval/official_d4.py`, `eval/d4_eval/document_list.py` |
| 평가 프로필 | `eval/d4_eval/document_list.py`의 `PROFILES["d5"]`: 아래 경로들, 태그 `d5-registered`, 공유 도구 9개, P `180e621` |
| 고정 기록 | `eval/freeze_d5.json` (`d4_preflight.py freeze --profile d5 --documents-count N`; 프로필과 N을 담는다) |
| 제외 목록 | `eval/d5_excluded.json` = D4 제외 9곳 + D4 포함 10곳의 고유번호 |
| 후보 기록 | `eval/d5_candidates/` (5절) |
| 문서 목록 | `eval/d5_eval/documents.json` (`expected_documents` 필수, 고정 기록의 N과 같아야 함) |
| 정답·매핑표 | `eval/d5_eval/gold/` |
| 스캔 대응표 | `eval/d5_eval/scans/` |
| 위치 검사 등록 자리 | `eval/d5_eval/duplicate_places.json` |
| 등록 기록 | `eval/register_d5.json` (`register --profile d5`; 프로필 이름과 태그를 담는다) |
| 절차서 | `docs/D5_RUN_PROCEDURE.ko.md` |
| 결과 | `eval/d5_eval/results/<날짜>/` |

- **명령 (④·⑦·⑧은 정해져 있다; 폴더 이름만 절차서에서 정한다):**
  - ④: `python eval/d4_preflight.py freeze --profile d5 --documents-count N --product 180e621 --tools T --out eval/freeze_d5.json`
    - N은 ③에서 사용자가 정한 회사 수다. 문서 목록이 생기기 전에 고정 기록에 들어간다.
    - P가 프로필의 `180e621`이 아니면 고정하지 않는다. T의 도구는 프로필의 9개다(명령에서 고를 수 없다).
    - 고정 기록만 담은 커밋 F를 만들고, F에 주석 태그 `d5-frozen`을 달아 `origin`에 push한다(push는 사용자 승인). **이 push 전에는 D5 후보의 PDF를 받거나 열지 않는다.**
    - 등록(R)만으로는 등록한 N이 F에서 정한 N인지 보일 수 없다. F와 R 사이에 N과 목록을 함께 줄여도 R 태그는 그 줄인 값을 잠글 뿐이다(Codex 3차 1번). 그래서 F를 저장소 밖(원격 태그)에 따로 고정한다.
  - ⑦: `python eval/d4_preflight.py register --profile d5 --freeze eval/freeze_d5.json --paths <등록 파일 전부> --out eval/register_d5.json --remote origin`
    - 등록 파일에는 문서 목록, 위치 검사 등록 자리, 목록이 가리키는 정답·매핑표·대응표 전부가 들어가야 한다. 빠지면 등록하지 않는다.
    - 문서 목록은 고정 기록의 N으로 검사한다.
    - 로컬과 `origin`의 `d5-frozen`이 같은 커밋 F를 가리켜야 하고, HEAD의 고정 기록이 F의 것과 같은 객체여야 한다. 등록 기록에 F와 그 객체를 적는다.
    - **등록 시점의 HEAD는 F의 자손이어야 한다.** F 옆의 가지에서 등록하지 않는다(Codex 4차 1번).
    - 등록 뒤에는 등록 기록 하나만 더한 커밋을 R로 만든다. R의 부모는 등록 시점의 HEAD(`based_on`) 하나뿐이다. 병합 커밋은 R이 될 수 없다.
    - 고정 기록과 등록 기록은 링크가 아닌 일반 파일이어야 한다(Codex 3차 2번).
  - ⑧: `python eval/d4_preflight.py check --profile d5 --freeze eval/freeze_d5.json --register eval/register_d5.json --registered d5-registered --remote origin --log <실행 폴더>.preflight.json`
    - 점검은 다음을 확인한다.
      - 고정 기록의 프로필
      - 등록 기록의 프로필·태그·고정 기록 경로, `--registered`가 태그인지
      - 등록 기록의 F가 로컬 `d5-frozen`이고 HEAD의 조상이며, `origin`의 `d5-frozen`도 F를 가리키는지
      - 고정 기록이 F의 것과 같은 객체인지
      - 고정·등록 기록이 HEAD에서 일반 파일인지
      - R의 부모가 등록 기록의 `based_on` 하나뿐이고, 둘 사이에 바뀐 파일이 등록 기록 하나뿐인지
      - F가 `based_on`의 조상인지, 등록 파일들이 `based_on`에서도 기록된 객체인지
  - ⑧ 실행: `python eval/d4_eval/run_d4.py --pdf-dir <D5 PDF 폴더> --scan-dir <D5 스캔 폴더> --out <실행 폴더> --documents eval/d5_eval/documents.json --preflight <실행 폴더>.preflight.json`
    - 실행기는 점검 로그의 프로필이 d5인지 확인한다(프로필이 없는 로그는 D4의 것이다).
  - ⑨의 정확한 명령(`official_d4.py --documents eval/d5_eval/documents.json --places eval/d5_eval/duplicate_places.json`)은 절차서에 적는다. 위치 검사는 공식 집계가 호출마다 `position_check.check`를 안에서 부르므로 따로 돌리지 않는다. 별도 `position_check.py check`는 문제를 살펴볼 때만 쓴다(Codex 등록 전 검토 5번).
  - 절차서는 ⑥ 전에 쓴다. 등록 전 Codex 검토를 받고, 같은 이름으로 등록한다.
- 실행기·위치 검사·공식 집계는 문서 목록을 먼저 검사한다(Codex D5 1번, 재검토 1·2번).
  - **문서 수 N은 목록 밖에서 온다.** D4 자기 목록이면 10이다. D5 목록이면 프로필 자리(`eval/d5_eval/documents.json`)에 있어야 하고, N은 고정 기록의 프로필에서 읽는다. 다른 자리의 목록은 거부한다.
  - 목록의 `expected_documents`와 문서 수가 N과 같아야 한다.
  - 순번·고유번호·key·PDF와 스캔의 해시가 겹치지 않아야 한다.
  - 스캔 세 조건이 모두 있어야 한다.
  - 정답·매핑표·대응표는 저장소 안의 상대 경로여야 하고, 가는 길에 심볼릭 링크가 없어야 한다. 문서 목록·고정 기록·등록 파일도 마찬가지다.
  - 공식 집계는 프로필의 위치 검사 등록 자리만 받는다. 묶음마다 호출이 정확히 N개(텍스트)·3N개(스캔)일 때만 판정한다. 일부 표본으로는 `met`이 나오지 않는다.

## 4. 평가 도구의 변경 (④ 전, Codex 검토 대상)

D4에서 새 문서가 드러낸 도구 결함 두 건과, D5에 필요한 경로·관문 변경이다.

1. **정답 생성기의 재무제표 찾기:**
   - 점 날짜 기간 줄을 기간 줄로 본다. 줄 전체가 기간 줄일 때만이다("제 62 기 2025.12.31 현재", "제 62 기 2025.01.01 부터 2025.12.31 까지").
   - 날짜가 든 설명문이나 행은 재무제표 시작도 아니고 버리지도 않는다(Codex D5 4번).
   - "2025년 12월 31일 현재" 형태의 규칙은 D4 그대로다.
   - 받지 않는 점 날짜 변형(같은 줄에 단위가 붙은 줄, 당기·전기 날짜가 한 줄에 있는 줄, 물결표 범위 "2025.01.01 ~ 2025.12.31")은 재무제표를 못 찾은 것(`statement_not_found`)으로 사람에게 넘어간다. 이 항목은 무시할 수 없고 재무제표 추가·같은 재무제표·채점 불가 중 하나로 정한다(Codex 재검토 확인). 넓혀 받는 것은 이 계약의 범위가 아니다.
2. **계정명 비교 (`label_key`):** 끝에 붙은 콜론을 빼고, 가운뎃점 ㆍ·・‧를 한 글자(ㆍ)로 본다. 정답 생성기와 채점기가 같은 방식으로 비교한다.
3. **경로와 관문:**
   - 실행기·위치 검사·공식 집계에 `--documents`·`--places`를 추가했다. 기본값은 D4다.
   - 문서 목록 검사(2절)를 추가했다.
   - 고정·등록·사전 점검에 `--profile`을 추가했다. 기본값은 D4다. D5 프로필이 경로·도구·P·태그·F 태그를 정한다.
   - D4의 동작과 기록 형식은 그대로다. 고정·등록 기록, 점검 로그, 공식 집계 JSON의 키가 D4 공식 기록과 같다. `expected_documents`는 D5 집계에만 들어간다(Codex 3차 3번).
- **확인 결과** (2026-10-20, D4 기록으로):
  - 1번(정답 생성기)은 코드 `09c0e4430f771ad35a9ccb57cb400516861f3a50`에서 확인했고, Codex 재검토가 같은 커밋에서 다시 확인했다. 그 뒤 정답 생성기와 채점기는 바뀌지 않았다.
  - 2번의 다시 집계는 재검토 수정 커밋 `0050149504c76fdf094d2c99e419c3492908cf9b`와 3차 수정 커밋 `be10b549c862f95826c0f4cd4fdfd57442a77f4a`의 도구로도 다시 했다. 결과는 아래와 같고, 두 번 모두 같았다.
  - 1번:
    - D4 문서 10개의 정답을 고친 생성기로 다시 만들었다(같은 PDF, 같은 OpenDART 캐시 `cache/d4`). DSR 말고 9개는 저장된 정답 파일과 **바이트 단위로 같다.**
    - DSR은 4개 재무제표를 맞는 쪽 범위와 단위로 찾았다. 만든 칸 211개는 D4에서 사람이 옮겨 적은 212칸과 같다. 비교 기준은 채점기의 계정명 정규화(`label_key`), 기간, 인쇄값이다. 원래 계정명 글자로는 6칸이 사람이 넣은 띄어쓰기만 다르다.
    - 남은 1칸(8쪽 이익잉여금, 금액이 두 줄로 끊김)은 사람이 정할 항목으로 넘어온다.
  - 2번: D4 공식 저장 보고서 80개와 확정 판정을 고친 채점기로 다시 집계했다.
    - 바뀐 것은 호출 3개의 10칸뿐이다. 모두 계정명 틀림에서 맞음으로 바뀌었다.
    - 정답 쪽 계정명은 바뀐 것이 없고, D4 등록 자리 66곳도 그대로다(`verify`).
    - 네 묶음의 판정은 모두 그대로다(미충족).
    - **D4 기록을 HEAD의 도구로 다시 집계한 숫자는 D4 공식 결과가 아니다.** 공식 결과는 R의 도구로 낸 것이다.

## 5. 평가 문서

- **텍스트 PDF:** D4의 모집단과 순서(`eval/d4_population.json`, `sha256("D4-2026|" + 고유번호)`)를 그대로 쓴다. **20번부터** D4 계약 3.2의 절차로 판정해, 포함이 9절 1번의 수가 되면 멈춘다. 멈춘다는 것은 그 뒤 후보의 입력 조회, 첨부 이름 기록, PDF 받기를 모두 하지 않는다는 뜻이다(실제로는 조회와 첨부 기록을 40번까지 했다: 11절 3번).
  - 계약을 확정한 뒤에는 고르는 규칙이 결정적이라 결과를 보고 회사를 바꿀 재량은 없다.

## 6. 정답 밖 칸의 판정 기준 (D4 4.5에 더함)

- 정답 밖의 표시 없는 칸은 엑셀에서 다음 넷이 **모두** 인쇄와 같게 읽히면 `ok`다. 하나라도 틀리거나 알 수 없으면 `wrong`이다.
  - **재무제표:** 그 칸이 든 시트가 정답의 특정 재무제표 id에 대응하는 인쇄 표다. 제목만 같은 것으로는 부족하다.
  - **계정명:** 채점기의 `label_key`로 같다.
  - **기간:** 인쇄된 그 열의 기간이다.
  - **금액:** 인쇄 금액이다.
- 판정 근거(note)에는 PDF 쪽, 인쇄 행, 기간 머리글, 인쇄 금액을 적는다.
- D4는 이 기준을 실행 뒤 Codex 결과 검토로 바로잡았다(D4 결과 보고서 6.1절). D5는 처음부터 이 기준으로 판정한다.
- 기준의 예(D4에서 판정한 것):
  - 세 열 재무상태표의 "전기초" 열에 든 인쇄값: ok
  - 손익 행이 재무상태표 시트에 든 것: wrong
  - 기간 머리글을 알 수 없는 열에 든 맞는 금액: wrong
  - 자본변동표의 행이 포괄손익계산서 시트에 든 것: wrong. 같은 포괄손익계산서에 같은 행·기간·값이 인쇄돼 있으면 ok

## 7. "제목 미확인 표"

- 제품은 제목을 읽지 못한 표를 "제목 미확인 표"로 따로 두고 모든 칸을 표시한다. 채점기는 이 표를 어느 정답 재무제표와도 짝짓지 않는다. 그래서 그 칸들은 정답 밖 칸(표시됨, 목록으로만 보고)이 되고, 정답 칸은 빠짐이 된다.
- 그 표의 문제 문장은 짝이 없는 정답 재무제표의 칸을 가리키지 않는다. 그래서 텍스트 PDF에서는 S2가 된다(제품에 불리한 쪽). 시험: `tests/test_d4_tools.py` `test_an_untitled_table_is_never_a_gold_statement_and_points_at_nothing`
- 보고서에 "제목 미확인 표"의 수와 칸 수를 따로 적는다.

## 8. 실행 (D4 7절에 더함)
