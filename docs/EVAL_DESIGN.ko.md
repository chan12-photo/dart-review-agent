# 평가 설계: 세 가지 방식과 채점 규칙 (로드맵 1-4)

- 상태: **초안 (2026-10-07, Claude).** 실제 모델 결과를 보기 전에 정한 규칙이다. 1-5 실행 전에 Codex 검토(로드맵 "Codex 이중 검증 계획"의 1-5 항목)에서 함께 검토받는다. 1-5 결과를 본 뒤 이 규칙을 바꾸면, 바꾼 이유와 전후 점수를 모두 보고한다.
- 정답: [`eval/dev_gold.json`](../eval/dev_gold.json) ([정답 규칙](GOLD_RULES.ko.md))
- 코드: `dart_review/answer.py`(답 형식), `dart_review/tools.py`(도구), `dart_review/llm.py`(로컬 모델), `eval/scoring.py`(채점), `eval/run_eval.py`(실행기)

## 1. 왜 세 가지로 나누는가

틀린 답이 나왔을 때 원인이 규칙인지, 모델의 답 작성인지, 모델의 질문 해석·도구 사용인지 구분하기 위해서다 (SCOPE 7절).

| 방식 | 모델이 받는 것 | 모델이 하는 일 | 재는 것 |
|---|---|---|---|
| ① 규칙만 | (모델 없음) | 정답의 해석(회사·기준·계정·기간)을 규칙 코드에 넣고, 정해진 문장 틀로 답을 만든다 | 도구·규칙과 채점기의 정확도. **목표 100%** |
| ② 근거 제공 | 질문 + **올바른 해석으로 실행한 도구 결과** | 도구 결과를 읽고 상태·숫자·기준을 맞게 전하는 답을 쓴다 | 완벽한 근거가 있을 때 모델의 답 작성 능력. **목표 80% 이상** |
| ③ 전체 흐름 | 질문 + 도구 | 질문을 해석해 도구를 부르고, 결과로 답을 쓴다 | 해석·도구 사용까지 포함한 실제 성능 (1차 버전) |

- **②의 근거는 "원본 행"이 아니라 "도구 결과"다.** SCOPE 7절은 "올바른 행을 모델에게 주고"라고 썼다. 하지만 이 제품에서 칸의 기간 해석은 규칙 코드가 하고, 모델은 도구 결과를 받는다. 그래서 ②는 ③과 같은 형식의 도구 결과를 주고, ③과의 차이를 "해석과 도구 사용의 몫"으로 본다. 원본 행 해석은 규칙의 몫이며 ①과 단위 테스트가 잰다.
- **②의 되묻기 질문(dev12):** 두 후보(영업이익, 당기순이익)의 도구 결과를 **모두** 준다. 근거가 다 있어도 하나를 골라 답하지 않고 되묻는지 본다.
- **② 이후에 ③을 해석한다.** ②가 낮으면 모델의 답 작성 자체가 병목이므로, ③의 실패를 해석이나 도구 사용 탓으로 돌리지 않는다.

## 2. 답 형식

모델은 아래 JSON 하나로 답한다(Ollama의 구조화 출력). 자유 문장만으로는 숫자와 기준을 안정적으로 채점할 수 없기 때문이다.

| 칸 | 내용 |
|---|---|
| `status` | `비교 가능` / `비교 불가` / `데이터 없음` / `확인 필요` / `나란히 표시` / `되묻기` |
| `company` | 회사 이름 |
| `account` | 계정 키 (`revenue` 등) 또는 null |
| `values` | 답에 쓴 값의 목록: `basis`(연결/별도), `period`(`start`, `end`; 시점 값은 `start`가 null), `amount`(원 단위 정수) |
| `change`, `change_pct` | 변화량(원), 변화율(소수 둘째 자리 문자열). 없으면 null |
| `answer` | 사용자에게 보여 줄 한국어 답 |
| `clarifying_question` | 되물을 때의 질문. 아니면 null |

- `나란히 표시`는 연결·별도를 함께 묻는 질문(dev05)의 상태다. 이때 정답 파일의 `status`(`비교 불가`)는 "두 기준을 시간 변화처럼 비교할 수 없다"는 규칙의 판정이고, 답의 상태는 `나란히 표시`가 맞다.
- 형식이 맞지 않는 답(JSON이 아님, 필수 칸 없음, 허용되지 않은 값)은 **형식 오류**로 세고, 그 문항은 실패다. 고쳐서 다시 묻지 않는다.

## 3. 문항별 채점

| 항목 | 맞는 조건 | 적용 문항 |
|---|---|---|
| **상태** | `status`가 기대 상태와 같다 | 전부 |
| **결정** | 답한다 / 나란히 보여 준다 / 거절한다 / 되묻는다 중 맞는 것을 골랐다. 상태보다 거친 기준이라, "확인 필요를 비교 가능으로" 같은 상태 오류와 "답해야 할 것을 거절" 같은 결정 오류를 나눠 본다 | 전부 |
| **숫자 일치** | 정답의 각 값이 같은 기준·기간으로 `values`에 있고 금액이 원 단위로 같다. `change`가 같다. `change_pct`가 같거나 둘 다 null이다 | 정답에 숫자가 있는 문항 |
| **기준** | 회사·계정이 맞고, `values`의 기준(연결/별도)과 기간(시작·끝 날짜)이 정답과 같다. 정답에 없는 기준·기간의 값을 섞지 않았다 | 숫자가 있는 문항 |
| **거절·되묻기** | 거절 문항: 상태가 맞고 `values`, `change`, `change_pct`가 비어 있다. 되묻기 문항: 상태가 `되묻기`이고 질문에 두 후보 계정 이름이 모두 있으며 숫자를 내놓지 않았다 | 거절·되묻기 문항 |
| **부호 표현** | 부호가 바뀌어 변화율이 없는 문항은 답에 정답의 표현(흑자 전환, 적자 전환, 적자 축소, 적자 확대)이 있다(띄어쓰기 무시) | dev09 |
| **근거 없는 숫자** | 4절. 0개여야 한다 | 전부 |
| **표현 경고** | 문항별 금지 표현(예: dev05의 "증가")이 나오면 기록만 한다. 부정문("증가율은 계산하지 않는다") 같은 오탐이 있어 자동 실패로 쓰지 않고, 1-5 보고서에서 사람이 확인한다 | 지정 문항 |

- 회사 이름은 띄어쓰기와 "(주)", "주식회사"를 무시하고 비교한다.
- `나란히 표시` 문항은 `change`, `change_pct`가 null이어야 숫자 일치로 본다(연결과 별도의 차이는 시간 변화가 아니다). 차이는 문장으로만 말한다.
- 시점 값은 `start`가 null이어야 한다. 시작 날짜를 끝 날짜와 같게 쓰면 기준 오류다.

**문항 통과(엄격):** 형식 오류 없음, 상태·결정 맞음, 해당하면 숫자 일치·기준·거절·되묻기·부호 표현 모두 맞음, 근거 없는 숫자 0개, ③은 예산 안에서 끝남.

## 4. 근거 없는 숫자

**원칙: 답에 나온 숫자는 모델이 본 도구 결과나 질문에서 와야 한다** (SCOPE 3절 "모든 숫자는 도구 결과에서만").

- **허용 집합:** 모델이 그 문항에서 본 도구 결과 JSON에 있는 모든 숫자(금액, 변화량, 변화율, 차이, 접수번호, 기간의 연·월·일)와 질문에 나온 숫자.
  - ②는 제공한 도구 결과, ③은 실행 중 실제로 반환된 도구 결과다. 정답 파일이 아니라 **모델이 본 것**을 기준으로 한다. 그래서 ③에서 엉뚱한 도구 결과를 받아 그 숫자를 옮기면 근거 없는 숫자는 아니지만 숫자 일치에서 틀린다.
- **검사 대상:** `answer` 문장과 구조화 칸(`values`, `change`, `change_pct`)의 모든 숫자.
- **숫자의 종류별 판정:**

| 종류 | 예 | 근거가 있다고 보는 조건 |
|---|---|---|
| 금액(조·억·만·원 단위) | `333조 6,059억 원`, `333.6조`, `2,431,791,719,869원` | 허용 금액 가운데 하나와 절댓값이 **표시한 마지막 자리 단위 안**에서 같다. 예: `333.6조`는 0.1조 단위라 333,605,938,000,000과 맞다. 반올림과 버림을 모두 인정하고, 부호는 "감소" 같은 말로 쓸 수 있어 절댓값으로 본다 |
| 비율 | `10.88%`, `10.9%`, `-4.48%` | 허용 변화율과 절댓값이 표시한 자리 단위 안에서 같다. `%p`(퍼센트포인트)도 같은 규칙이다 |
| 연도 | `2025년`, `2025-09-30` | 허용 집합의 연도 |
| 달력 숫자 | `9월 30일`, `3분기`, `1~9월`, `12개월` | 월 1~12, 일 1~31, 분기 1~4, 개월 1~12면 허용. 기간이 맞는지는 "기준" 항목에서 따로 본다 |
| 접수번호 | `20251114002447` | 허용 집합에 있는 번호 |
| 단위 없는 큰 수 | `333,605,938,000,000` | 1,000 이상이거나 쉼표가 있으면 원 단위 금액으로 보고 정확히 같아야 한다 |
| 단위 없는 작은 정수 | `2개`, `두 보고서` | 검사하지 않는다(개수 표현) |

- **모델이 스스로 계산한 숫자는 근거 없는 숫자다.** 예: 별도/연결 비율 71.4%, 도구가 주지 않은 분기 차감 값. 도구 결과에 없는 숫자를 만들지 않는 것이 이 제품의 보장이다(SCOPE 8절).
- 이 판정은 2-3의 "출력 전 숫자 검증"과 같은 함수를 쓰도록 만든다. 평가와 제품의 기준을 하나로 둔다.

## 5. 지표 (방식별)

- 문항 통과율(엄격), 상태 정확도, 결정 정확도, 숫자 일치율(숫자 문항), 기준 정확도(숫자 문항), 거절·되묻기 정확도(해당 문항)
- 근거 없는 숫자: 전체 개수와 1개 이상 나온 문항 수
- 형식 오류 수, 표현 경고 수
- 모델 요청 수, 도구 호출 수(모델이 부른 것만; ①②에서 실행기가 미리 실행한 도구는 세지 않는다), 지연 시간(문항별 합계, 전체 중앙값)
- ③만: 도구 인자 정확도(첫 도구 호출의 회사·기준·계정·기간이 정답 해석과 같은가), 예산 초과 문항 수

**SCOPE 10절 기준과의 대응:** ① 통과율 100%, ② 통과율 80% 이상, 모든 방식에서 근거 없는 숫자 0개. 판정은 1-5 보고서에서 한다.

## 6. 실행 조건

- 모델: 로컬 Ollama(`127.0.0.1:11434`)만 쓴다. 다른 주소, 프록시, 리다이렉트를 허용하지 않는다.
- 요청마다 모델 이름, digest, Ollama 버전, 옵션, 토큰 수, 지연 시간을 기록한다. `truncate=false`로 Ollama가 긴 대화를 몰래 잘라내지 못하게 한다.
- gpt-oss는 `think: false`를 보내도 생각 과정(`thinking`)을 내놓는다(local-agent-lab 모델 확인에서 관찰). 생각 과정은 기록만 하고 채점하지 않는다. 숫자 검사는 사용자에게 보이는 `answer`와 구조화 칸에만 적용한다.
- ③의 예산: 문항당 모델 요청 5회(최종 답 작성 포함), 도구 호출 3회. 넘으면 그 문항은 실패로 기록한다.
- 재시도 없음: 한 문항은 한 번 실행한다. 결과가 마음에 들지 않는다고 다시 돌려 고르지 않는다.
- 실행 기록: 문항마다 보낸 메시지, 모델 응답, 도구 호출과 결과, 채점 결과를 JSON으로 남긴다.

## 7. 알려진 한계

- 금지 표현 검사는 단순 문자열 비교라 오탐과 미탐이 있다. 그래서 자동 실패로 쓰지 않는다.
- "확인 필요"의 이유를 단정적으로 쓰는지(dev08), "왜"에 대한 해석을 사실처럼 쓰는지(dev05)는 자동으로 판정하지 않는다. 1-5에서 사람이 답을 읽고 따로 기록한다.
- 숫자 추출은 한국어 금액 표기의 흔한 형태만 다룬다. 처리하지 못한 표기(예: 단위 없는 소수 `10.88`)는 "판정 불가 숫자"로 따로 기록하고, **보수적으로 근거 없는 숫자로 센다.** 채점기의 한계 때문에 모델이 불리해질 수 있으므로 1-5 보고서에서 사람이 다시 확인한다.
- 개발용 13문항은 통계적으로 작다. 1-5 판정은 "가능성 확인"이고 성능 주장이 아니다.
