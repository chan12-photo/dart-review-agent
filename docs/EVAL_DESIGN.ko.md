# 평가 설계: 세 가지 방식과 채점 규칙 (로드맵 1-4)

- 상태: **v2 (2026-10-07, Claude).** v1에 대한 Codex 검토([결과](reviews/1-5_codex_result.ko.md), [반영 내역](reviews/1-5_codex_response.ko.md))를 반영했다. **1-5 모델 실행 전에 고정한다.** 실행 뒤에 바꾸면 바꾼 이유와 바꾸기 전후 점수를 모두 보고한다.
- 정답: [`eval/dev_gold.json`](../eval/dev_gold.json) ([정답 규칙](GOLD_RULES.ko.md)) / 본문 검토 기준: [`eval/HUMAN_REVIEW.ko.md`](../eval/HUMAN_REVIEW.ko.md)
- 코드: `dart_review/answer.py`(답 형식), `dart_review/tools.py`(도구), `dart_review/numbers.py`(숫자 근거), `dart_review/llm.py`(로컬 모델), `dart_review/prompts.py`, `eval/scoring.py`(자동 채점), `eval/run_eval.py`(실행기), `eval/finalize.py`(본문 검토와 최종 점수)

## 1. 왜 세 가지로 나누는가

틀린 답이 나왔을 때 원인이 규칙인지, 모델의 답 작성인지, 모델의 질문 해석·도구 사용인지 구분하기 위해서다 (SCOPE 7절).

| 방식 | 모델이 받는 것 | 모델이 하는 일 | 재는 것 |
|---|---|---|---|
| ① 규칙만 | (모델 없음) | 정답의 해석(회사·기준·계정·기간)을 규칙 코드에 넣고, 정해진 문장 틀로 답을 만든다 | 도구·규칙·채점기가 서로 맞는지. **목표 100%**. 질문 문장을 해석하는 자연어 기준선(로드맵 2-2)이 **아니다** |
| ② 근거 제공 | 질문 + **올바른 해석으로 실행한 도구 결과** | 도구 결과를 읽고 상태·숫자·기준을 맞게 전하는 답을 쓴다 | 올바른 도구 결과가 있을 때의 답 작성. **목표 80% 이상(13문항 중 11개)** |
| ③ 전체 흐름 | 질문 + 도구 | 질문을 해석해 도구를 부르고, 결과로 답을 쓴다 | 해석·도구 사용을 포함한 전체 흐름 (1차 버전) |

- **②의 근거는 원본 행이 아니라 도구 결과다.** 칸의 기간 해석은 규칙 코드의 몫이고, 모델은 도구 결과를 받는다. 그래서 ②는 원본 행에서 재무 의미를 찾는 능력이 아니라, 올바른 도구 결과를 받았을 때의 답 작성을 잰다.
- **②와 ③의 차이를 "해석·도구 사용의 순수한 손실"로 계산하지 않는다.** ③은 도구 대화, 오류 회복, 예산, 더 긴 문맥을 거치므로 경로 자체가 다르다. 차이는 "도구 사용을 포함한 전체 흐름의 추가 어려움"으로 보고, 원인은 문항별 실제 도구 인자로 나눠 본다.
- **②의 되묻기 질문(dev12):** 두 후보(영업이익, 당기순이익)의 도구 결과를 모두 준다. 근거가 다 있어도 하나를 골라 답하지 않는지를 본다. 후보를 스스로 찾는 능력은 재지 않는다.

## 2. 답 형식

모델은 아래 JSON 하나로 답한다(Ollama의 구조화 출력). `values`의 각 항목은 **평평한 구조**다(`period` 객체로 감싸지 않는다).

| 칸 | 내용 |
|---|---|
| `status` | `비교 가능` / `비교 불가` / `데이터 없음` / `확인 필요` / `나란히 표시` / `되묻기` |
| `company` | 회사 이름 |
| `account` | 계정 키(`revenue` 등) 또는 null |
| `values` | 답에 쓴 값의 목록. 각 항목: `basis`(연결/별도), `start`(시점 값은 null), `end`, `amount`(원 단위 정수) |
| `change`, `change_pct` | 변화량(원), 변화율(`-4.48`처럼 소수 둘째 자리 문자열). 없으면 null |
| `answer` | 사용자에게 보여 줄 한국어 답 |
| `clarifying_question` | 되물을 때의 질문. 아니면 null |

- `나란히 표시`는 연결·별도를 함께 묻는 질문(dev05)의 상태다. 정답 파일의 `status`(`비교 불가`)는 "두 기준을 시간 변화처럼 비교할 수 없다"는 규칙의 판정이다.
- 형식이 맞지 않는 답(JSON이 아님, 필수 칸 없음, 허용되지 않은 값이나 타입)은 **형식 오류**다. 고쳐서 다시 묻지 않는다. 스키마(`ANSWER_SCHEMA`)와 서버 쪽 검증(`parse_answer`)은 같은 규칙을 쓴다. 스키마 출력이 성공했다고 서버 검증까지 통과한 것으로 보지 않는다.

## 3. 자동 채점 (문항별)

| 항목 | 맞는 조건 | 적용 문항 |
|---|---|---|
| **상태** | `status`가 기대 상태와 같다 | 전부 |
| **결정** | 답한다 / 나란히 보여 준다 / 거절한다 / 되묻는다 중 맞는 것을 골랐다 | 전부 |
| **숫자 일치** | 정답의 각 값이 같은 기준·기간으로 `values`에 있고 금액이 원 단위로 같다. `change`가 같다. `change_pct`가 같거나 둘 다 null이다. `나란히 표시`는 `change`, `change_pct`가 null이어야 한다 | 정답에 값이 있는 문항(10개) |
| **기준** | 회사가 맞다(띄어쓰기, "(주)", "주식회사" 무시). 숫자 문항은 계정과 `values`의 기준·기간(시작·끝 날짜)이 정답과 정확히 같고 다른 값을 섞지 않았다. 거절 문항은 회사와 계정. 되묻기 문항은 회사가 맞고 계정을 고르지 않았다(null) | 전부(13개) |
| **거절·되묻기** | 거절: 상태가 맞고 `values`, `change`, `change_pct`가 비어 있다. 되묻기: 상태가 `되묻기`, 질문에 두 후보의 이름이 모두 있고(당기순이익은 "순이익"도 인정), 본문과 질문에 금액·비율을 내놓지 않았고, `values` 등이 비어 있다 | 거절·되묻기 문항(3개) |
| **부호 표현** | 정답의 표현(흑자 전환 등)이 본문에 있고, 바로 뒤에 "않/아니/못"으로 부정되지 않았다(띄어쓰기 무시) | dev09 |
| **근거 없는 숫자** | 4절. 0개여야 한다 | 전부 |
| **표현 경고** | 문항별 금지 표현(dev05의 "증가" 등)이 나오면 기록만 한다. 판정은 본문 검토에서 한다 | dev05 |

- **적용 여부는 정답이 정한다.** 형식 오류인 답은 적용되는 모든 항목에서 실패로 센다. 실패한 답 때문에 분모가 줄지 않는다.
- **자동 통과(`automatic_passed`):** 형식 오류·모델 오류·평가기 오류·예산 초과가 없고, 위의 적용 항목이 모두 맞고, 근거 없는 숫자가 0개.
- **자동 채점이 보지 않는 것:** 본문이 기간·방향·이유를 맞게 말하는지(예: 1~9월 누적을 "7~9월"이라고 쓰기, 거절 이유를 "서버 장애"로 바꾸기, 원인 단정). 이것은 5절의 본문 검토가 본다.

## 4. 근거 없는 숫자

**원칙:** 답에 나온 숫자는 그 문항에서 모델이 받은 **성공한 도구 결과**에서 와야 한다(SCOPE 3절).

- **근거가 되는 것:** 성공한 도구 결과 JSON의 숫자(금액, 변화량, 변화율, 차이, 접수번호, 날짜의 연도). 규칙 코드가 만든 이유·메모 문장 속 숫자(예: 재작성 전후 금액)도 포함한다.
- **근거가 되지 않는 것:** 오류 결과(`error` 키가 있는 결과)는 전부. 모델이 보낸 도구 이름·인자가 오류 문구로 되돌아와도 근거가 아니다. 질문에서는 **연도만** 근거가 된다. 질문 속 금액이나 비율은 사용자의 주장이지 근거가 아니다.
- **검사 대상:** `answer`, `clarifying_question`, 구조화 칸(`values`, `change`, `change_pct`)의 모든 숫자.
- **표시 자리 규칙:** 쓴 숫자는 근거 숫자를 **그 자리에서 반올림(0.5는 올림)하거나 버린 값과 정확히 같아야** 한다. 절댓값으로 비교한다(감소를 말로 쓸 수 있으므로).
  - 예: 근거 1.24조 → `1.2조`(반올림·버림) 통과, `1.3조` 실패. 근거 1.19조 → `1.1조`(버림), `1.2조`(반올림) 통과. 근거 3.275조 → `3.3조` 통과, `약 4조` 실패.
- **숫자의 종류별 판정:**

| 종류 | 예 | 근거가 있다고 보는 조건 |
|---|---|---|
| 금액 | `333조 6,059억 원`, `333.6조`, `9백억`, `5천만 원`, `2,431,791,719,869원` | 허용 금액을 표시 자리에서 반올림·버림한 값 |
| 비율 | `10.88%`, `10.9%` | 허용 변화율을 표시 자리에서 반올림·버림한 값 |
| 퍼센트포인트, 배수 | `6.6%p`, `1.4배` | 같은 종류의 근거 숫자가 있을 때만. **변화율은 근거가 되지 않는다.** 지금 도구는 이런 숫자를 주지 않는다 |
| 연도 | `2025년`, `2025-09-30`, `2025.09.30`, `2025/09/30`, `20250930` | 허용 연도. 날짜가 실제로 없는 날(예: `2025-02-31`)이면 판정 불가 |
| 달력 숫자 | `9월 30일`, `3분기`, `1~9월`, `12개월` | 월 1~12, 일 1~31, 분기 1~4, 개월 1~12 범위. 그 기간이 맞는지는 본문 검토가 본다 |
| 14자리 숫자 | `20251114002447` | 허용 접수번호이거나, 쉼표 없이 쓴 허용 금액과 같다. 뒤에 "원"이 붙으면 금액으로만 본다 |
| 단위 없는 큰 수 | `333,605,938,000,000` | 쉼표가 있거나 1,000 이상이면 원 단위 금액으로 정확히 같아야 한다 |
| 단위 없는 작은 정수 | `2개` | 검사하지 않는다 |
| 판정 불가 | 읽지 못한 단위 조합(`1천2백억`의 `1천`), 단위 없는 소수, 없는 날짜 | **근거 없는 숫자로 센다.** 본문 검토에서 사람이 "도구 결과의 값을 바르게 쓴 표기"라고 확인한 경우에만 정정할 수 있다(5절) |

- 모델이 스스로 계산한 숫자(비중, 배수, 도구가 주지 않은 분기 차감 값)는 근거 없는 숫자다.
- 이 판정은 2-3의 "출력 전 숫자 검증"에서 같은 함수를 쓴다.

## 5. 본문 검토와 최종 판정

- 사람은 [`eval/HUMAN_REVIEW.ko.md`](../eval/HUMAN_REVIEW.ko.md)의 기준(공통 5개 + 문항별 확인 사항)으로 **모든 문항**의 본문을 본다. 이 기준은 모델 실행 전에 커밋한다.
- 실행기가 `review_sheet.md`와 `human_review.json`(빈 양식)을 만든다. 검토자는 문항마다 `body_ok`와 이유를 적고, `python eval/finalize.py <폴더>`가 `final.json`을 만든다.
- **최종 통과(`reviewed_passed`) = 자동 통과 ∧ 본문 통과.** 사람이 자동 점수에서 바꿀 수 있는 것은 "판정 불가" 표기를 근거 있는 표기로 인정하는 것뿐이다. 반올림 규칙에 어긋난 숫자나 구조 오류는 바꿀 수 없다.
- 검토자: Claude가 1차로 판정하고 사용자가 확인한다. 다르면 사용자 판정을 따르고 둘 다 기록한다.

**1-5 판정에 쓰는 점수 (실행 전에 고정):**
1. ① 규칙만: 자동 통과 13/13.
2. ② 근거 제공: **최종 통과 11/13 이상**(80%).
3. 근거 없는 숫자: ②와 ③ 모두 0개(사람이 인정한 판정 불가 표기는 제외).
4. ③은 판정 기준이 없다. 결과와 원인을 보고한다.
5. 자동 통과 수도 항상 함께 보고한다.

## 6. 지표 (방식별)

- 자동 통과, 최종 통과(본문 검토 뒤), 상태, 결정, 숫자 일치, 기준, 거절·되묻기, 부호 표현. 분모는 3절의 적용 문항 수이며 형식 오류도 포함한다.
- 근거 없는 숫자의 개수와 1개 이상 나온 문항 수, 판정 불가 숫자 수, 형식 오류 수, 평가기 오류 수, 표현 경고 수.
- 모델 요청 시도 수(`model_attempts`; 실패한 요청 포함)와 응답 수(`model_responses`), 모델 도구 호출 수(①②에서 실행기가 미리 실행한 도구는 세지 않음), 모델 지연 시간 합계·중앙값, 문항 전체 실행 시간 합계.
- ③: **첫 도구 호출의 인자**가 정답 해석과 같은지(`tool_args_first_ok`), 그리고 오류 뒤에라도 맞는 호출에 성공했는지(`tool_args_any_ok`)를 나눠 센다. 예산 초과 문항 수.

## 7. 실행 조건

- 모델: 로컬 Ollama(`127.0.0.1:11434`)만. 다른 주소, 프록시, 리다이렉트 불가.
- 옵션: `temperature` 0, `num_ctx` 8192, `num_predict` 4096, `stream` false, `truncate` false, `shift` false. `think`는 보내지 않는다(모델 기본값 사용이지 "생각 안 함"이 아니다). 실제로 돌아온 `thinking`, 종료 이유, 토큰 수를 그대로 기록한다. `truncate=false`를 보냈다는 것과 실제 런타임의 컨텍스트 초과 처리는 다르므로, 1-5의 연결 확인에서 확인한 것만 보고한다. 온도 0이라도 비트 단위 결정성은 주장하지 않는다.
- **기록:** 요청마다 실제로 보낸 payload와 그 SHA-256, 원시 응답 또는 오류, 소요 시간을 남긴다(실패한 요청 포함). 실행마다 모델 이름·digest·Ollama 버전·옵션, 커밋, 정답·질문·프롬프트·도구·스키마의 해시를 남긴다. **모델 실행은 커밋하지 않은 변경이 있으면 시작하지 않는다.**
- **중간 저장:** 실행 정보는 시작할 때, 문항 결과는 끝나는 즉시 저장한다. 중단돼도 끝난 문항은 남는다. 결과 폴더는 덮어쓰지 않는다.
- **오류 격리:** 모델 오류, 평가기 오류(채점기·실행기의 버그), 예산 초과는 그 문항만 실패시키고 다음 문항으로 넘어간다. 평가기 오류는 따로 세고, 하나라도 있으면 실행기가 실패 코드로 끝난다.
- **③의 예산:** 문항당 모델 요청 5회(최종 답 포함), 도구 호출 3회. 넘으면 **최종 요청 없이** 그 문항을 끝낸다(응답 없는 도구 호출이 남은 대화를 보내지 않는다). 정상 흐름도 "도구 요청 → 도구 결과 뒤 응답 → 최종 답" 3회가 될 수 있다.
- 재시도 없음: 한 문항은 한 번 실행한다.
- 실행 첫 단계: 실제 Ollama에 요청 1회로 연결, 구조화 출력 스키마(enum의 null, pattern), 도구 형식을 확인한다. 문제가 있으면 결과를 보기 전에 고치고 다시 커밋한다.

## 8. 알려진 한계

- 본문 검토는 사람의 판정이라 일관성이 완벽하지 않다. 기준을 미리 고정하고 이유를 남기는 것으로 줄인다.
- 부호 표현의 부정 검사는 "바로 뒤 8글자 안의 않/아니/못"만 본다. 다른 부정 표현은 본문 검토가 잡는다.
- 숫자 추출은 흔한 한국어 금액·날짜 표기만 다룬다. 읽지 못한 표기는 판정 불가로 보수적으로 센다.
- 개발용 13문항은 통계적으로 작다. 1-5 판정은 "가능성 확인"이고 성능 주장이 아니다.
- (기록) v1의 결함 가운데 Codex가 찾은 것과 그 처리는 [1-5 반영 내역](reviews/1-5_codex_response.ko.md)에 있다.

## 9. 2-1 에이전트 방식 (`--mode agent`, 1-5 판정 뒤 추가)

1-5 잠정 판정(사실 문장은 코드, 모델은 해석·결정)에 따른 새 구조를 같은 13문항, 같은 채점 규칙, 같은 본문 검토 기준으로 잰다. **이 절은 에이전트 방식 실행 전에 커밋한다.**

- 모델이 하는 일: 도구 호출(③과 같은 도구, 같은 예산: 모델 요청 5회, 도구 호출 3회), 마지막 결정 JSON(`action`: answer/clarify, `clarify_accounts`, `explanation`).
- 코드가 하는 일: 마지막으로 성공한 도구 결과로 사실 문장과 구조화 칸을 만든다(`dart_review/render.py`). 되묻기는 모델이 고른 후보 계정으로 질문을 만든다.
- 모델의 `explanation`은 숫자가 모두 근거 있을 때만(4절과 같은 판정) "해석(모델):"을 붙여 보여 준다. 아니면 버리고 기록한다. 버린 문장은 채점하지 않는다.
- 실패로 세는 경우: 결정 JSON 형식 오류, 성공한 도구 결과 없이 answer를 고름, 예산 초과(결정 요청 없이 종료), 모델 오류.
- 본문 검토: 렌더러가 쓴 문장도 [HUMAN_REVIEW.ko.md](../eval/HUMAN_REVIEW.ko.md)로 똑같이 본다. 모델의 해석 문장은 공통 5번(단정 금지)으로 본다.
- **해석할 때 주의:** 사실 문장을 코드가 쓰므로 ②·③과 본문 점수를 그대로 비교하면 안 된다. 에이전트 방식의 점수는 "모델의 해석·결정 + 코드의 문장"이라는 제품 구조의 성능이고, 차이의 원인은 도구 인자, 결정, 해석 문장으로 나눠 본다. ① 규칙만은 같은 렌더러를 쓰므로 렌더러 자체의 점검이다.

## 10. 규칙 기반 기준선과 표현 변형 세트 (로드맵 2-2, 실행 전 커밋)

- **기준선(`--mode baseline`):** 모델 없이 키워드 규칙으로 질문을 읽고 정해진 순서로 도구 하나를 부른 뒤, 에이전트와 같은 렌더러로 답한다. 규칙은 `dart_review/baseline.py` 설명에 있고, GOLD_RULES 2절 기본값 표를 일반 규칙으로 옮긴 것이다(문항별 예외 없음).
- **표현 변형 세트(`--set paraphrase`, `eval/dev_paraphrases.json`):** 13개 개발 문항과 뜻과 정답이 같고 표현만 다른 질문 13개. 기준선을 만들기 전에 커밋했다(`8d41404`).
- **비교 방법:** 기준선과 에이전트를 같은 채점 규칙(3·4절), 같은 본문 기준(HUMAN_REVIEW)으로 두 세트에서 잰다. 에이전트의 개발 세트 결과는 2-1 실행(`eval/feasibility_2026-10-07/agent/`)을 쓴다.
- **판정에 쓰는 방식(SCOPE 7절):** 에이전트가 기준선을 이기는지는 두 세트의 최종 통과 수(본문 검토 뒤)와 자동 통과 수로 본다. 이기지 못하면 그대로 보고하고 SCOPE 10절에 따라 "검증 도구 + LLM 설명"으로 정직하게 재정의한다.
- **한계(미리 적어 둠):** 개발 문항, 표현 변형, 기준선 규칙, 에이전트 프롬프트를 모두 같은 사람(Claude)이 썼다. 기준선 작성자는 두 세트를 이미 봤으므로 표현 변형도 완전한 미지 데이터가 아니다. 이 비교는 "같은 저자의 개발용 점검"이고, 공정한 비교는 3-1의 봉인된 평가에서 한다.

## 11. 교차 확인 구조 (설계 B, `--mode crosscheck`, 실행 전 커밋)

- **구조:** 키워드 규칙(2-2 기준선)과 모델이 각자 질문을 읽는다. 모델은 도구 없이 해석 JSON 하나만 낸다(질문당 요청 1회, 프롬프트 `reading-v1`). 두 해석이 같으면 코드가 도구를 한 번 부르고 렌더러로 답한다. 다르면 두 해석을 보여 주며 되묻는다. 한쪽만 읽었으면 그 해석으로 답하고 "한 가지 해석으로만 확인"이라고 표시한다. 모델의 해석 문장은 쓰지 않는다.
- **출력 검증(로드맵 2-3):** 보여 줄 문장의 모든 숫자를 4절 규칙으로 검사해, 근거 없는 숫자가 하나라도 있으면 답을 내보내지 않는다(`output withheld`).
- **채점:** 3·4절과 같다. 두 해석이 달라 되물은 문항은 기대 상태가 되묻기가 아니면 실패로 센다(안전하지만 답을 못 한 것). 그래서 실패를 두 종류로 나눠 보고한다.
  - `confident_wrong`: 답(되묻기 아닌 상태)을 보여 줬는데 틀림. **이 구조가 줄이려는 것.**
  - `asked_back_instead`: 답해야 했는데 되물음.
- **평가 세트:** 개발 13 + 표현 변형 13. 비교 대상은 기준선(25/26, confident_wrong 1)과 2-1 에이전트(23/26).
- **주의:** 이 구조는 2-2 결과를 본 뒤 정했다. 표현 변형 세트는 이 구조를 만들기 전에 있었지만, 같은 저자가 모든 것을 썼다. 개발 세트 성적은 설계 근거일 뿐이고, 효과는 3-1의 봉인된 평가로 확인한다.

### 11.1 3-0b 변경 (2026-10-08, 실행 전 커밋)

Codex 검토 B4·B7·C1·C3와 사용자 결정(`docs/reviews/roadmap_proposal_codex_response.ko.md` 5절)에 따라 바꿨다. 위 11절의 "한쪽만 읽었으면 그 해석으로 답한다"는 이 절로 대체한다.

| 경우 | 동작 | 기록(`readings.used`) |
|---|---|---|
| 두 해석이 같음 | 지금과 같다 | `both` |
| 두 해석이 다름 | 되묻는다. 되묻기 문장도 숫자 검사를 거친다(허용 연도: 질문 연도와 두 해석이 제안한 연도) | `neither (asked back)` |
| 규칙만 읽음(모델 실패) | **답하지 않는다** | `rule only (withheld)` |
| 모델만 읽음(규칙이 못 읽음) | 코드가 쓴 "이렇게 이해했습니다: …"를 맨 앞에 두고 답한다. 숫자 검사에서 모델 해석의 연도를 허용한다 | `model only` |
| `--no-model`(사용자가 직접 선택) | 규칙 해석으로 답하고 그 사실을 표시한다 | `rules only (--no-model)` |
| 둘 다 못 읽음 | 답 없음 | `none` |

- **비지원 계정:** 두 해석기 모두 "지원하지 않는 계정"을 낼 수 있다. 모델은 `action: unsupported`를 쓴다. 규칙은 지원 키워드가 개발 캐시 계정명 사전(`dart_review/account_vocabulary.json`)의 더 긴 계정명 안에 있으면 그 계정으로 읽지 않는다(예: 유동자산 ≠ 자산총계). 두 해석이 모두 거절일 때만 상태 `비교 불가`로 거절한다. 한쪽만 거절이면 되묻는다.
- **기준 날짜:** 해석 프롬프트(`reading-v2`)에 기준 날짜를 넣는다. "올해", "작년", "재작년"은 이 날짜로 정한다. 평가 실행은 `--reference-date`로 이 날짜를 고정하고 `run.json`에 기록한다. 프롬프트 해시는 날짜를 넣기 전의 템플릿으로 계산한다.
- **보고:** 해석 경로별 결과를 따로 센다. 특히 `model only` 경로의 정답·오답과 `rule only (withheld)` 횟수를 보고한다. 3-1의 해석 기여·제품 기여 표(Codex A2)는 3-1 사전 등록 때 확정한다.
- **재측정:** 프롬프트가 바뀌었으므로 개발·변형 세트를 `reading-v2`로 다시 실행해 새 폴더에 둔다. 기존 `feasibility_2026-10-07` 결과는 그대로 둔다. 비지원·상대 시점·약칭·동의어 질문은 점수에 넣지 않는 탐색 세트(`eval/probe_3-0b.json`, 실행 전 커밋)로 따로 확인한다.
