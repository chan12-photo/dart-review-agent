# 정답 규칙: 개발용 질문 세트

- 대상: [`eval/dev_questions.json`](../eval/dev_questions.json) (질문과 사람이 지정한 근거), [`eval/dev_gold.json`](../eval/dev_gold.json) (코드가 만든 정답)
- 상태: **초안 v2 (2026-10-07, Claude 작성).** Codex 독립 검토([결과](reviews/1-3_codex_result.ko.md), [반영 내역](reviews/1-3_codex_response.ko.md))를 반영했다. 사용자 검토가 남았다. 개발용이므로 검토 뒤 고칠 수 있다. 최종 평가 세트(3-1)는 따로 만들고 실행 전에 봉인한다.

## 1. 정답을 만드는 방식 (순환 방지)

정답을 1-2의 규칙 코드로 계산하면, 규칙의 버그가 정답에도 그대로 들어가 평가가 버그를 못 잡는다. 그래서 정답은 두 갈래로 만들고 서로 대조한다.

1. **사람이 지정한 근거:** 질문마다 정답이 들어 있는 보고서(연도, 보고서 코드), 칸(`thstrm` 등), 재무제표, 계정ID를 `dev_questions.json`에 직접 적는다. 기대 상태(`비교 가능` 등)와 부호가 바뀌는 경우의 표현(흑자 전환 등)도 적는다.
2. **독립 계산:** [`eval/build_gold.py`](../eval/build_gold.py)는 다음을 규칙 코드 없이 한다.
   - 캐시 원본에서 지정된 행을 직접 읽는다(재무제표 + 계정ID + 합계 행이 정확히 1개).
   - 각 칸이 어느 기간인지 **자체 칸-기간 표**로 정하고, 질문이 요구한 기간과 같은지 확인한다. 기간 라벨도 직접 만든다.
   - 변화량, 변화율, 증감 표현을 직접 계산한다.
   - 재작성 근거 쌍은 같은 기간, 같은 재무제표·계정, 서로 다른 두 보고서, 다른 금액, 같은 통화인지 확인한다.
   - **공유하는 것:** 캐시와 HTTP 클라이언트(응답 읽기), 회사 이름, 계정 표시 이름.
3. **대조:** 같은 질문을 규칙 코드(`review_change`)로도 풀어서 다음이 모두 같은지 확인한다. 하나라도 다르면 정답 파일을 만들지 않고 멈춘다.
   - 상태, 두 금액, 근거 보고서·칸, 접수번호, 통화, 기간 라벨
   - 변화량, 변화율, 증감 표현
   - 재작성 이유가 **정확한 근거 쌍**(기간, 두 금액, 두 접수번호)을 가리키는지
   - 앞 보고서의 값을 메모할 때 그 금액과 접수번호

이 방식이 막지 못하는 것:
- 근거를 지정한 사람(지금은 Claude)과 규칙을 만든 사람이 **같은 착각**을 하는 경우. 그래서 독립 검토(사용자, Codex)가 필요하다.
- `case_types` 태그는 질문이 그 함정을 시험한다고 **선언**할 뿐, 실제로 시험하는지는 자동으로 증명하지 않는다.
- 되묻기 질문(dev12)은 구조만 확인한다. 질문 해석기가 실제로 되묻는지는 1-4 이후 평가에서 본다.

## 2. 질문 해석의 기본값

질문이 말하지 않은 부분은 아래 기본값으로 정한다. Agent도 같은 기본값을 따르고, **답에 어떤 기본값을 썼는지 밝혀야 한다.**

| 질문 표현 | 해석 |
|---|---|
| 연결·별도 언급 없음 | **연결.** 범위 안 회사에 대한 제품의 기본값이다. 답에 "연결 기준"을 밝힌다. 연결 자료가 없으면 별도로 조용히 바꾸지 않고, 그 사실을 알리고 되묻는다 |
| "N년 매출" (분기 언급 없음) | N년 연간 12개월 (사업보고서) |
| "N년 3분기 매출", "2분기 매출" | 그 분기 3개월 (3분기는 7~9월, 2분기는 4~6월) |
| "3분기 누적", "3분기까지", "1~9월" | 1~9월 누적 |
| "상반기" | 1~6월 누적 (반기 보고서의 누적 칸) |
| "3분기말 자산" | 9월 30일 시점 |
| "전년보다", "작년 같은 분기와", "전년 같은 기간" | 기간 길이와 위치가 같은 전년 기간 |
| 시점 값의 "1년 전" | 전년 같은 날짜 시점 |
| "직전 분기보다" | 바로 앞 분기의 같은 길이 기간 (3개월끼리) |
| "당기순이익", "순이익" | 연결 기준이면 **비지배지분을 포함한 당기순이익 합계**(`ifrs-full_ProfitLoss`). 지배기업 소유주 귀속 순이익과 섞지 않는다 |
| "이익"처럼 계정이 둘 이상으로 읽힘 | **되묻는다** (영업이익인지 당기순이익인지) |

## 3. 계산 규칙

- **금액:** 원 단위 정수. 조·억 단위 표시는 출력 단계(2-3)의 일이고, 정답 비교는 원 단위로 한다.
- **기준 값:** 비교 기간 보고서에 기준 기간 칸이 있으면 그 칸을 쓴다(같은 보고서의 당기·전기는 같은 기준으로 작성된다). 없으면 기준 기간의 원래 보고서를 쓴다.
- **변화량:** 비교 값 − 기준 값.
- **변화율:** 기준 값이 0보다 크고 비교 값이 0 이상일 때만 계산한다. (비교 값 − 기준 값) ÷ 기준 값 × 100을 **소수 셋째 자리에서 반올림해 둘째 자리까지** 표시한다. 정확히 반(±0.005)이면 0에서 먼 쪽으로 올린다(+0.005 → 0.01, −0.005 → −0.01). 비교 값이 0이면 −100.00%다.
- **부호가 바뀌거나 기준 값이 0 이하:** 변화율을 표시하지 않는다. 수학적으로 불가능해서가 아니라 오해를 막기 위한 정책이다. 영업이익·당기순이익은 흑자 전환, 적자 전환, 적자 축소, 적자 확대로 표현한다. 현금흐름처럼 손익이 아닌 계정에는 흑자·적자라는 말을 쓰지 않는다.
- **상태:**
  - `비교 가능`: 변화를 계산한다. 두 보고서의 값을 쓸 때는 "관찰한 범위에서 기준 불일치가 없다"는 뜻이지, 재작성이 없다는 증명이 아니다.
  - `비교 불가`: 연결과 별도, 시점과 기간, 다른 기간 길이, 다른 통화, 보고서에 없는 기간(반기·3분기의 단독 분기 현금흐름, 4분기 3개월 손익). 이유를 밝히고, 가능하면 비교할 수 있는 대안을 제시한다. 차감 계산은 지금 제품이 지원하지 않는 범위다.
  - `데이터 없음`: 요청한 보고서에 데이터가 없는 경우(예: 2014년, OpenDART 013). 오류와 구분해서 답한다.
  - `확인 필요` (숫자 없음): 계정 후보가 여러 개라 하나로 정할 수 없을 때.
  - `확인 필요` (숫자와 함께): 두 보고서의 기준이 같은지 확인되지 않을 때(관찰된 재작성, 필요한 보고서 없음, 이어지는 값 없음), 계정명과 다른 표준ID가 충돌할 때, 통화가 비어 있을 때. 숫자를 보여 주되 이 사실을 먼저 밝힌다. 이유에는 **관찰한 것만** 적는다. 예를 들어 dev08에서 "2024년 3분기말 값의 기준이 실제로 다르다"고 단정하면 틀린 답이다.
- **연결과 별도를 함께 묻는 질문(dev05):** 두 값을 나란히 보여 준다. "연결이 별도보다 N원 크다"는 같은 시점·같은 통화의 **집계 범위 차이**로 말해도 된다(정답 파일의 `allowed_difference`). 다만 증가·성장 같은 시간 변화로 표현하거나, 차이의 원인을 근거 없이 단정하면 안 된다. 원인 설명은 해석이므로 확정 사실과 구분한다.
- **앞 보고서의 다른 값(dev07):** 기준 값은 같은 보고서(2025 사업보고서)의 값을 쓰고, 앞 보고서(2024 사업보고서, 캐시한 판은 정정본)에서 값이 달랐다는 점을 밝힌다. 사용자가 "당시 발표 기준"을 명시해서 묻는다면 다른 질문이므로 그 기준을 밝히고 따로 답한다.

## 4. 사례 유형과 질문 배치

| 사례 유형 (SCOPE 7절) | 질문 |
|---|---|
| 정상 비교 | dev01(연결, 연간), dev13(별도, 상반기 누적) |
| 전년 분기 추가 조회 (재무상태표) | dev02, dev08 |
| 3개월·누적 함정 | dev03(현금흐름 누적), dev04(손익 3분기 누적), dev06(3개월 직전 분기), dev13(상반기 누적) |
| 연결·별도 함정 | dev05 |
| 표준계정코드 없음 (다른 ID로 오표기, 확인된 예외) | dev06 |
| 재작성 (1-2에서 추가) | dev07(같은 보고서), dev08(두 보고서 사이, 확인 필요) |
| 부호 전환 | dev09 |
| 비교 불가 (거절이 정답) | dev10 |
| 데이터 없음 | dev11 |
| 모호한 질문 (되묻기가 정답) | dev12 |

- SCOPE 2절의 대표 요청 5개는 dev01, dev02, dev03, dev05, dev11에 들어 있다.
- 로드맵은 10~12개를 계획했지만, Codex 검토(E7)에 따라 위험 신호가 없는 별도 기준 정상 비교(dev13)를 더해 13개가 됐다.
- **비어 있는 유형:** 표준계정ID 자체가 없는 행(`-표준계정코드 미사용-`)만으로 답해야 하는 경우는 개발용 캐시의 대상 계정에 없다. 합성 단위 테스트로만 확인한다.
