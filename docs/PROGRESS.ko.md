## 1. 목표

### 1.1 포트폴리오 목표
- 대상 직무: LLM 평가·앱 엔지니어링, 사무 DX, 백엔드, 금융.
- 보여 주려는 것: "AI를 썼다"가 아니라 **AI가 틀리는 지점을 재고, 틀린 결과가 사람에게 표시 없이 가지 않게 만드는 능력.** 사전 등록 평가, 독립 검토(Codex), 실패를 숨기지 않는 보고가 핵심이다.

### 1.2 제품 원칙 (v0.1부터 이어짐)
- 숫자는 원본에서만 가져온다. 의심되는 칸은 **고치지 않고** "확인 필요"로 표시한다.
- 읽지 못한 것은 **경고 없이 빠뜨리지 않는다.**
- 결과가 나빠도 그대로 보고한다. 평가는 결과를 보기 전에 기준을 고정한다(사전 등록).

### 1.3 작업 방식
- push, 저장소 생성, 비용이 드는 API, 새 모델 내려받기, OpenDART 새 조회, 파일 내려받기는 **매번 사용자 승인**.
- 평가 사전 등록 전, 공개 전에는 **Codex 독립 검토**를 받는다(사용자가 실행).
- 커밋 전에 테스트와 공개 안전 검사(인증키·개인정보·로컬 경로)를 통과해야 한다.

## 2. v0.1: 공시 재무 비교 (완료, 공개)

한국 상장사의 OpenDART 공시로 재무 수치를 조회하고 기간끼리 비교하는 도구. 비교가 성립할 때만 비교하고(연결·별도, 기간 길이, 통화, 재작성), 아니면 거절하거나 되묻는다.

| 평가 | 질문 | 공식 판정 | 제품의 틀린 수치 답 | 해결률 (제품 / 규칙만) | LLM이 막은 오답 / 잃은 정답 |
|---|---|---|---|---|---|
| 3-1 봉인 평가 | 사람이 쓴 36개 | **기준 미달** (비교용 방식의 채점기 불일치) | 0 / 22 | 22/23 / 23/23 | 0 / 1 |
| 3-5 대량 템플릿 평가 | 규칙으로 만든 600개 | **기준 충족** (고친 채점기, 판정 조건 P5 기준) | 0 / 419 | 419/480 / 476/480 | 0 / 62 |

- 두 평가 모두 제품은 틀린 수치를 내지 않았다.
- **키워드 규칙만 쓴 쪽이 더 많이 맞혔다.** LLM 교차 확인은 오답을 하나도 막지 못했고 정답만 잃었다. 이 결과를 숨기지 않고 README 맨 앞에 적었다.
- v0.1.2: 3-5에서 찾은 결함(회사 이름 정규화, 모르는 회사 거절 등)을 고쳤다. 이미 본 질문이라 평가 결과로 쓰지 않는다.
- 보류한 과제(다시 꺼낼 조건은 README 표): 3-6 재평가, 교차 확인 정책 변경, 검토 메모, MCP 어댑터, 변화 이유 찾기(RAG).

## 3. v0.2: 문서 → 검증된 엑셀 (개발 중)

### 3.1 무엇을 만드는가
- 감사보고서·영업보고서 같은 재무제표 PDF(**텍스트 PDF, 스캔, 휴대폰 사진**)를 넣으면 재무제표를 엑셀로 옮긴다.
- 엑셀 시트 네 개:
  - 안내: 읽는 법
  - 재무제표: "확인 필요" 칸은 노란색과 메모
  - 셀 출처: 쪽, 위치, 원문 표기, 읽은 방법, 증거
  - 검증: 문제 목록
- 사용 방법: CLI `python -m dart_review extract 파일.pdf`, 로컬 API와 업로드 화면 `python -m dart_review serve`.

### 3.2 주요 결정 (사용자)
| 날짜 | 결정 |
|---|---|
| 10-10 | 친구 조언(사무 DX)에 따라 v0.2를 이 저장소 안의 새 기능으로 만든다 |
| 10-10 | 텍스트 PDF와 스캔 PDF 둘 다. CLI → API → 화면 순서 |
| 10-10 | **AI가 숫자까지 읽고, 원본 증거로 따로 확인한다** (처음의 "LLM은 보조로만"에서 바꿈) |
| 10-10 | 로컬·무료 먼저(Ollama `qwen3-vl:8b`), 상용 API는 나중에 같은 인터페이스로 |
| 10-10 | OCR은 Tesseract(Homebrew), macOS Vision을 보조 증거로 |

### 3.3 작동 방식
- **AI 방식 (기본값, `--reader ai`):**
  - 로컬 비전 모델이 표를 8줄 안팎의 띠로 나눠 "계정 | 금액 | 금액"으로 옮긴다.
  - 금액마다 원본에서 같은 숫자를 찾는다.
    - 텍스트 PDF: PDF 글자의 같은 줄
    - 스캔·사진: Tesseract와 Vision OCR의 같은 줄, 기간 순서까지
  - 기간은 증거 숫자의 위치로 정한다. 계정명은 텍스트 PDF면 인쇄된 이름을 쓰고, 사진이면 Vision이 읽은 이름과 같은지 본다.
  - 원본에서 찾지 못한 숫자는 "확인 필요"다. 원본에 있는데 AI가 읽지 않은 금액은 쪽·행·금액으로 보고한다.
- **규칙 방식 (`--reader rules`):** 단어 위치와 규칙만 쓴다. 빠르지만 사진은 읽지 못한다.
- **검산:**
  - 재무상태표 항등식(자산총계 = 부채총계 + 자본총계 등)
  - 소계 검산: 세부·소계의 인쇄 위치로 층을 나누고, 항목 기호로 세 번째 층을 알아본다.
  - 구조를 확인할 수 없는 소계는 검산했다고 치지 않고 칸을 표시한다.

## 4. D4 정확도 평가: 계약 6판 요약

- 목적: 처음 보는 재무제표 PDF에서 **표시 없이 틀린 값(S1), 표시 없이 틀린 계정명(L1), 가리켜지지 않은 빠진 칸(S2)**을 잰다. 기준은 텍스트 PDF에서 셋 모두 0이다(합성 스캔은 S1 0).
- 문서:
  - 새 상장사 10곳의 2025 연결감사보고서. 고정 시드 순서로 고르고, 개발·봉인 회사와 금융업은 뺀다.
  - 같은 문서의 합성 스캔 3조건.
  - (선택) 사진.
- 순서:
  1. 계약
  2. Codex 검토
  3. 사용자 결정
  4. **제품 P·평가 도구 T·모집단 고정 (후보 문서를 열기 전)**
  5. 후보 판정과 문서 받기
  6. 정답 생성기와 사람이 확정하는 매핑표
  7. 사전 등록
  8. 실행 (diff 확인)
  9. 정답에 없는 칸의 사람 판정과 채점
- 정답: 제품 코드와 독립인 정답 생성기(`eval/d4_gold.py`)와 사람이 확정한 매핑표. 채점기(`eval/d4_score.py`)는 매핑표가 확정되지 않으면 돌지 않는다.
