  - 인용이 있다고 변화의 원인이라는 뜻은 아니다. 회사·기간은 맞지만 무관한 문장, 반대 근거, 다른 회계 범위를 평가에 넣는다.

  - 숫자 검사기를 붙였다는 이유만으로 해결됐다고 보지 않는다.
  - 임베딩 모델 내려받기는 사용자 승인이 필요하다.
- [ ] **4-5 새 기능 평가와 v0.2**
  - 기존 봉인 회사에서 "새 과제"를 평가할 수 있다. 미지 회사 일반화와는 구분해 보고한다.
  - 새 봉인 회사 2~3곳은 선택이다(A5). 쓴다면 선정 요건과 교체 금지 규칙을 먼저 정한다. 업종까지 바꾸면 실패 원인이 섞인다.
- **확장 비용 기록 (기능마다):**
  - 기능 규모와 완료 기준을 고정한다.
  - 실제 작업 시간, 바뀐 공통 인터페이스, 새 의존성, 회귀를 기록한다.
  - 새 기능을 뺐을 때 기존 기능이 독립적으로 돌아가는지, 코드를 복제했는지 기록한다.
  - LOC와 테스트 수는 참고값으로만 남긴다. 기능 하나의 적은 LOC로 일반적 확장성을 주장하지 않는다.

## 사용자 결정 대기
1. 약칭(예: "삼전") 지원 여부. 지원·되묻기·거절 중 하나를 3-1a에서 정한다.
2. 3-1 자유 표현 질문 일부를 사용자가 직접 쓸지, 몇 개를 쓸지.
3. 새 의존성 정책. 제안: 핵심은 표준 라이브러리로 두고, MCP·API·RAG는 선택 설치.
4. 상용 API 비교를 할지(비용 발생).
5. 4단계에서 새 봉인 회사를 쓸지, 쓴다면 선정 방법(사용자 지정 권장, 선택 편향은 남음).

## 위험이 현실이 되었을 때
| 상황 | 대응 |
|---|---|
| OpenDART 응답이 불안정하거나 호출 제한에 걸림 | 캐시 우선, 호출 간격 확대, 원인 기록. 계속되면 범위 축소 |
| 근거 제공 평가가 60% 미만 | 모델 병목. 상용 API 비교를 사용자에게 제안(승인 필요) |
| Agent가 기준선을 이기지 못함 | "검증 도구 + LLM 설명"으로 정직하게 재정의 |
| 계정 6개도 안정적으로 못 맞춤 | 회사 또는 계정 축소, 원인을 보고서에 기록 |
| 세션이 작업 중간에 끊김 | 이 문서의 상태 표시와 "현재 상태"를 기준으로 이어서 진행 |
| 3-2에서도 LLM이 기준선을 못 이김 | 그대로 보고한다. "검증 도구 + LLM 해석 보조"로 정의하고, 질문 비중을 사후에 바꾸지 않는다 |
| 평가기 버그·정답 모호성 발견 | 모델 성능 판정을 보류하고, 수정은 새 버전으로 분리해 전후를 모두 보고한다 |
| 범위가 계속 커짐 | 기능마다 최소 버전과 완료 기준을 먼저 정하고, 넘치면 다음 버전으로 미룬다 |
| 새 의존성 때문에 재현이 어려워짐 | 핵심은 표준 라이브러리로 두고, 확장 기능은 선택 설치와 고정 버전으로 둔다 |
| 재배포 조건상 데모 데이터를 넣을 수 없음 | 데이터 없이 공개하거나, 합성 데모로 바꾸고 표시한다 |
