# 로드맵 수정안 (2026-10-08, 제안 단계)

- 상태: **제안.** 사용자 승인과 Codex 검토 뒤에 [ROADMAP.ko.md](ROADMAP.ko.md)와 [SCOPE.ko.md](SCOPE.ko.md)에 반영한다. 반영 전까지 기존 로드맵이 유효하다.
- 작성: Claude. 근거: 1~2단계 결과([REPORT.md](../eval/feasibility_2026-10-07/REPORT.md)), 사용자 요청(기능 확장성, LLM 필요성), 2026-10-06 채용 공고·가이드 조사(다시 확인 필요).

## 1. 왜 고치는가 (현재 로드맵의 문제)

1. **문서가 현실과 어긋난다.**
   - SCOPE의 정의와 역할 표는 설계 B(교차 확인) 이전 내용이다.
   - 2-1에 하지 않기로 한 도구(회사 찾기·보고서 목록)가 남아 있다.
   - 3-2는 "Agent와 기준선 비교"인데 지금 제품은 교차 확인형이다.
   - RAG가 SCOPE에서는 "2단계", 로드맵에서는 "4단계"다.
2. **3-1이 핵심 질문 두 개를 시험하지 않는다.**
   - "LLM이 왜 필요한가": 정형 질문만 쓰면 키워드 규칙이 또 이긴다(2-2에서 이미 25/26).
   - "확장되는가": 코드 수정 없이 새 회사에 돌린다는 조건이 없다.
3. **기능 확장이 로드맵에 없다.** 사용자가 중요하게 보는 "기능을 계속 붙일 수 있는 구조"를 보여 줄 계획이 없다.
4. **봉인 데이터는 한 번만 쓸 수 있다.** 봉인 4곳을 비교 기능에 쓰면, 나중 기능을 공정하게 평가할 데이터가 없다.
5. **채용 시장의 요구 중 비어 있는 것이 많다.** RAG와 하이브리드 검색, 문서 처리 자동화, MCP, 배포(FastAPI·Docker), 상용 API, 워크플로우(LangGraph).
6. **밀린 일이 쌓였다.**
   - 본문 1차 판정의 사용자 확인(`[경계]` 4건), 개발 질문과 기본값 확인
   - 미룬 Codex 재검증
   - 출력 한도 도달(`done_reason: length`)을 표시하지 않음
   - 데모 데이터의 재배포 조건 미확인

## 2. 바꾸지 않는 원칙

- 평가 기준은 실행 전에 커밋한다. 결과를 본 뒤 바꾸면 이유와 전후 점수를 모두 보고한다.
- 실패와 한계를 그대로 보고한다. 개발 세트 점수로 성능을 주장하지 않는다.
- 사용자에게 보이는 숫자는 코드가 검증한 도구 결과에서만 나온다. 모든 기능에 적용한다.
- 인증키, 봉인 회사, 공개 안전성 검사 규칙은 그대로 유지한다.
- push, 저장소 공개, 비용이 드는 API, 새 모델 내려받기는 매번 사용자 승인을 받는다.
- 작업은 한 세션 크기로 나눈다.

## 4. 3단계: 비교 기능 확정과 1차 공개 (v0.1)

### 3-0 정리 (신규) · 추천 모드: 높음 · Codex: 이 수정안 자체를 검토(권장)
- SCOPE와 ROADMAP을 설계 B 기준으로 갱신한다. 정의, 역할 표, 단계 번호, 낡은 항목을 정리한다.
- 밀린 사용자 확인을 처리한다.
  - 본문 1차 판정과 `[경계]` 4건
  - 개발 질문 문장과 해석 기본값(GOLD_RULES 2절)
- 실행 기록에 출력 한도 도달(`done_reason: length`)을 표시하고 집계한다.
- **두 번째 봉인 회사 선정**(4단계 기능 평가용, 2~3곳).
  - 업종이 기존 7곳과 겹치지 않게 고르고, 금융사는 제외한다.
  - 재무 데이터는 보지 않고 회사 목록(이름·코드)만 확인한다.
  - 선정 방식은 사용자 지정을 권한다(Claude의 선택 편향 방지).
- 채용 공고 요구 사항을 짧게 다시 조사해 4·5단계 우선순위를 확인한다(2026-10-06 조사의 갱신).
- **완료 기준:** 문서 갱신 커밋, 사용자 확인 기록, 두 번째 봉인 목록 커밋.

### 3-1 최종 평가 설계와 사전 등록 (수정) · 추천 모드: 엑스트라 · **Codex: 필수(커밋 전)**
- 대상: 봉인 회사 4곳(NAVER, CJ제일제당, 이마트, LG에너지솔루션).
- 질문 세 묶음:
  1. **정형 표현:** 개발 질문과 같은 유형
  2. **자유 표현:** 구어체, 회사 별칭("삼전" 같은 약칭), 상대 시점("작년", "직전 분기"), 띄어쓰기·오타, 한 문장에 조건이 여러 개
  3. **범위 밖:** 지원하지 않는 계정·회사·기간, 모호한 질문
- **질문 작성자를 나눠 독립성을 높인다.** 일부는 사용자, 일부는 다른 모델(Astra 등), 일부는 Claude가 쓰고 작성자를 기록한다.
- 비교 대상: 키워드 규칙만 / 모델 해석만 / 교차 확인(제품).
- 지표:
  - **주 지표:** 자신 있게 틀린 답 0
  - 보조 지표: 최종 통과율, 되묻기 비율(불필요한 되묻기 포함), 숫자 근거 위반 0
  - **LLM 필요성 지표:** 규칙이 읽지 못했거나 틀린 질문에서 모델 해석이 맞은 비율
  - **회사 확장성:** 코드 수정 없이 실행. 실행 전에 필요한 변경이 생기면 그 목록이 곧 결과다
- 정답: 근거 칸 지정과 독립 계산(1-3 방식), 판정 기준, 본문 검토 기준을 실행 전에 커밋한다.
- 커밋을 push한다(사용자 승인 필요). 사전 등록 직후 새로 클론해서 검증한다.
- **완료 기준:** 사전 등록 커밋과 push, 새 클론 검증, Codex 검토 반영 기록.

### 3-2 최종 평가 실행과 보고 (수정) · 추천 모드: 실행 중간, 보고 엑스트라 · Codex: 권장(보고서 공개 전)
- 세 방식의 비교와 묶음별 결과, 확장성 결과(회사별 계정 찾기 성공률, 새로 나온 예외)를 보고한다.
- "규칙이 못 읽은 질문에서 LLM이 한 일"을 따로 보고한다.
- 실패 사례는 모두 공개한다. 판정 기준은 SCOPE 10절을 갱신한 것을 쓴다.

### 3-3 문서·CI·공개 준비 (수정) · 추천 모드: 높음

- 공개 안전성 검사를 git hook이나 CI로 강제한다(지금은 절차일 뿐).

## 5. 4단계: 기능 확장과 확장성 검증 (신규, 기존 4단계 RAG 흡수)

### 4-0 기능 입구와 기능 규약 · 추천 모드: 엑스트라 · Codex: 권장
- **기능 입구(라우터):** 질문을 비교 / 문서 작성 / 변화 이유 / 범위 밖으로 나눈다.
  - LLM이 분류하고, 확신이 없거나 두 기능이 함께 해당하면 되묻는다.
  - 분류 정확도를 따로 평가한다.
- **기능 규약 문서:** 새 기능이 지켜야 할 것
  - 공통 숫자 검사를 통과한다
  - 실행 기록을 남긴다
  - 평가 기준을 먼저 정한다
  - 사실 문장은 도구 결과로 만든다
  - 재생 데모를 추가한다
- **확장 비용 측정법:** 기능마다 다음을 기록한다.
  - 기존 코드에서 고친 줄 수와 새로 쓴 줄 수
  - 공통 장치를 고치지 않고 재사용했는지
  - 추가한 테스트 수, 걸린 세션 수
- **완료 기준:** 라우터와 규약, 측정 스크립트. 기존 비교 기능이 라우터 뒤에서 그대로 통과한다.

### 4-1 MCP 서버 (도구 공개) · 추천 모드: 높음
- 지금 검증 도구(compare_values, side_by_side, 숫자 검사)를 MCP 규격으로 공개한다. Claude 같은 다른 AI가 이 도구를 그대로 쓸 수 있다.
- 이유: 비용이 작고 채용 키워드(MCP, 도구 연결) 가치가 크다. "도구 계층 재사용"을 처음 시험하는 기능이기도 하다.
- 결정 필요: 공식 MCP Python SDK 같은 새 의존성을 받아들일지. 지금은 표준 라이브러리만 쓴다. **제안: 핵심 패키지는 표준 라이브러리만 유지하고, MCP·API·RAG는 선택 설치 묶음으로 분리.**
- **완료 기준:** MCP 클라이언트에서 도구를 호출해 대표 질문의 값이 같게 나오는 테스트. 확장 비용 기록.

### 4-2 검토 문서 작성 (문서 처리 자동화) · 추천 모드: 엑스트라(설계), 높음(구현)
- 예: "카카오 2025년 실적 검토 메모", "세 회사 3년 실적 비교표(엑셀)".
- 흐름: 계획(어떤 비교가 필요한가, LLM) → 조회와 판정(코드) → 문서 구성(틀과 사실 문장은 코드, 요약·강조점·연결 문장은 LLM) → 숫자 검사 → 사람 검토.
- 출력 형식: Markdown과 엑셀(.xlsx)을 우선한다. Word는 선택.
- 평가 기준(실행 전 고정):
  - 숫자 근거 위반 0
  - 필수 항목 포함
  - "확인 필요·비교 불가" 항목 누락 없음
  - 근거 없는 단정 없음
  - 사람 검토 기준
- 선택: 이 흐름을 **LangGraph**로 구현해 비교한다(키워드 가치). 필요성이 약하면 하지 않고 이유를 기록한다.
- 위험: 로컬 모델의 긴 글쓰기 약점(1-5에서 확인). 대응은 LLM이 쓰는 부분을 짧게 제한하는 것이다.
- **완료 기준:** 개발 문서 요청 세트(5~8개)에서 기준 충족, 재생 데모 추가, 확장 비용 기록.

### 4-3 변화 이유 찾기 (RAG) · 추천 모드: 엑스트라(설계), 높음(구현)
- 공시 원문 XML(`document.xml`, 허용 목록에 이미 있음)을 절 단위로 나눈다. 경영진단, 사업의 내용 등.
- **하이브리드 검색:** 키워드(BM25)와 임베딩 벡터 검색을 결합한다.
  - 결정 필요: 로컬 임베딩 모델 내려받기(승인 필요)와 벡터 저장 방식(경량 로컬 저장 우선).
- 답: 확정된 변화(코드) + 근거 문장 인용(LLM이 고르고, 원문에 실제로 있는지 코드로 검증).
- 평가 기준:
  - 인용 정확도: 인용이 원문에 있고 해당 회사·기간의 것인가
  - 근거 적합성: 그 문장이 변화를 설명하는가(사람 검토)
  - 검색 재현율: 정답 절을 찾았는가
- 데이터 근거: 이미 찾은 "설명이 필요한 변화"(카카오 재작성, 셀트리온 합병 영향)를 개발 사례로 쓴다.
- **완료 기준:** 개발 질문 세트에서 기준 충족, 인용 검증 테스트, 확장 비용 기록.

### 4-4 두 번째 봉인 평가 · 추천 모드: 엑스트라 · **Codex: 필수(사전 등록 전)**
- 3-0에서 봉인한 회사로 라우터·문서 작성·RAG를 사전 등록 평가한다.
- **확장 비용 보고:** 기능 3개를 붙이는 동안 공통 장치를 몇 번 고쳤는지, 기능별 비용과 테스트 수.

### 4-5 공개 v0.2 · 추천 모드: 중간 · Codex: 권장

## 6. 5단계 (선택): 서비스화와 모델 비교

| 항목 | 내용 | 승인·비용 |
|---|---|---|
| 5-1 API 서버와 Docker | FastAPI로 라우터를 감싼 API, 재생 데모가 들어 있는 Docker 이미지 | 의존성 추가 |
| 5-2 로컬 대 상용 모델 비교 | 같은 평가로 gpt-oss:20b와 상용 API 1~2개를 비교(정확도, 비용, 지연 시간) | **비용 발생, 사용자 승인 필수** |
| 5-3 관측 가능성 | 실행 기록을 요약하는 간단한 대시보드나 리포트(요청 수, 지연, 실패 유형) | 없음 |

FastAPI·Docker는 채용 키워드 가치가 있다. 시간이 부족하면 5-1만 4단계 안으로 당겨서 하는 방안도 있다.

| 4-4 사전 등록 커밋 전 | **필수** | 기능 평가 기준(문서 품질, 인용 검증) |
| 각 공개 전 | 권장 | 공개 안전성, 재배포 조건 |

## 8. 위험과 중단 기준

| 위험 | 대응 |
|---|---|
| 범위가 계속 커짐 | 기능마다 최소 버전과 완료 기준을 먼저 정하고, 넘치면 다음 버전으로 미룬다. 4·5단계 항목은 각각 빼도 앞 단계 결과가 완결되게 만든다 |
| 3-1에서도 LLM이 기준선을 못 이김 | 그대로 보고하고 "검증 도구 + LLM 보조"로 정의한다. 4단계(문서, RAG)에서 LLM 역할을 보여 준다 |
| 로컬 모델이 문서·RAG에 약함 | LLM이 쓰는 부분을 짧게 제한한다. 그래도 부족하면 5-2(상용 비교)를 앞당길지 사용자에게 묻는다 |
| 새 의존성이 늘어 재현이 어려워짐 | 핵심은 표준 라이브러리로 유지하고, 확장 기능은 선택 설치 묶음과 고정 버전으로 둔다 |
| 재배포 조건상 데모 데이터를 못 넣음 | 데모를 합성 데이터나 수치 일부 마스킹으로 대체한다 |
| 자유 표현 질문 작성이 또 한쪽에 치우침 | 작성자를 섞고 기록한다. 사용자가 쓴 질문을 따로 보고한다 |

## 9. 사용자가 정할 것
