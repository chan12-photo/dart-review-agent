# 범위 문서 (초안): 공시 재무 변화 검토 Agent

- 상태: **확정 (2026-10-07)**. 구현 전. 저장소 `dart-review-agent`
- 근거: 2026-10-07에 실제 OpenDART API로 확인한 사실(5절)과 지금까지의 검토. 확인하지 못한 것은 "미확인"으로 적는다.

## 1. 한 줄 정의
상장사의 재무 수치가 **기간 사이에 어떻게 바뀌었는지**, 사용자의 질문에 맞는 계정·기간·기준으로 찾아 비교한다. 비교 기준이 맞지 않으면 **비교하지 않고 이유를 밝히는** 로컬 도구다.

## 2. 사용자와 대표 요청
**사용자:** 기업 재무를 확인해야 하는 사람 (재무·IR·리서치 담당자, 기업 분석을 하는 학생). 지금은 DART 화면과 엑셀을 오가며 숫자를 옮기고 기준을 눈으로 맞춘다.

**대표 요청 (첫 버전에서 처리할 것)**
1. "삼성전자 2025년 매출액이 전년보다 얼마나 늘었어?" → 연결 기준 비교표
2. "삼성전자 2025년 3분기말 자산총계를 작년 3분기말과 비교해 줘." → **작년 3분기 보고서를 추가로 조회**해야 함 (분기 보고서의 재무상태표 "전기"는 작년 3분기말이 아니라 작년 연말)
3. "삼성전자 2025년 3분기까지 영업활동현금흐름이 얼마야?" → 현금흐름표의 "당기" 칸이 이미 누적이라는 점을 반영
4. "연결 매출이랑 별도 매출 차이가 왜 이렇게 커?" → 두 기준을 **나란히 보여 주되 합치지 않음**
5. "2014년 매출 비교해 줘." → **데이터 없음**(2015년 이전 미제공)을 오류와 구분해 답함

## 3. 출력
- **비교표:** 회사, 보고서(접수번호), 재무제표 구분, 연결/별도, 계정ID·계정명, 기간 라벨, 금액, 비교 금액, 변화량·변화율, 통화, **검증 상태**
- **검증 상태:** `비교 가능` / `비교 불가(이유)` / `데이터 없음` / `확인 필요(사람)`
- **짧은 설명:** 확정 사실(도구 결과)과 해석(LLM)을 구분. **모든 숫자는 도구 결과에서만** 나오며, 답변 속 숫자는 출력 전에 도구 결과와 대조한다.

## 4. 첫 버전 범위
| 포함 | 제외 (나중에 또는 안 함) |
|---|---|
| 개발용 회사 3곳: 삼성전자(제조), 카카오(플랫폼), 셀트리온(바이오). 최종 평가용 회사 4곳은 봉인: NAVER, CJ제일제당, 이마트, LG에너지솔루션 | 금융사, 금융 부문이 섞인 회사(예: 현대자동차) |
| 계정 6개: 매출액, 영업이익, 당기순이익, 영업활동현금흐름, 자산총계, 부채총계 | 전체 계정 자유 질의 |
| 2023~2025 사업보고서 + 분기·반기 보고서 | 2015년 이전 (API 미제공) |
| 구조화 재무제표 API만 사용 | **공시 원문 검색(RAG)**: 2단계에서 "변화 이유" 기능으로 추가 |
| CLI와 Markdown 보고서 | 웹 화면 (최소 시연 버전 이후 필요하면) |
| 로컬 모델 gpt-oss:20b, 한국어 답변 지시 | 상용 API 비교 (선택, 사용자 승인 후) |

## 5. 2026-10-07에 실제로 확인한 사실 (가능성 근거)
- 인증키로 회사 목록(119,558개, 상장 3,998개)과 삼성전자 재무제표 조회 성공.
- 2025 사업보고서: 연결 229행, 별도 141행. 같은 매출액이 **연결 333.6조, 별도 238.0조**.
- 3분기 보고서는 **재무제표 종류마다 칸 구성과 의미가 다르다**:
  - 손익계산서: 당기 3개월(86.1조), 당기 누적(239.8조), 전년 같은 분기, 전년 누적을 모두 제공
  - 현금흐름표: 당기와 전년 같은 분기만 있고, 이름은 "3분기"지만 둘 다 누적
  - 재무상태표: "전기"가 작년 3분기말이 아니라 작년 연말
  - (정정 2026-10-07: 처음에는 "분기 보고서에 전년 비교값이 비어 있다"고 적었으나 틀렸다. 첫 행(재무상태표)의 칸만 보고 판단한 실수였다)
- 표준계정코드가 없는 계정이 실제로 있다 (연결 5개, 예: 단기차입금).
- 회사가 없거나 2015년 이전이면 똑같이 `013 조회된 데이타가 없습니다`가 온다.
- 공시 원문은 압축된 XML (본문 7.5MB, 136개 절, "경영진단" 절 포함).
- 후보 7곳 모두 계정 6개를 표준계정ID로 제공한다. 다만 **계정 이름이 회사마다 다르다**.
  - 카카오·NAVER는 매출을 "영업수익"으로, CJ제일제당은 "수익(매출액)"으로 표시한다.
  - 여러 회사가 "당기순이익(손실)", "영업활동으로 인한 현금흐름"을 쓴다.
  - 표준코드가 없는 계정은 연결 기준으로 셀트리온 36개, 이마트 24개, 카카오 22개다.
- **미확인:** 표준코드 없는 계정이 질문 대상이 되는 빈도, 호출 제한의 실제 수치, 원문·수치 재배포 조건.
- **추가 확인 (2026-10-07, 로드맵 1-2):** 정정공시가 있으면 재무제표 API는 마지막 정정본을 돌려준다(카카오 공시 목록으로 확인). 같은 기간 값이 나중 보고서에서 재작성되는 경우(카카오, 셀트리온)와 계정ID가 잘못 표기된 경우(카카오 2023 분기 매출)가 있다. 자세한 근거는 [DATA_NOTES.ko.md](DATA_NOTES.ko.md).

## 6. 역할 분담
| 주체 | 맡는 일 |
|---|---|
| 일반 프로그램 | API 호출·캐시, 금액 계산, **비교 가능성 규칙**(같은 연결/별도, 같은 기간 종류, 3개월과 누적 구분, 같은 통화, 0으로 나누기), 오류와 "데이터 없음" 구분 |
| LLM | 사용자의 표현을 계정·기간·기준으로 해석, 결과 설명 문장 |
| **Agent 판단** (필요할 때만) | 추가로 무엇을 조회할지 (전년 같은 분기 보고서, 다른 기준), 표준계정코드가 없을 때 이름으로 후보 찾기, 요청이 모호할 때 되묻기 |
| 사람 | 회계적 의미와 중요성 판단, `확인 필요` 항목 |

**정직성 원칙:** 고정된 순서로 충분한 요청은 고정 순서로 처리한다. Agent가 매번 같은 순서로만 도구를 부른다면 Agent라고 부르지 않는다.

## 7. 평가 설계 (실패 원인을 분리)
1. **도구·규칙 정확도:** 계산과 비교 가능성 규칙을 단위 테스트로 검증한다. 목표 100%.
2. **정답 근거를 직접 준 경우:** 올바른 행을 모델에게 주고, 계정·기간·기준을 맞게 해석해 답하는지 본다. 모델 자체의 한계를 측정한다.
3. **전체 흐름:** 질문부터 도구 선택, 최종 답까지.
4. **기준선 비교:** 키워드로 회사·연도·계정을 뽑아 고정 순서로 조회하는 **규칙 기반 파이프라인**과 비교한다. Agent가 이 기준선을 이기지 못하면 그대로 보고하고 설계를 바꾼다.

- **사례 유형:** 정상 비교 / 연결·별도 함정 / 3개월·누적 함정 / 전년 분기 추가 조회 / 표준계정코드 없음 / 비교 불가(거절이 정답) / 데이터 없음 / 모호한 질문(되묻기가 정답)
- **정답 만들기:** 질문은 사람이 쓰고, 정답 숫자는 API 원본에서 코드로 계산한다(계산 규칙도 함께 공개).
- **분리 원칙:** 개발용 회사와 최종 평가용 회사를 나눈다. 최종 평가 세트는 사전 등록하고 봉인한다.
- **지표:**
  - 숫자 일치
  - 기준(연결/별도, 기간) 정확도
  - 거절·되묻기 정확도
  - **근거 없는 숫자 0건**
  - 잘못된 도구 호출
  - 지연 시간, 요청 수

## 8. 보장하는 것과 보장하지 않는 것
- **보장:**
  - 답변의 모든 숫자는 도구 결과(접수번호·계정·칸)로 추적된다.
  - 비교 가능성 규칙을 어긴 비교는 출력되지 않는다.
  - 같은 캐시로 다시 돌리면 같은 결과가 나온다.
- **보장하지 않음:**
  - 회계적 해석의 정확성
  - 캐시 이후의 정정공시 반영
  - 금융사 등 범위 밖 회사
- **재현:** API 응답을 받은 시각과 해시를 함께 저장하고, 평가와 데모는 저장된 응답으로 재생한다. **인증키 없이도 데모가 돌아간다.**
- **보안:**
  - 인증키는 `~/.config/opendart/api_key`에서만 읽는다.
  - 로그와 저장소에 키가 남지 않게 공개 안전성 검사에 `crtfc_key` 패턴을 추가한다.

## 9. 재사용 후보 (기존 local-agent-lab)
- 도구 인자 검증, 호출·시간 제한 → API 호출 정책 (허용된 엔드포인트만, 호출 예산)
- 실행 기록, 재생 → API 응답 캐시와 재생 데모
- 사전 등록 평가 방식, 공개 안전성 검사
- **재사용하지 않음:** 파일 읽기·검색 도구 (이 제품에는 필요 없음)

## 10. 진행 순서와 기준
| 단계 | 내용 | 다음으로 넘어가는 기준 |
|---|---|---|
| 가능성 검증 | 회사 3곳 × 2년, 개발용 질문 10~12개, 평가 1~3번 | 도구·규칙 100%, 정답 근거 제공 시 80% 이상, 근거 없는 숫자 0건 |
| 최소 시연 | 질문 → 조회 → 규칙 검증 → 비교표·설명, 재생 데모 | 대표 요청 5개를 처음부터 끝까지 처리 |
| 제출 버전 | 사전 등록 평가, 기준선 비교, 실패 사례 정리, README | 남이 키 없이 재생 데모를 돌리고 결과를 검토할 수 있음 |
| (2단계) | 공시 원문에서 "변화 이유" 근거 찾기 (RAG) | 1단계 완료 후에만 착수 |

**중단·전환 기준**
- 정답 근거를 줘도 60% 미만이면 → 모델이 병목. 상용 API 비교 검토(승인 필요) 또는 범위 축소.
- Agent가 기준선을 끝내 이기지 못하면 → "검증 도구 + LLM 설명"으로 정직하게 재정의.
- 회사별 계정 차이가 너무 커서 계정 6개도 안정적으로 맞추지 못하면 → 회사 수를 줄이고 원인을 기록.

**일정:** 가능성 검증 후에 실제 속도로 다시 산정한다 (지금 확정하지 않음).

## 11. 결정 사항 (2026-10-07)
1. 저장소: 새 저장소 `dart-review-agent`
2. 개발용 회사: 삼성전자, 카카오, 셀트리온 / 평가용(봉인): NAVER, CJ제일제당, 이마트, LG에너지솔루션
   - 봉인 전 회사 선정 과정에서 평가용 4곳의 2025년 사업보고서·3분기 보고서에 대해 **계정 행 수와 계정 이름만** 확인했다. 금액은 보지 않았다.
3. 작업 시간: 사용자의 토큰이 충전되는 대로 최대한 진행 (세션 단위로 끊기 쉽게 작업을 나눈다)
4. 상용 API 비교: 지금은 제외 (필요하면 승인 후)
