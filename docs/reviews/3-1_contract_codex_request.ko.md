### Part A. 3-1 평가 계약 (`docs/EVAL_CONTRACT_3-1.ko.md`)

1. **순서(1절):** 봉인 데이터를 보기 전에 계약, 제품, 질문을 고정하는 순서가 실제로 지켜질 수 있는가. 사용자 질문을 블라인드로 받는 방법(4.3)에 빈틈이 있는가. ⑤에서 정답과 제품 규칙이 다를 때 사람이 판정하는 방식이 결과를 유리하게 바꿀 여지가 있는가.
2. **측정과 기준(8·9절):** 결과 칸의 정의에 빈틈이나 겹침이 있는가. 예를 들어 다음 경우가 어느 칸에 들어가는가.
   - 거절이 정답인데 다른 이유로 거절함
   - 되묻기가 정답인데 답함
   - 출력 숫자 검사로 막힘

   합격 기준(해결률 70%, 비용 25%, 범위 밖 75%, 틀린 수치 답 0)이 "전부 거절"이나 "전부 되묻기" 같은 전략으로 통과될 수 있는가. 36문항이라는 표본 크기로 이 기준이 의미가 있는가.
3. **LLM 필요성:** 개발 중에 규칙이 상대 연도와 약칭을 읽게 되면서, 모델만 맞히는 질문이 한 개로 줄었다(v4 보고서). 이 상태에서 해석 기여 표와 교차 확인 효과 표가 LLM의 역할을 공정하게 보여 주는가. 결과가 미리 정해지는 설계인가.
4. **평가 모드와 확장성(7절, A4):** 다음 경계가 명확하고 우회할 수 없는가.
   - "설정 변경"과 "코드 수정"을 나누는 기준
   - 비지원 계정 사전을 개발 캐시로만 만드는 것
   - 봉인 회사 별칭표(4.4)를 미리 고정하는 것
5. **질문 계약(4.2):** 다음 항목이 채점과 일관되는가: 오타 제외, 그룹 이름 되묻기, 기준 날짜 = 수집일, "직전 분기"의 1분기 처리.

### Part B. 코드 (직전 검토 이후 전부)

1. **3-0a·3-0b 수정:** B1~B7과 C1~C3가 실제로 고쳐졌는가. 반례를 다시 시도해 보고, 새 우회로가 있는지 확인해 줘.
2. **값 조회(`dart_review/tools.py` `lookup_value`, `render.py`):**
   - 재작성 확인(다음 해 같은 종류 보고서)이 맞는가.
   - "확인하지 않았다" 노트가 정확한가.
   - 상태값(값 확인, 조회 불가, 범위 밖)과 결정 매핑이 채점기(`eval/scoring.py`)와 맞는가.
3. **회사 이름(`dart_review/company_names.py`, `companies.py`, 사전 두 개):**
   - 가장 긴 이름 규칙에 반례가 있는가. 별칭이 다른 회사명의 일부인 경우(예: "삼전순약")가 대표적이다.
   - 그룹 이름 처리와 여러 회사 판별에 반례가 있는가.
   - 회사 집합을 바꾸는 방식(`using_company_set`)에서 상태가 새거나, 개발 모드에서 봉인 회사가 조회될 길이 있는가.
4. **해석(`dart_review/baseline.py`, `crosscheck.py`):**
   - 비교 신호어 정규식이 조회와 비교를 잘못 가르는 경우가 있는가.
   - 상대 연도("작년"과 "재작년" 구분)와 기본 연도(4월 1일 기준)에 문제가 있는가.
   - 계정 여러 개 판별, `canonical` 판별 결과로 분기하는 방식, 모델만 방식(`use_rules=False`)이 맞는가.
5. **평가 장치(`eval/judge.py`, `run_eval.py`, `rescore.py`, `build_lookup_gold.py`):**
   - 결과 분류와 판정 보류 조건이 맞는가.
   - 조회 정답 생성기의 독립성이 유지되는가. 제품 코드에 기대는 부분이 있는가.
   - 재채점 경로 통일이 맞는가.
6. **테스트 품질:** 공허하게 통과하는 테스트가 있는가. 새 테스트들이 옛 코드에서 실제로 실패하는가(보고서에 일부 확인 기록이 있다).
