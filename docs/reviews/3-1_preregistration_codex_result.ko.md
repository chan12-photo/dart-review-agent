## 사전 등록 전에 고칠 것

### 1. [치명] 봉인 평가가 끝난 뒤 사람 검토지 생성에서 중단된다

- 위치: `eval/finalize.py:29-36,55-69,89-93`; 호출부 `eval/run_eval.py:406-416`.
- 근거: `finalize._gold()`는 `dev_gold.json`과 `dev_lookup_gold.json`만 읽는다. 봉인 정답 `eval/sealed_3-1/gold.json`을 읽지 않으므로 첫 봉인 ID `C01`을 검토지에 넣을 때 `KeyError`가 난다. 모델 없이 최소 가상 case로 `finalize.review_sheet([{"id":"C01", ...}])`를 호출해 **`KeyError 'C01'`**을 재현했다. 실행기는 모든 case와 요약을 쓴 *다음* `write_review_files`를 부르므로, 36건에 모델 비용을 쓴 뒤 CLI가 오류로 끝나고 정규 검토지가 빠질 수 있다. `--out`은 이미 만들어져 같은 경로의 정상 재실행도 거부된다.
- 제안: `run_eval.load_questions`에서 선택된 정답을 `write_review_files`/`review_sheet`에 명시적으로 넘기거나, `run.json.question_set`으로 해당 정답을 로드하도록 최소 수정한다. 개발 세트와 봉인 세트 각각 임시 출력 경로에서 검토지·템플릿까지 만들어지는 오프라인 테스트를 추가한다. 평가기 고정 파일을 고치는 것이므로 P 이후 예외 수정의 이유·diff·새 커밋/고정 기준을 공개 기록하고, 제품 판정 코드나 gold는 바꾸지 않는다. **이 결함이 해소되기 전에는 모델 실행을 시작하지 않는다.**

### 2. [중요] 엄격 판정기가 세 실행의 봉인 질문·정답 해시를 서로 대조하지 않는다

- 위치: `eval/judge.py:113-129,149-161`; 해시 생성 `eval/run_eval.py:230-243`.
- 근거: 실행기는 `set_questions`, `set_gold`를 기록하지만 `check_runs`의 `shared`에는 빠져 있다. `check_contract`는 **crosscheck 한 실행의** 해시만 현재 파일과 비교한다. 임시 메타 객체로 baseline의 두 봉인 해시를 가짜 값으로 바꾸고 다른 조건을 같게 둔 결과, `check_runs(...)`가 **`[]`**을 반환했다. 정상적인 깨끗한 트리·동일 커밋 실행에서는 추적된 두 파일이 달라지기 어렵다. 이 문제는 특히 잘못 작성되거나 교체된 실행 메타를 엄격 판정기가 검출하지 못하는 **로그 검증의 빈틈**이다.
- 제안: `set_questions`, `set_gold`를 세 실행 간 필수 동일 해시로 검사하고 세 실행 각각의 기록 해시를 현재 파일과 대조한다. 한 메서드의 해시만 다르게 만든 작은 음성 테스트를 추가한다. 이는 판정기 수정이므로 위 1번과 함께 P 이후 평가기 변경으로 명확히 기록한다.

### 3. [중요] 사람 검토 결과가 해당 실행에 강하게 묶이지 않는다

- 위치: `eval/finalize.py:105-124`; `eval/judge.py:170-185`.
- 근거: 판정기는 `final`의 ID와 `automatic_passed`만 case와 대조하며 `final.mode`, 질문 본문, 답변, case 파일의 해시를 확인하지 않는다. 36개 ID를 가진 임시 객체에서 `final.mode="unrelated-run"`으로 하고 자동 점수를 동일하게 주었는데, `check_runs`와 `check_contract` 모두 **`[]`**였다. 두 실행의 자동 통과 벡터가 우연히 같으면 다른 실행에 작성한 사람 판정을 붙일 수 있다. 이는 엄격 모드의 사용자 확인을 형식적으로만 만족시킬 위험이다.
- 제안: 최종 검토 파일에 실행 메타/`cases.jsonl`의 SHA-256 및 mode를 기록하고 판정 시 확인한다. 최소한 mode와 case 해시가 다른 검토 파일은 보류해야 한다. 사람 판정 파일의 생성·확정·수정 절차와 버전도 사전 등록한다.

### 4. [중요] 계약의 실제 통과 분모와 숫자 오류율 설명이 현 질문 세트와 다르다

- 위치: `docs/EVAL_CONTRACT_3-1.ko.md:194-205,228-237`; 실제 분모 계산 `eval/judge.py:260-283`.
- 근거: gold 36건은 **답이 있는 질문 23건**(값 확인 11, 비교 가능 9, 확인 필요 1, 나란히 표시 2), 거절 10, 되묻기 3이다. A 16건 중 C04·C07·C12는 거절이다. 계약의 `A16+B10=26`, 최소 `20/26`은 현 세트에 맞지 않는다. 수치 오답 0, 비용 ≤25%, 해결률 ≥70%를 동시에 적용하면 23건 중 최소 **18/23 = 78.26%**를 해결해야 한다. 17/23은 비용 6/23=26.09%여서 실패한다. 코드의 분모는 gold 결정으로 동적 계산하므로 **코드의 20/26 하드코딩 오류는 아니다**.
- 같은 문서 11절의 “36문항 0건이면 95% 상한 약 8%”는 36건 모두가 해당 오류에 노출된 독립 시행이라는 조건에서만 맞는다(`1-0.05^(1/36)=7.98%`). 수치 답을 요구하는 23건을 분모로 하면 모두 실제로 답했고 오류 0이어도 약 **12.21%**다. 실제 답변 건수가 더 적으면 상한은 더 커진다. 거절·되묻기를 수치 답의 안전성 표본으로 세면 안 된다.
- 제안: 사전 등록 문구를 `23건, 최소 18건`으로 고치고, 11절의 약 8%는 “36건 전체 질문에서 특정 오류 0건”이라는 조건을 명시하거나 수치 답변 분모별 상한으로 고친다. **70%·25%·0건이라는 사용자 결정 자체는 바꾸지 않는다.**

### 5. [중요] “잘못된 수치 답”과 본문 설명 실패가 한 칸으로 합쳐진다

- 위치: `docs/EVAL_CONTRACT_3-1.ko.md:183-190`; `eval/HUMAN_REVIEW.ko.md:11-27`; `eval/judge.py:90-104`; `eval/finalize.py:105-117`.
- 근거: 계약은 잘못된 수치 답을 값·기간·기준·회사·계정 오류 등으로 정의한다. 그러나 `body_ok=false`가 이유 설명 누락 또는 근거 없는 원인 단정처럼 **금액과 기간은 맞는** 사례여도 `reviewed_passed=false`가 되고, 답 상태라면 `outcome`이 무조건 `잘못된 수치 답`을 반환한다. 임시 답 `{status:"확인 필요"}`, gold decision=`answer`, `passed=False`의 결과가 실제로 `잘못된 수치 답`이었다.
- 제안: 사람 검토 실패를 숫자·대상·기간 오류와 설명 품질 실패로 구분해 기록하고, 기준의 “잘못된 수치 답 0”에 무엇이 들어가는지 실행 전에 확정한다. 설명 실패도 불합격으로 만들 수 있으나, 정확한 수치 오류 수로 보고하면 안 된다. 기존 사람이 읽는 기준을 실행 결과를 본 뒤 완화하지 않는다.

### 6. [중요] 결과 열람 전에 사람 검토의 운영 규칙을 더 고정해야 한다

- 위치: `eval/HUMAN_REVIEW.ko.md:5-8,47-69`; `docs/EVAL_CONTRACT_3-1.ko.md:115-130,205-216`; `eval/finalize.py:84-86,140-144`.
- 근거: Claude 1차·사용자 확인이라는 역할은 문서에 있지만, 세 방식의 검토 순서, 검토자가 mode/자동 점수/다른 방식 답을 볼지, 중간 검토 파일 수정·재확정 규칙, 동일 case의 서로 다른 실행 결과 연결법은 고정되어 있지 않다. `finalize`는 `final.json`을 덮어쓸 수 있다. 1-5 후 본문 기준 보완 사례도 있어, 실행 뒤 해석 변경의 여지를 줄일 필요가 있다.
- 제안: reviewer/사용자 확인 방식, 방식별 검토 순서와 노출 정보, `human_review.json`/`final.json`의 고유 버전 경로·해시, 재검토는 사유와 전후 판정 동시 보존, 실행 순서 및 동일 질문 재실행 금지를 ⑥에 적는다. 검토자는 먼저 각 답의 원문·근거로 판정하고 다른 방식의 점수는 그 뒤 확인하는 순서가 좋다. 평가 도중 같은 36건으로 프롬프트를 조정하지 않는다.
