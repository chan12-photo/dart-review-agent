## 요청문

`AGENTS.md`를 따른다. 인증키, OpenDART API, Ollama는 쓰지 않는다. 추적 파일은 수정하지 말고, 결과는 `docs/reviews/D4_contract_codex_result.ko.md`에 저장해 줘. 칭찬은 필요 없다. 틀렸거나, 근거가 약하거나, 결과를 실제보다 좋게 보이게 하는 것만 적어 줘. 발견마다 다음을 적어 줘.
- 심각도(치명/중요/사소)
- 위치(파일:줄)
- 근거(명령과 결과)
- 제안

그리고 "평가 전에 고칠 것"과 "기록만 할 것"을 나눠 줘.

대상은 `6e8528d^..HEAD`(v0.2 전체)와 `docs/EVAL_CONTRACT_D4.ko.md`, `eval/documents_2026-10-10/`이다.

### Part A. 표시 없이 틀리거나 빠지는 경로 (가장 중요)

v0.2의 원칙은 "숫자를 고치지 않고, 의심되는 칸은 '확인 필요'로 표시하고, 읽지 못한 것은 경고 없이 빠뜨리지 않는다"이다. 이 원칙이 깨지는 코드 경로를 찾아 줘. 개발 중에 실제 문서에서 찾은 것은 커밋 메시지에 있다(단위를 앞 쪽의 행 이름에서 가져옴, 같은 계정명 두 번, 중첩 열의 기간 배정, 주석 제목을 재무제표로 읽음, 주당이익 단위 등). 같은 종류의 경로가 남아 있는지 봐 줘.

1. `dart_review/documents/statement.py`, `table.py`, `verify.py` (규칙 읽기와 검사): 값이 다른 칸·다른 기간·다른 재무제표로 들어가거나, 금액이 버려지는데 `problems`나 `unplaced`에 남지 않는 경로.
2. `dart_review/documents/ai_reader.py`, `vision.py` (AI 읽기): 모델이 읽은 숫자가 원본 증거 없이 "검사 통과"가 되는 경로. `_add_row`, `_add_row_by_tokens`, `_existing_row`, `Header.period_of`, 띠 겹침 처리, 미청구 금액 보고(`_is_amount_like`)를 봐 줘. 특히 다음을 확인해 줘.
   - 증거 숫자를 "같은 줄"이 아닌 곳에서 찾아 통과시키는 경우
   - 사진 경로(`_read_with_model_structure`)에서 OCR 토큰이 띠 안 어디에든 있으면 통과하는 것이 얼마나 약한지(같은 숫자가 띠 안 다른 줄에 있을 때)
   - 모델이 계정명을 틀리게 읽었을 때 텍스트 PDF는 원본 계정명을 쓰는데, 그 판단(`_match_line`)이 틀린 줄을 고를 수 있는지
3. 소계 검산(`verify._subtotals`, `_collapsed`): 틀린 칸을 표시하지 못하는 경우(검산을 건너뛰는 조건이 너무 넓은지), 반대로 우연히 맞아 떨어져 틀린 칸이 통과하는 경우.
4. 테스트가 실제로 그 경로를 막는지. 새 테스트가 고치기 전 코드에서 실패하는 것을 확인했다고 커밋에 적었다. 표본으로 두세 개를 직접 확인해 줘(`git stash`로 소스만 되돌리는 방식).

### Part B. API 서버 (`dart_review/server.py`, `upload.html`)

1. 업로드 처리: 크기 제한(`file.read(MAX+1)`), PDF 판별, 파일 이름, 작업 ID 검사, 경로 조작, 지울 때의 경쟁 상태.
2. 작업 실패 시 문서 내용이 오류 메시지나 기록에 남는지.
3. 127.0.0.1 기본값과 인증 없음이 README와 화면에 분명한지. 업로드 화면의 XSS(보고서 JSON의 계정명을 DOM에 넣는 방식).
4. SQLite 접근이 작업 스레드와 요청 스레드에서 안전한지.

### Part C. 개발 측정 기록 (`eval/measure_documents.py`, `eval/documents_2026-10-10/`)

1. 분류 규칙(`classify`)이 틀린 칸을 맞음으로 넣는 경우. 예: `dart_value`(같은 값, 다른 계정명)의 우연한 일치, `pdf_only`가 기간이나 단위 오류를 덮는 경우, `name_key`의 정규화가 너무 느슨한 경우.
2. 빠진 칸(`dart_not_extracted`)의 정의가 빠진 것을 놓치는 경우(같은 값이 다른 행에 있으면 빠지지 않은 것으로 센다).
3. `REPORT.ko.md`의 숫자와 주장이 `rules.json`, `ai.json`과 맞는지, "평가 아님"이 분명한지, 결과를 좋게 보이게 하는 표현이 있는지.
4. 규칙 방식 측정은 오프라인으로 다시 돌릴 수 있다. PDF는 `~/Desktop/감사보고서/`에 있다. 측정에 쓴 6개 파일(`eval/measure_documents.py`의 `DOCUMENTS`)만 읽어 줘. 그 폴더의 다른 파일은 열지 말아 줘.
   - `python3 eval/measure_documents.py --pdf-dir ~/Desktop/감사보고서 --reader rules --out /tmp/d4check` (`.venv`에 `pip install -e '.[docs]'`가 필요하다. 사진 PDF는 Tesseract가 필요하다)
   - 기록된 `rules.json`과 같은 결과가 나오는지 봐 줘. AI 방식은 Ollama가 필요하므로 돌리지 않는다.

### Part D. D4 계약 (`docs/EVAL_CONTRACT_D4.ko.md`)

1. 지표 S1·S2와 기준이 목적("표시 없이 틀린·빠진 숫자")을 제대로 재는가. 표시의 정의(칸 표시 또는 재무제표 문제 목록)가 너무 넓어서, 문제 목록에 한 줄만 있으면 그 재무제표의 모든 빠진 칸이 "표시됨"이 되는 일은 없는가.
2. 정답 규칙의 약점: OpenDART와 인쇄본이 다른 경우, 합성 스캔의 정답을 텍스트 PDF에서 가져오는 것, 사람 검토를 Claude가 1차로 하는 것.
3. 회사 선정 규칙(고정 시드, 금융업 제외)의 편향, 문서 수 10곳이 충분한지.
4. 개발 문서와 평가 문서의 분리. 개발 중에 본 회사(삼성전자, NAVER, 한화시스템, 포스코, LG에너지솔루션)가 다시 들어올 수 있는 경로가 있는가.
5. 순서(계약 → Codex → 사용자 결정 → 문서 준비 → 정답 → 사전 등록 → 실행)에서 결과를 보고 무엇을 고를 수 있는 틈이 있는가.

## 이미 알고 있는 것 (다시 적지 않아도 됨)

- 자본변동표는 읽지 않는다(문제로만 표시). 범위 밖이다.
- 사진 PDF는 규칙 방식으로 읽지 못한다(제목을 찾지 못했다는 문제로 표시). AI 방식에서만 읽는다.
- `--reader ai`가 기본값이고 로컬 Ollama `qwen3-vl:8b`가 필요하다. 서버의 `/health`가 준비 여부를 알려 준다.
- 개발 측정은 개발에 쓴 문서라 평가가 아니다.
- 손익계산서·포괄손익계산서는 소계 검산을 하지 않는다(비용에 부호가 없다).
