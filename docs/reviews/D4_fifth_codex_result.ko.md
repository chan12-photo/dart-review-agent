## ④ 고정 전에 고칠 것

### 1. [치명] 쉼표 없는 금액을 사람 검토로 보낸 뒤, 그 금액을 정답에 추가할 수 없다

- **위치:** `eval/d4_gold.py:155-169, 208-210, 329-341, 410-416`; `docs/EVAL_CONTRACT_D4.ko.md:141-155`.
- **근거(명령·결과):** `./.venv/bin/python - <<'PY'`에서 합성 `손익계산서`, 단위 원, 인쇄 줄 `매출액 1000 2000`을 `cells_of()`에 주자 `cells=0`, `no_grouped_amounts` 한 건이 나왔다. 그 결정에 인쇄 그대로 `printed="1000", value=1000`인 `add` 칸을 넣어 `apply_mapping()`하면 `ValueError: mapping:n1: printed '1000' is not an amount or '-'`가 난다. `_checked_cell()`의 허용 형식에 새 `UNGROUPED`가 빠졌다. 쉼표 있는 행과 `기타 1000 -`를 섞어도 `ungrouped_amount` 항목은 나오지만 동일한 추가 검사가 막는다. 반면 위 항목을 합성 `confirmed` 매핑표에서 `ignore`로 정하고 제품 보고서도 표를 놓친 경우, `score()`는 `gold_cells=0`, `S1=L1=S2=0`, `official_ready=True`였다. 이는 사람이 잘못 `ignore`를 확정한 반례이며, 자동 검사가 그 실수를 막지 못한다는 뜻이다.
- **제안:** `_checked_cell()`이 `UNGROUPED` 인쇄값을 받아 부호·단위·자리 검사를 하게 한다. 숫자 있는 표의 `no_grouped_amounts`/`ungrouped_amount`를 모두 `ignore`하여 정답 칸이 0개가 되는 경우는 공식 판정을 막거나, 원본의 각 숫자 줄을 어떻게 제외했는지 별도 확인을 요구한다. 쉼표 없는 금액으로만 된 표의 `add → 채점` 회귀를 넣는다.

### 2. [치명] 등록 점검이 R에 커밋된 등록 기록 대신 외부 JSON을 신뢰한다

- **위치:** `eval/d4_preflight.py:91-109, 115-149, 185-206`; `docs/EVAL_CONTRACT_D4.ko.md:47-61`.
- **근거(명령·결과):** `./.venv/bin/python - <<'PY'`로 **임시 Git 저장소와 임시 로컬 bare 원격**을 만들어 P/T, `freeze.json`, 원래 `gold.json`을 커밋했다. `register_record()`로 원래 정답 파일의 객체를 적은 뒤, 정답을 바꿔 커밋 R로 만들고 `d4-registered`를 로컬 원격에 push했다. 진짜 등록 객체를 `check()`에 주면 `registered gold.json ...` 검사 실패로 `ok=False`였다. 그러나 R의 객체로 바꾼 등록 dict를 외부 JSON처럼 전달하면 **동일한 R·태그·환경에서 `ok=True`, 실패 검사 0개**였다. 다른 임시 저장소에서 `register_record(root, "freeze.json", ["README.md"])`도 수용돼 필수 정답 파일 없이 객체 목록이 `freeze.json, README.md`만 남았다. `check()`는 `--register`의 파일 자체가 R에 커밋된 등록 기록인지 확인하지 않는다. `--remote`도 `origin`/GitHub로 제한하지 않아 임시 로컬 경로가 통과했다. 별도 임시 저장소에서 가벼운 태그와 주석 태그는 둘 다 정상 커밋으로 풀리는 것을 확인했다. 태그 이동 뒤 재 push라는 계약의 기지 한계와는 별개의 우회다.
- **제안:** R의 정해진 등록 경로에서 `git show R:<path>`로 등록 기록을 읽고, 전달된 파일의 객체/내용과 대조한다. 필수 등록 파일의 종류·수·경로를 검사한다. ④ 고정 기록에 신뢰할 GitHub 원격 URL을 적고 `check`에서 그 URL 및 `origin`과 대조한다. 임의 로컬 bare 원격과 임의 외부 등록 JSON은 실패해야 한다.

### 3. [치명] 사전 점검 통과가 실제 채점 입력·실행 명령과 연결되지 않는다

- **위치:** `eval/d4_preflight.py:115-170, 184-211`; `eval/d4_score.py:298-345`; `docs/EVAL_CONTRACT_D4.ko.md:30-37, 47-61, 225-230`.
- **근거(명령·결과):** `check()`는 등록된 **파일의 HEAD 객체**만 대조하고, 뒤이어 실행하는 명령의 `--gold`, `--mapping`, `--page-map`, `--report`, `--reader`가 등록 명령·경로를 쓰는지 받지도 검사하지도 않는다. `d4_score.py`도 사전 점검 로그를 받지 않는다. 별도 `/tmp` 합성 `gold.json`·`mapping.json`·`report.json`을 `./.venv/bin/python eval/d4_score.py --gold ... --mapping ... --report ... --out ...`으로 실행했다. 실제 PDF 파일이 **없는데도** 종료코드 0, `source_verified=True`, `official_ready=True`였다. 두 JSON의 임의 문자열 `source.sha256=source_sha256="src"`가 같으면 인정하기 때문이다. 이는 실제 공식 실행을 했다는 주장이 아니라, 현재 CLI가 등록되지 않은 입력과 자기 선언 해시만으로 공식 가능 상태를 낸다는 재현이다.
- **제안:** 등록된 실행 명령·입력 경로/해시를 평가 실행기가 직접 읽어 강제하고, 성공한 preflight의 R·입력 객체·명령을 결과 manifest에 묶는다. 저장 보고서 재채점에도 실제 PDF의 SHA-256과 보고서 생성 기록을 확인한다. 적어도 `source_verified`는 파일을 열어 재계산했을 때만 참으로 쓰고, 출처 필드 문자열의 일치만 확인한 상태는 따로 표시한다.

### 4. [중요] `same_statement`가 실제 인쇄 표와 연결되지 않아 누락 표를 0칸으로 처리할 수 있다

- **위치:** `eval/d4_gold.py:279-286, 386-430`; `docs/EVAL_CONTRACT_D4.ko.md:146-149`.
- **근거(명령·결과):** 합성 정답에 인쇄된 `IS` 한 표와 누락된 `CIS`의 `statement_not_found`를 넣고 `same_statement`를 결정했다. 메모에 “실제 공통 표 여부는 미확인”이라고 적어도 `apply_mapping()`은 `other in printed`만 검사한다. 별도 CIS 정답 칸이나 `unscorable` 표시는 생기지 않았다. IS 한 칸만 제품이 읽은 합성 보고서를 채점하면 `gold_cells=1`, `scorable=True`, `official_ready=True`였다. 진짜 PDF의 한 표가 양쪽을 겸한다면 이 결정은 타당할 수 있다. **그 사실을 결정과 특정 인쇄 표의 연결로 검증하지 못하는 점**이 문제다.
- **제안:** `same_statement`에 겸용이라고 확인한 `statement_id`·쪽 범위·대표 인쇄 행과 근거를 필수로 적고, 적어도 해당 표가 존재하며 누락 종류의 인쇄 행이 그 범위에 있는지 검사한다. 사람이 겸용 여부를 확인하지 못하면 `unscorable`로 남긴다. 결정의 정당성을 코드만으로 확정할 수 없다는 한계도 공식 기록에 표시한다.

### 5. [중요] 사람이 추가한 재무제표의 쪽 범위가 실제 PDF 밖이어도 통과한다

- **위치:** `eval/d4_gold.py:245-250, 313-325, 386-395`; `docs/EVAL_CONTRACT_D4.ko.md:147-155`.
- **근거(명령·결과):** 원래 `BS`가 1~2쪽인 합성 정답에서 누락 `CF`를 `add_statement`로 추가했다. 새 `CF`의 쪽을 2로 두어 기존 표와 겹치게 해도 수용됐고, **999쪽**으로 두어도 `apply_mapping()`이 수용됐다. 이 합성 정답에는 실제 PDF 쪽 수가 기록되지 않아 999쪽 검사가 불가능하다. 서로 다른 표가 같은 쪽의 위아래에 인쇄될 수 있으므로, **경계 쪽 한 장의 겹침 자체를 무조건 오류라고 단정하지 않는다.**

### 8. [중요, 사람 판단의 한계] `row_unit="원"`은 다른 검증 없이 백만원 표의 일반 행 값을 100만 배 바꿀 수 있다

- **위치:** `eval/d4_gold.py:313-347`; `docs/EVAL_CONTRACT_D4.ko.md:155`.
- **근거(명령·결과):** 합성 백만원 표의 일반 `매출액`, `printed="1,000"`, `value=1000`은 `row_unit`이 없으면 `ValueError`다. 같은 칸에 `row_unit="원"` 한 필드를 붙이면 수용된다. 실제 줄에 원 단위가 인쇄됐는지는 `_checked_cell()`이 알 수 없다. 이 예외는 실제 원 단위 행을 사람이 복원하기 위해 계약이 **의도적으로 허용**한 것이다. 사용자가 원본을 확인하면 타당할 수 있으므로 자동 오답이라고 판정하지 않는다.
- **제안:** 확정 매핑표에서 `row_unit`을 쓴 칸은 인쇄된 단위 글자와 쪽·줄을 별도 필드로 남기고 사용자가 직접 확인한다. 이 예외가 기계적으로 검증됐다고 설명하지 않는다.

### 9. [사소, 함수 수준] 열 근거가 없는 쪽의 주석 번호가 “읽지 않은 금액” 경고 후보가 된다

- **위치:** `dart_review/documents/ai_reader.py:219-254, 417-432`.
- **근거(명령·결과):** 합성 머리글 시작점 `[300,400]`, 같은 줄의 당기 금액 `1,000` 오른쪽 끝 350, 주석 번호 `1` 끝 420을 넣자 `_period_edges()`는 `{0:[350]}`을 반환했다. 주석 `1`은 `report=False`일 때 금액 후보가 아니지만 `report=True`일 때 `True`여서 `원본의 금액 '1'를 AI가 읽지 않았다`는 경고 후보가 된다. 4차의 다른 반례(주석과 실제 전기 열의 오른쪽 끝이 겹침)는 그대로 남아 있다. **전체 AI·실제 모델 경로를 실행하지 않았으므로 실제 개발 보고서에 경고가 늘었다고 주장하지 않는다.**
- **제안:** 열 근거가 없는 작은 숫자는 구조화된 금액 경고와 구분해 불확실로 남기고, 실제 작은 금액과 주석 번호가 섞인 가상 페이지로 전체 경로 회귀를 만든다. 경고가 실제로 가리킨 칸과 S2에 미치는 영향을 본 뒤 제품 수정을 결정한다.

## 4차 지적의 재확인과 계약 대조

| 4차 항목 | 현재 재확인 |
|---|---|
| 1 R 고정 | 원래 등록 기록의 금 객체를 바꿔 R을 만들면 점검이 실패했다. 외부 등록 JSON·다른 로컬 원격 우회는 위 2번. 가벼운/주석 태그의 정상 해석은 확인했다. |
| 2 쉼표 없는 수치 | `no_grouped_amounts`와 `ungrouped_amount`로 항목은 생긴다. 그러나 `add`가 실패하고 `ignore` 후 0칸 공식 가능은 위 1번. `회계연도 2025 2024`는 혼합 표에서 `ungrouped_amount` 항목이 되는 과잉 검출도 재현했다. |
| 3 찾지 못한 표 | `ignore`는 허용되지 않고 `unscorable`은 공식 판정을 막는 시험이 통과했다. `same_statement`의 느슨한 연결은 위 4번. |
| 4 매핑 단위·중복 | 정규화한 같은 자리 추가를 거부하는 회귀가 통과했다. 원 단위 사람 선언의 잔여 위험은 위 8번. |
| 5 짝짓기 | 같은 쪽의 틀린 계정명을 우선하여 `L1=1`로 세는 회귀가 통과했다. |
| 6 부호 | `(47)`과 `47`은 서로 가리키지 않도록 분리한 회귀가 통과했다. |

## 개발 기록과 실행 범위

- `./.venv/bin/python -m unittest tests.test_d4_tools tests.test_measure_documents tests.test_documents tests.test_ai_reader tests.test_server`: **137개 통과**. 위 합성 반례는 이 통과와 별개다.
