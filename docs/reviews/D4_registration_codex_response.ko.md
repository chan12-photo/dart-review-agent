### 1.1 위치 검사 (계약 7판 4.6)

- **방식:** 고정 채점기(T)는 계약상 바꿀 수 없다. 그래서 Codex가 제안한 첫 번째 길을 택했다. 같은 저장 보고서에 따로 도는 검사를 공식 절차에 더한다.
  - **등록할 자리** `eval/d4_eval/duplicate_places.json`: 정답에서 (재무제표, 다듬은 계정명, 기간)에 칸이 둘 이상인 곳이다. PDF 글자 층에서 칸마다 인쇄 줄을 찾아 인쇄 순서(쪽, 위→아래)로 적었다. 줄을 하나라도 못 찾으면 만들지 않는다.
  - **검사** `eval/d4_eval/position_check.py check`: 채점기와 같은 방식으로 짝지은 제품 재무제표에서, 그 계정명의 행을 보고서 순서대로 모은다.
    - 행 수가 같으면 k번째 행끼리 비교한다. 값이 다른 표시 없는 칸 수에서 채점기가 그 자리에서 이미 센 칸 수를 빼고, 남은 만큼(0 이상)을 `S1_position`에 더한다. 두 번 세지 않고, 채점기의 S1을 줄이지도 않는다.
      - 예: 두 행이 바뀌면 채점기 0, 위치 2 → 2를 더한다.
      - 예: 두 행에 같은 값이 들어가면 채점기 1, 위치 1 → 더하지 않는다.
    - 행 수가 다르면(빠짐, 나뉨, 더해짐) 사람이 판정한다(`needs_verdict`). 다만 그 자리의 인쇄 값이 제품 칸에 있고 인쇄 값끼리 다를 때만이다.
      - 사람은 채점기가 "맞음"으로 센 칸 가운데 자리가 틀린 칸만 센다. 검사 결과가 행마다 채점기 결과를 보여 주고, 그 수를 넘으면 거부한다.
  - **공식 집계** `eval/d4_eval/official_d4.py`: 공식 S1 = 채점기 S1 + `S1_position`이다. 호출의 `official_ready` = 채점기의 `official_ready`와 `position_ready`가 모두 참일 때다. 묶음 판정은 그 묶음의 모든 호출이 공식 판정 가능일 때만 낸다(계약 5절에 적었다).
- **Codex가 센 58곳보다 넓다:** 66곳(8개 문서)이다.
  - Codex가 센 것은 같은 **쪽**의 묶음이다. 채점기는 같은 쪽 칸이 없으면 **다른 쪽** 칸도 쓰므로(`eval/d4_score.py` `same_place`), 쪽을 넘어도 같은 사각지대가 있다. 두산 10쪽 유동 "충당부채"와 11쪽 비유동 "충당부채" 등 6곳이다. 그래서 자리를 쪽이 아니라 재무제표 단위로 잡았다.
  - 같은 쪽 묶음은 60곳이다. Codex의 58곳은 매핑 적용 전 정답이고 금액 있는 묶음만 센 수다. 60곳은 매핑을 적용한 정답이고 "-" 칸이 든 묶음 2곳을 포함한다(엠엑스로보틱스 "기타금융자산" 전기, 와이솔 "당기손익-공정가치측정금융자산" 당기).
- **시험** (`tests/test_d4_position.py` 22개, `tests/test_d4_official.py` 6개):
  - Codex의 반례(두 행 교환)와 두 쪽에 걸친 교환: 모두 위치 틀림. 끝에서 끝까지(채점기 + 위치 검사 + 집계) 재현하면 채점기 S1 0, `S1_position` 4, 묶음 판정 `not met`이다.
  - 정상 순서: `in_order`
  - 한 행 누락: 채점기는 남은 행을 맞음, 빠진 행을 S2로 센다. 위치 검사는 사람 판정으로 넘기고, 판정 전에는 공식 판정 불가다.
  - "-" 칸으로 옮겨진 값, 표시된 교환(S1에 넣지 않음), 같은 인쇄 값끼리는 바뀔 것이 없음
  - 두 번 세지 않음: 같은 값 두 행(더하지 않음), 위로 옮긴 값과 인쇄되지 않은 값(채점기 1, 더함 1), 표시된 틀린 행과 맞는 행(채점기 몫을 줄이지 않음)
  - 판정 파일 검사: 다른 보고서, 판정자 없음, 필요 없는 자리, 잘못된 값, 채점기가 맞음으로 센 칸 수를 넘는 수
  - 스캔 쪽 번호, 채점기와 같은 재무제표 짝짓기
  - 등록 자리와 정답의 일치. 실제 개발 보고서(네이버)에서 두 칸을 바꾸면 잡는다.
- **설계 중 Claude가 찾아 고친 것 (커밋 전):** 처음 설계에는 두 가지 문제가 있었다. 둘 다 위 규칙으로 고쳤다.
  - "다른 인쇄 행의 값"만 세서, 채점기가 이미 값 틀림으로 센 칸(같은 값이 두 행에 들어간 경우)을 다시 셀 수 있었다.
  - 행 수가 다를 때 사람이 센 수가 채점기·4.5 판정과 겹칠 수 있었다.
- **개발 보고서로 확인:** 개발 문서 5개의 저장 보고서 10개(규칙·AI)에서 62곳 모두 `in_order`였다. 제품이 인쇄 순서대로 행을 낸다는 가정이 개발 문서에서는 맞는다. 평가 문서의 제품 결과는 보지 않았다.
- **한계 (계약 4.6에 적음):** 순서가 인쇄와 다르면 맞는 값도 위치 틀림이 될 수 있다(제품에 불리한 쪽). 새 규칙은 S1을 늘리거나 공식 판정을 막을 수만 있다. 고정 채점기만의 S1도 함께 보고한다.

### 1.2 실행기의 실패 종료값 (`eval/d4_eval/run_d4.py`)

- 호출마다 종료값을 `run_log.jsonl`에 남기는 것은 그대로다. 끝에 성공 수와 실패한 호출(이름, 종료값)을 `run.json`에 적는다. 실패가 하나라도 있으면 종료값 1로 끝난다. 나머지 호출은 계속 돈다(계약 7: 모델 서버 장애 판단은 사람이 기록을 보고 한다).
- 시험(`tests/test_d4_run.py`, 가짜 채점기 호출, 제품은 돌지 않음):
  - 모두 성공하면 0
  - 둘이 실패하면 1이고, `failed`에 두 이름이 남고, 16회 모두 호출된다.

### 1.3 점검 로그 위치와 실행 절차 (`docs/D4_RUN_PROCEDURE.ko.md`)

- Codex의 제안대로, 점검 로그를 아직 없는 실행 폴더의 **형제** 경로(`~/D4_official/run1.preflight.json`)에, 등록 작업 폴더 **밖**에 쓴다. 실행 폴더의 새 폴더 조건은 그대로다.
- 더 막은 것: 실행기가 `--preflight`로 로그를 받는다. 다음을 모두 확인한 뒤에만 실행하고, 로그의 SHA-256을 `run.json`에 적는다. 하나라도 아니면 아무것도 실행하지 않는다(종료값 2). 시험이 있다.
  - 로그가 작업 폴더 밖이다.
  - 모든 항목이 통과했다.
  - 지금 HEAD를 점검했다.
  - 작업 폴더가 여전히 깨끗하다.
  - 실행 폴더가 작업 폴더 밖이다.
- **Claude가 더 찾은 것 (점검):** 고정 도구의 사용 예시대로 `python eval/d4_preflight.py check`를 하면 `ModuleNotFoundError: No module named 'dart_review'`로 멈춘다. 제품이 가상환경에 설치돼 있지 않고, 스크립트 실행은 `eval/`만 경로에 넣기 때문이다. 개발 저장소에서 실패하는 점검(가짜 등록 기록, 없는 원격)으로 확인했다. `python -m eval.d4_preflight check`로 작업 폴더에서 실행하면 "dart_review imported from this checkout"를 통과한다. 틀린 결과가 아니라 멈추는 문제이고, 고정 도구는 바꾸지 않는다. 절차서와 계약 1.2에 모듈 실행으로 적었다.
