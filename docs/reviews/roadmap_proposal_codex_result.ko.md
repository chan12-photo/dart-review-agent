## 1. 판단 요약

**프로젝트를 계속할 근거는 있다. 다만 제안 전체를 그대로 승인하기보다, 아래 결함과 평가 설계를 정리하고 v0.1까지를 먼저 확정하는 편이 낫다.**

1. 저장된 핵심 점수는 맞다. 근거 제공 1/13, 전체 흐름 2/13, 기준선 25/26, 에이전트 23/26, 교차 확인 25/26이라는 집계는 재현된다. 모두 기존 실행에 대한 재확인이다.
2. 천 단위 공백 수정에 따른 재채점은 실제 파서 결함의 수정으로 판단한다. 정답이나 금액 허용 오차를 느슨하게 해서 점수를 올린 흔적은 이 변경에서 발견하지 못했다.
3. 현재 제품이 **항상 두 해석이 일치할 때만 답하거나, 모든 출력 숫자를 빠짐없이 검증한다는 주장은 성립하지 않는다.** 한쪽 해석만 사용하는 예외, 숫자 파서 우회, 최종 Markdown 검사 누락이 있다.
4. 새 코드에는 합법적인 `확인 필요` 결과에서 렌더러가 중단되는 문제와 모델 JSON의 잘못된 타입을 처리하지 못하는 문제가 있다. 현재 209개 테스트를 모두 통과해도 이 경계는 놓친다.
5. 로드맵의 LLM 필요성 지표는 **모델 해석의 기여**를 재지만, 그것이 **현재 교차 확인 제품의 답변 개선**으로 이어지는지는 별도로 재야 한다. p06이 이미 그 차이를 보여 준다.
6. MCP·문서 작성·RAG·라우터를 한 번에 약속할 근거는 부족하다. 공통 출력·기록 계약을 정리하고 작은 문서 기능 하나를 추가한 뒤 확장 비용을 재는 순서를 권한다.

이번 확인에서 저장된 평가 원본을 무효로 만드는 치명적 손상은 발견하지 못했다. 아래의 ‘중요’ 항목은 새 평가와 공개 주장에 영향을 준다. **개발 세트 점수를 유지한다는 것과 새 입력에 안전하다는 것은 별개다.**

### A2. [중요] LLM 필요성 지표와 교차 확인 제품의 이득을 분리해야 함

- 위치: 수정안 `:66`~71, REPORT p06.
- 근거: p06에서 모델은 맞고 규칙은 틀리지만 제품은 정답 대신 되묻는다. ‘규칙 실패 중 모델 정답률’에는 성공으로 잡히고 ‘제품 최종 정답률’에는 실패다. 한쪽 미해석 때는 현재 코드가 모델만 사용하므로, 둘의 불일치와 한쪽 실패도 다른 사건이다.
- 제안: 같은 질문을 같은 도구·렌더러·출력 계약으로 비교하고 다음을 함께 사전 등록한다.

| 측정 | 필요한 분류 |
|---|---|
| 해석 기여 | 규칙 정답/모델 정답, 규칙 오답/모델 정답, 규칙 정답/모델 오답, 둘 다 오답, 각자의 미해석 |
| 제품 기여 | 정답 제공, 맞는 거절, 필요한 되묻기, 불필요한 보류, 잘못된 단정, 무응답 |
| 교차 확인 효과 | 차단한 오답, 잃은 정답, 일치한 오답, 한쪽 해석으로 낸 답 |
| 실용 비용 | 총 질문 대비 해결률, 답한 질문 중 오류율, 추가 확인 필요 횟수, 지연·토큰 |

- ‘자신 있게 틀린 답 0’만 주 지표로 두면 전부 거절하는 방식도 통과한다. 답변 가능한 세트의 최소 해결률과 보류 한도를 같이 정한다. 거절이 정답인 범위 밖/모호 문항은 보류 실패와 구분한다.
- 모델 단독은 현재 agent 루프 대신 **동일 reading JSON 1회 + 동일 도구/렌더러**로 비교하는 것이 원인 구분에 맞다. 과거 agent 결과에는 도구 계획·결정 단계·설명 생성의 차이가 섞여 있다.
- 조건부 지표의 분모가 1~2문항이면 비율만 크게 제시하지 말고 ID·개수를 함께 보고한다. LLM이 우세하지 않아도 평가 실패로 간주하거나 질문 비중을 사후 바꾸지 않는다.

- 제안: 질문 작성자에게 제품 범위만 주고 구현 규칙·실패 사례는 가린다. 정형/자유/범위 밖의 개수·난도·원문/변형 묶음을 먼저 정한다. 자유 표현을 일부러 현재 정규식이 못 읽는 표현으로만 채우지 않는다. 두 방식의 개발 예산과 동결 시점을 맞춘다.

### A7. [중요] 4단계가 너무 많은 목표를 한 번에 묶고 확장성 측정도 약함

- 위치: 수정안 `:92`~142.
- 근거: 라우터, MCP, 문서 생성, XML 수집/파싱, 검색, 임베딩, 인용/원인 검토는 각각 실패 경계가 다르다. MCP는 같은 도구의 접속 방식이며 사용자 기능 하나를 추가한 것과 동등하게 세기 어렵다. LOC·테스트 수·세션 수는 코드 이동/복제/얕은 테스트로 쉽게 좋아 보이게 만들 수 있다.
- 제안 순서:
  1. 기존 비교 기능의 입력·오류·출력·출처·기록 계약을 정리한다. 추상 프레임워크부터 만들지 않는다.
  2. 검증된 비교 결과를 모으는 **작은 Markdown 문서 기능 하나**를 만든다. 회사 수·기간·표 수 상한과 부분 실패 표현을 고정한다. XLSX는 그다음 선택한다.
  3. 외부 클라이언트 연결 목적이 명확하면 같은 도구를 MCP로 감싼다. 기능 추가와 접속 방식 재사용을 별도 성과로 기록한다.
  4. 실제 기능이 둘 이상 생기면 명시적 모드 선택과 LLM 라우터를 비교한다. ‘확신이 없으면’이라는 자기평가만으로 경계를 정하지 않는다.
  5. RAG는 별도 작은 단계로 설계하고, 새 봉인 평가를 그 기능 범위에 맞춘다.
- 확장 비용은 기능 규모/완료 기준을 고정하고 실제 작업 시간, 변경된 공통 인터페이스, 새 의존성, 회귀, 새 기능을 뺐을 때 기존 기능 독립 실행 여부, 코드 복제 여부를 함께 기록한다. LOC·테스트 수는 참고값으로 남긴다. 기능 하나의 낮은 LOC로 일반적 확장성이 증명됐다고 하지 않는다.

### A8. [중요] 기능별 완료·중단 기준이 아직 선언 수준

- 위치: 수정안 `:118`~138, 8절 위험 표.
- 제안:
  - 문서: 필수 항목의 분모, 다회사/다기간 숫자의 소속, 단위·통화·재작성 버전, 계산 불가 항목의 표기, 일부 조회 실패 시 전체 성공 금지, 최종 파일 출력 후 검증을 정한다. 글을 짧게 쓰는 것만으로 dev05의 원인 단정을 막지 못한다.
  - RAG: 키워드 단독과 하이브리드의 검색 품질·지연을 비교하고, top-k·재현율 기준·정답 근거 단위·근거 없음 문항을 미리 정한다. 인용이 존재해도 변화의 원인이라는 뜻은 아니다. 회사/기간이 맞는 무관 문장, 반대 근거, 다른 회계 범위도 넣는다.
  - 수집/도구: 문서 크기·압축 해제 상한, XML 처리, 외부 문장의 악성 지시, 다운로드/캐시 재현성, 로컬 도구의 허용 범위와 비밀값 로그 금지를 설계한다. 새 공개 도구에 숫자 검사기를 붙였다는 이유만으로 해결된 것으로 보지 않는다.
  - 중단: 평가기 버그·정답 모호성·데이터 누락이면 모델 성능 판정을 보류한다. 사전 등록 후 수정은 기존 평가와 분리해 이유/새 버전을 남긴다. 결과가 나쁘다고 봉인 문항을 개발 세트처럼 반복 조정하지 않는다.

### A9. [사소] 채용 기술의 가치·세션 추정에 근거가 부족

|---|---|---|

| FastAPI·Docker | 원격 서비스/다른 사람의 배포 재현 요구가 생길 때 | 현재는 키 없는 CLI 데모가 있으므로 필수 선행 아님 |

| RAG·하이브리드 검색 | 별도 후속 목표 | 데이터 수집·인용·설명 근거 평가까지 포함한 다른 규모의 작업 |

세션은 길이가 정의되지 않아 일정 단위가 아니다. 작업별 시간 예산과 중단 조건을 정하고, 작은 기능 하나의 실제 소요로 재추정한다. **v0.1 먼저 공개는 조건부 찬성**이다. 진행 중 프로젝트·개발 세트·사용자 미확인 판정·데모 재생임을 표시하고, 실제 안전성 보장 문구와 재배포 문제를 먼저 정리해야 한다.

5. 회사명 생략 등 본문 판정 경계를 사용자가 확인한다. 자동 채점 오탐 정정과 최종 진행 gate(B9·B10)는 **3-1 사전 등록 전에** 명확히 한다.

### 나중에 해도 되는 것

- MCP, LLM 라우터, XLSX, RAG, LangGraph, API 서버·Docker, 상용 비교.
- 데모 schema 해시 강화, CLI 영속 로그, 새 모드용 rescore 확장. 각각 실제 기능을 공개/재채점하기 전에 보완한다.
- consistency를 더 많이 실행하거나 온도를 바꾸는 추가 실험. 지금은 기존 기록의 한계를 명시하는 것으로 충분하다.

### 진행·전환 의견

모델에 올바른 근거를 줘도 본문 최종 1/13이라는 실패는 회사명 생략 경계를 완화해도 사라지지 않는다. **사실 문장을 코드가 만드는 전환은 기존 근거에 부합한다.** 다만 그것만으로 모델 해석이 일반적으로 정확해졌다거나 교차 확인이 항상 안전해졌다고 할 수 없다.

현재 증거는 “이 26개 개발 문항에서 교차 확인이 기준선의 오답 1개를 되묻기로 바꿨다”까지다. 그 효과가 약 306초의 총 모델 시간과 사용자 확인 부담을 감수할 가치가 있는지 다음 사전 등록 평가가 판단해야 한다. LLM의 필요성을 증명하는 결론을 미리 정해 놓으면 안 된다.

## 7. 확인 범위와 미확인 사항

**직접 확인:** 적용 지침·깨끗한 시작 상태, 요청된 코드와 관련 문서/테스트, E1~E10 재현, 26개 본문, 주요 실행 8폴더 집계, U+202F 재채점 원인 분리, 158개 요청 기록의 내부 일관성, 가짜 전송 경계, 캐시/축소 데모 5개 동등성, 추가 합성 경계 사례.

**확인하지 않음:** 실제 모델 재실행·재현 확률·현재 런타임 상태, OpenDART 서버의 최신 자료, 봉인 회사 자료, 최신 채용 수요, 이용약관·재배포 허용 여부, 실제 공개/새 원격 클론/새 기기 설치. consistency의 원시 응답·실측 14분은 기록이 없어 독립 확인 불가. 209개 통과를 제품 신뢰성이나 새 모델 성능으로 해석하지 않는다.

현재 완료 수준: Part A·B 감사와 오프라인 재검증 완료. 제품 수정·공개·새 평가 실행은 하지 않음.

이번 범위에서 남은 필수 작업: 없음.

사용자가 지금 할 일: 이 보고서를 Claude에 전달하고, 먼저 3-0 필수 수정안과 한쪽 해석 실패 시 보류 정책을 결정하면 됨. 기존 결과 파일을 다시 만들 필요 없음.

추가 프롬프트가 필요한지: 감사는 완료. 실제 수정 착수를 위해서는 수정 범위 승인 필요. 아래 문장을 그대로 전달할 수 있음.

> `docs/reviews/roadmap_proposal_codex_result.ko.md`를 읽고 B1~B7을 재현해 수용/부분 수용/비수용과 이유를 먼저 기록해 줘. 이번에는 합의된 출력·해석 정책과 코드 결함의 최소 수정, 관련 오프라인 회귀 테스트, README·로드맵 정합성 수정까지만 진행해 줘. 교차 확인 기본 모드는 한쪽 해석 실패 시 보류하는 방향을 우선 검토하고, 명시적 --no-model은 구분해 줘. 기존 평가 점수와 원본 로그는 보존하고, 사후 채점 변경은 전후를 별도로 남겨 줘. 봉인 데이터 열람·모델 재실행·외부 전송·MCP/RAG 구현은 하지 마. A2~A6의 정책 선택이 필요한 항목은 3-1 사전 등록 전에 정리해 줘.

다음 권장 작업과 그 이유: 새 기능 추가보다 **현재 출력/오류 경계 수정과 평가 계약 확정**. 그래야 다음 봉인 평가 결과가 모델 문제와 제품·채점기 문제를 구별할 수 있음.

## 부록 — 핵심 반례를 다시 확인하는 짧은 코드

아래는 저장소 루트에서 실행하는 오프라인 코드다. 기존 파일에 쓰지 않는다. 더 긴 E1~E10 입력은 `1-5_codex_result.ko.md` 부록에 보존되어 있다.

```python
import json, sys
from unittest.mock import patch
sys.path[:0] = ['.', 'eval', 'tests']
from dart_review import numbers, crosscheck, demo
from dart_review.llm import Reply, ScriptedChat
from dart_review.cache import ResponseCache
from dart_review.client import DartClient
from test_crosscheck import model_reading
from scoring import says

allowed = numbers.allowed_from({'period': {'end': '2025-09-30'}})
for text in ('20250930만 원', '20250930%', '20250930배'):
    print(text, [(c.mention.kind, c.grounded)
                 for c in numbers.check_text(text, allowed)])
# 실제: 세 경우 모두 year/calendar/calendar, 모두 True

for field in ('account', 'basis'):
    reading = crosscheck.model_to_reading(crosscheck.parse_model_reading(
        json.dumps(model_reading('dev01', **{field: []}))))
    try:
        print(crosscheck.canonical(reading.kind, reading.arguments, reading.company))
    except TypeError as exc:
        print(field, type(exc).__name__)
# 실제: 둘 다 TypeError

print(says('흑자 전환했으며 적자는 아니고 이익입니다.', '흑자 전환'))
# 실제: False

def no_key():
    raise AssertionError('No key access')
client = DartClient(ResponseCache(demo.ROOT / 'cache'), key_loader=no_key, offline=True)
original = demo.markdown_report
with patch.object(demo, 'markdown_report',
                  lambda a, r: original(a, r) + '\n영업이익률은 99.9%입니다.\n'):
    result = demo.answer(demo.DEMO_QUESTIONS[0], client,
                         ScriptedChat([Reply(json.dumps(model_reading('dev01')))]))
    print(result['withheld'], '99.9%' in result['report'])
# 실제: None, True — 정상 생성의 관찰이 아닌 출력 경계 변이 검사
assert client.network_requests == 0
```
