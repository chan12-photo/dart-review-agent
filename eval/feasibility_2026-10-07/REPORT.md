## 3. 관찰 (규칙을 바꾸지 않고 기록만)

- **출력 한도 도달 1건:** ③ dev04의 두 번째 요청이 생각 과정 7,510자로 `num_predict` 4,096에 닿았다(`done_reason: length`). 내용은 나왔고 최종 답도 정상이었다. 실행기는 `length`를 따로 표시하지 않는다. 다음 수정 후보.
- 답은 26개 모두 한국어였다(local-agent-lab 모델 확인에서는 영어 답이 많았다).
- 생각 과정 길이: ② 중앙값 1,402자, ③ 794자. `think`를 보내지 않아도 생각 과정이 나온다.
- ② dev12에서 모델은 되물으면서 `account`에 영업이익을 채웠다. 실행 전에 정한 규칙(되묻기면 계정은 null)에 따라 실패로 셌다.

사용자 판정이 다르면 사용자 판정을 따르고, 두 판정을 모두 남긴다. 다만 해석 1을 완화해도 ②는 기준(11/13)에 크게 못 미친다. 한 단어 답, 이유 생략, 근거 없는 제안만으로도 5문항이 실패하기 때문이다.

## 5. 판정 전에 남은 일

1. 사용자가 `oracle/human_review.json`, `full/human_review.json`의 1차 판정을 확인한다(특히 4절의 두 해석).
2. Codex 재검증: 평가 장치 수정분(`fe8c198`, `0a684e6`), 재채점 절차, 본문 검토가 기준대로 됐는지.
3. 그다음 SCOPE 10절 기준으로 판정한다(엑스트라 모드). 참고로 SCOPE 10절은 "정답 근거를 줘도 60% 미만이면 모델이 병목: 상용 API 비교 검토(승인 필요) 또는 범위 축소", "Agent가 기준선을 이기지 못하면 '검증 도구 + LLM 설명'으로 재정의"를 미리 정해 두었다.

판정 전이라 결론을 쓰지 않는다. 다만 판정 때 검토할 근거로 한 가지를 기록해 둔다. **구조화된 칸은 정확했고 본문만 부실했다.** 따라서 사실 문장(숫자·기간·기준·상태 이유)은 코드가 검증된 구조에서 만들고, 모델은 질문 해석·상태 선택·설명에 집중하는 구조(Codex 1-5 검토 E3의 제안, SCOPE 10절의 "검증 도구 + LLM 설명")가 하나의 선택지다. 이 결과를 보고 프롬프트를 고쳐 같은 13문항으로 다시 점수를 올리는 실험은, 판정 전에 하지 않는다.

## 6. 잠정 판정 (2026-10-07)

- 상태: **잠정.** 사용자가 "Codex 재검증은 나중에 하고 진행"을 선택했다. 본문 1차 판정의 사용자 확인과 Codex 재검증은 뒤로 미뤘고, 결과가 이 판정을 바꾸면 다시 판정한다.
- **SCOPE 10절 기준:** ② 근거 제공 최종 1/13(경계 포함 2/13)으로 80%는 물론 60%에도 못 미친다. 근거 없는 숫자도 ②·③ 모두 0이 아니다. **현재 구조(모델이 사실 문장까지 직접 작성)로는 통과하지 못했다.**
- **원인 분리:** 구조화된 칸(상태 13/13, 숫자 10/10)은 맞았고, 실패는 본문 작성에 몰렸다. 모델의 해석·판단보다 "사실 문장 작성"이 병목이다.
- **결정: 설계 전환.** SCOPE 10절에 미리 정한 대안 "검증 도구 + LLM 설명"으로 바꾼다.
  - 숫자·기간·기준·상태 이유를 담은 **사실 문장은 코드가 검증된 구조에서 만든다.**
  - 모델은 질문 해석(도구 인자), 상태 선택, 되묻기, 짧은 해석 문장만 맡는다. 모델 문장의 숫자는 출력 전 검증(로드맵 2-3)을 통과해야 한다.
  - 상용 API 비교는 하지 않는다(필요해지면 사용자 승인 후).
- **하지 않는 것:** 같은 13문항으로 프롬프트를 고쳐 점수를 올리는 실험. 새 구조는 2단계에서 만들고, 같은 개발용 문항과 같은 기준으로 다시 잰다. 결과는 이번 점수와 나란히 보고한다.
