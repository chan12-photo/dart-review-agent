## 2. 퇴보와 실패: 두 건 모두 프롬프트의 "month" 정의 문제

### dev06 — reading-v1·v2에서는 맞았고 v3에서 틀렸다

- 질문: "카카오의 2023년 3분기 매출은 직전 분기보다 얼마나 늘었어?"
- v3 모델 해석: current와 base 모두 `{"kind": "quarter", "year": 2023, "month": 3}`.
- 생각 과정에서 모델은 프롬프트의 "month는 3, 6, 9, 12"를 분기 길이로 이해했다("quarter는 3개월이니 month는 3").
- 같은 문장은 v1·v2 프롬프트에도 있었고, 그때는 맞게 읽었다. **질문과 관계없는 프롬프트 부분이 바뀌자 같은 모델이 같은 질문을 다르게 읽었다.**
- 결과: 규칙 해석과 달라 되물었다. 틀린 답은 나가지 않았다. 다만 되묻기 선택지 ②가 "2023년 1분기를 2023년 1분기와 비교"라는 의미 없는 해석으로 사용자에게 보인다.

### L07 — 모델이 답을 내지 못했다(출력 한도)

- 질문: "카카오 2025년 4분기 매출 알려줘".
- 모델의 생각 과정이 "month가 필요한가?"를 반복하다 `num_predict` 4,096 토큰에 닿았다(`done_reason: length`, 생각 과정 17,225자, 답 0자).
- 정책(EVAL_DESIGN 11.1)대로 규칙 해석만으로는 답하지 않았다. 규칙 해석(조회, 4분기 3개월)은 맞았고, 그대로 냈다면 `조회 불가`가 정답이었다.
- 이 기록은 `length_stops`에 L07로 집계된다.

### 해석

- 두 건 모두 기간 표기의 `month`가 "기간이 끝나는 달"이라는 정의가 프롬프트에 분명하지 않아 생겼다. 예시("3분기 매출은 quarter, month 9")는 이미 있었는데도 모델이 혼동했다.
- 교차 확인과 보류 정책 덕분에 두 건 모두 틀린 답은 나가지 않았다. 그러나 답할 수 있는 질문 두 개를 답하지 못했다.
- 모델 해석은 프롬프트 변화에 민감하다. 프롬프트를 바꿀 때마다 전체 세트를 다시 재야 하는 이유다.
